# 事件认证与恢复

读取时机：设计或审查 webhook、notification、replay、异步状态和超时恢复时读取。认证算法、header、确认码、事件保留期和 scope 字段均是厂商适配事实，先查 [厂商时效事实](provider-facts.md)。

## 强制处理顺序

1. 保留原始载荷和认证元数据；在解析或产生资金副作用前，完成厂商适配的原始载荷认证。
2. 校验 `provider`、环境/账户等 scope 和允许的 endpoint/版本；scope 不匹配即拒绝。
3. 以 `provider + scope + event ID` 建立耐久去重记录。缺 event ID、认证或耐久存储时，不执行资金副作用。
4. 将事件作为刷新线索，使用适当 scope 查询权威当前对象、账务或报告，并作幂等、单调投影。
5. 保存失败原因、对象关联、重放游标和最后权威检查时间；查询失败保持待处理，恢复后再投影。

不得依赖到达顺序或事件时间戳重建权威资金流水，也不承诺 exactly-once。重复、乱序、迟到和 replay 是正常输入：重复不得重复副作用，旧事件不得覆盖较新权威事实，漏收须能由查询、replay、报表或人工调查收敛。

## 最小验证场景

验证认证失败、scope 不匹配、重复投递、已观察到较新权威事实后收到较旧事件、查询失败恢复、replay 及迟到逆向资金。证据须说明已验证的对象、事件、账务影响和恢复代码路径；不能从模拟结果推出真实网络、银行、容量、风控、合规或生产批准。
