### 高风险基础题完整性索引

以下只做检索检查，具体定义和规则仍以下文章节及其专项 reference 为准。涉及资金状态修改、完成承诺、通道切换、调账、出款或上线时，裁剪答案前先核对：

- 完成层级：业务义务、支付意图、支付尝试、外部处理、内部账务、清算、结算、到账和对账分别给出证据或 Owner；证据不足的层级保持待确认。
- 银行余额差异：分开产品账户、内部账本账户、会计科目和银行/真实资金账户；在试算平衡之外逐项检查企业已收银行未收、企业已付银行未付、银行已收企业未收、银行已付企业未付。余额调节表不直接改账，错账经审批追加修复后重新对账。
- 交易与混合支付：分开订单、计价、账单/支付义务、支付分配、各次支付尝试和履约；优惠不当支付工具，取消或退款关联原订单、原支付和已发生的资金事实。
- 超时恢复：保留支付意图和每次尝试，未知不改失败；先以原幂等语义回查，切换通道前控制重复扣款，并覆盖迟到成功、冲突结果和人工处理。
- 清结算：分开内部清分候选、机构间清算、商户结算和真实到账；规则、数据或授权变化使候选失效或重算，`T+N` 同时核对时区、cutoff、日历、币种、费用、冻结和失败恢复。
- 账务与对账：原事实、分录、匹配结果和差异对象不可变，修复后发起新对账；重复过账同时检查业务幂等键、posting plan 平衡和余额投影。
- 钱包与产品：分开产品、账本和外部资金三层，并沿六个设计面说明资金归属、业务原因、真实资金支持、可用时点、冻结/出款权限、风险承担、最终确认和退出；MVP 不删除资金安全、账务、对账、权限和合规基本控制。

## 1. 支付基础

### 支付解决什么问题

支付承接已经形成的业务义务，通过双方认可的支付工具和支付轨道，把付款指令、机构处理、账务记录与真实资金变化连接起来。产品设计不能只问“页面是否显示成功”，还要回答：

- 谁向谁履行什么义务，金额和币种是什么。
- 谁发起、授权、受理、执行、记账、清算、结算和最终确认。
- 每一层产生什么单据、状态、外部引用和证据。
- 失败、超时、重复、逆向和差异如何关闭。

### 基础概念边界

| 概念 | 解决的问题 | 不等于 |
| --- | --- | --- |
| 支付场景 | 在什么业务和终端中发生支付 | 支付方式或通道 |
| 支付工具/方式 | 用户用什么履行付款义务 | 具体通道账户 |
| 收银台 | 交易与支付之间的用户或系统接入产品 | 支付核心本身 |
| 支付通道 | 外部机构、账户和协议能力的接入集合 | 用户看到的支付方式 |
| 支付路由 | 在已满足资质、语义和风险约束的候选通道中选择执行路径 | 超时后盲目换通道 |
| 账户 | 归属于某主体、表达特定权利义务或余额口径的容器 | 会计科目或真实银行资金 |
| 清算/清分 | 交换信息并计算应收应付 | 资金已经到账 |
| 结算/出款 | 根据已确认规则执行余额释放或真实资金划拨 | 收款方银行已经最终入账 |
| 对账 | 用两个或多个独立来源证明一致或解释差异 | 修改数据直到差额为零 |

### 完成层级

常见完成链为：业务义务形成 -> 支付意图/账单 -> 支付尝试 -> 外部受理/授权 -> 外部资金事实 -> 内部账务 -> 清算/结算 -> 银行或目标账户到账 -> 对账与财务确认。

这些层级可以异步、并行或部分发生，不能压成一个 `SUCCESS`。具体对象和完成证据继续读取 `object-and-completion.md`。

## 2. 会计基础

### 会计恒等与复式记账

- 基本恒等式是资产 = 负债 + 所有者权益；收入和费用通过权益变化进入扩展表达。
- 复式记账要求同一经济事实在已确认的账簿和科目口径下保持借贷平衡。
- 借方、贷方是记账方向，不天然等于流入、流出、增加或减少；方向取决于账簿主体、账户性质和会计政策。

### 从业务事实到财务结果

```text
业务事件
  -> 原始证据/外部回执
  -> 账务事件与凭证规则
  -> posting plan
  -> 不可变分录
  -> 账簿与余额投影
  -> 总分核对、结账和报表
```

产品经理应定义业务事实、金额、币种、责任主体、记账时点和证据引用，由财务或账务 Owner 确认科目、借贷方向、收入成本确认和报表政策。

### 凭证、账簿与平衡验证

- 原始凭据证明经济事项发生；记账凭证依据原始凭据和已确认会计政策确定科目、借贷方向、金额与会计日期，两者必须可追溯但不能混为一物。
- 序时账按发生顺序保留记录，明细账按对象或明细科目展开，总账按总账科目汇总；产品账户、账本账户、会计科目和银行账户不是天然一一对应。
- 试算平衡只能检查借贷发生额或余额在算术上是否相等，不能证明没有漏记、重记、科目误用、金额等额记错或事实不真实；还需总分核对、外部对账和财务复核。
- 财务报表按核算主体、会计期间和政策汇总财务结果，不是支付对象状态或外部资金到账状态的替代品。

### 银行存款余额调节

企业账与银行对账单的差异可能来自双方入账时点不同，也可能来自记账错误。常见未达账项包括企业已收银行未收、企业已付银行未付、银行已收企业未收、银行已付企业未付。

余额调节表用于解释并验证调节后口径，本身不直接修改账簿。真实未达项应保留来源、日期、金额和后续到账证据；发现错账时按审批后的更正、冲正或调账凭证处理，再重新对账。

### 必须分开的账

- 客户或商户可见账：可用、冻结、待结算、在途等产品余额。
- 平台内部账本：支付、退款、清分、费用、分账、调账和差错事实。
- 外部机构账：通道、清算机构、银行或卡网络的交易与结算记录。
- 真实资金账：银行、存管、客户备付金、清算账户或资金池中的现金变化。
- 会计账：凭证、科目、明细账、总账和财务报表。

一个余额正确不能证明其他账簿完整或真实资金已到账。

## 3. 支付清算生态与基础分析能力

### 参与者和层级

支付场景通常涉及付款人、收款人、商户/平台、支付服务商、收单或账户侧机构、清算网络、银行和最终结算基础设施。正式方案先确定每个参与者的合同、资金、数据、风险和客服责任，不按机构名称猜职责。

可以按以下层级理解，但不得强制映射为独立系统：

1. 交易服务：选购、计价、订单、账单、履约和售后。
2. 支付服务：收银台、支付核心、支付尝试、通道适配、风控和通知。
3. 清算与账务：清分候选、确认、分录、余额、结算单和对账。
4. 外部网络与金融服务：支付机构、清算网络、银行、代理行和资金账户。
5. 财务、风险和合规：财务确认、审计、争议、监管和运营闭环。

### 机构角色与系统边界卡

同样叫“交易、支付、账户、清算”，平台商户、非银行支付机构、银行或清算机构承担的对象和责任可能完全不同。进入模块划分、账户设计或会计分录前，先冻结：

- 我方主体、法域、资质和合同角色；代谁受理、记账、持有或划转资金。
- 当前核心对象是业务订单、支付义务、支付意图、支付尝试、通道操作，还是外部资金事实。
- 清分对象与规则 Owner：按业务订单、履约、支付事实、合同费项还是外部清算文件计算。
- 记账触发、账本 Owner、会计政策确认方，以及产品账户、账本账户、会计科目和真实资金账户的映射。
- 每个完成层级的证据 Owner；谁能确认支付、清算、结算、到账、对账和财务完成。

机构名称、系统模块名、页面余额或“平台碰过资金”都不能单独确定上述答案。主体、资质、合同或资金控制权未确认时，停止具体分录、结算路径、“二清”和生产合规结论。

### 四流分析

- 业务流：交易义务、履约、售后和责任变化。
- 支付信息流：请求、授权、外部状态、通知、查询和回执。
- 账户/账务流：冻结、解冻、入账、扣减、冲正、调账和结转。
- 真实资金流：外部账户之间实际发生的扣款、清算、结算、出款和到账。

分析一笔支付时，沿四流回答：谁的钱、因何业务、沿何轨道、形成何种事实、如何记账结算、由谁最终确认。

## 4. 交易

### 核心对象

| 对象 | 主要职责 |
| --- | --- |
| 商品/服务项 | 描述交易标的、数量、价格和履约要求 |
| 计价结果 | 解释原价、优惠、税费、运费、应付和各方承担 |
| 订单 | 记录买卖义务、标的、履约和售后事实 |
| 账单/支付义务 | 表达某主体在某期限内应支付的金额和币种 |
| 支付分配 | 表达一笔账单如何由一个或多个真实支付工具履行 |
| 履约记录 | 证明商品、服务或权益是否交付 |
| 退款/售后单 | 表达业务逆向诉求，不替代外部退款执行事实 |

订单、账单和支付记录的数量关系由目标业务决定，不预设一对一或一对多。优惠、满减和商户折扣通常属于计价或资金承担，不因参与金额计算就自动成为支付方式。

### 正向、履约与逆向

交易系统产生支付需求，支付系统执行支付，履约系统交付商品或服务。支付成功不自动证明履约完成；取消、退款、撤销和拒付也不是同一对象。逆向处理必须关联原义务、原支付和已经发生的清算、结算与账务事实。

## 5. 支付

### 稳定对象

- 支付意图或支付单：描述本次要完成的支付义务。
- 支付尝试：记录一次具体支付方式、通道和请求语义。
- 通道操作：保存外部请求、响应、引用、状态和回查证据。
- 授权/扣款/清算事件：按支付轨道表达不同外部事实。
- 退款、撤销、冲正和争议：各自形成独立逆向事实。

### 处理主线

```text
校验业务义务和请求权限
  -> 创建支付意图/尝试
  -> 风控与路由决策
  -> 通道适配和外部请求
  -> 同步响应、异步事件与主动查询收敛
  -> 生成可审计内部事实
  -> 驱动账务、履约、清结算和通知
```

同步返回、外部受理、授权、捕获、清算、结算和银行到账的语义随支付轨道而变。超时表示结果未知，不代表失败；切换通道前必须先处理幂等、状态回查和重复扣款/重复出款风险。

## 6. 清算与结算

### 先定语境

- 内部清分/内部清算：平台按合同、计费和分账规则计算参与方应收应付，不是持牌清算业务。
- 网络或机构间清算：外部网络按正式规则交换支付信息、形成金融债权债务或清算文件。
- 商户结算：把已确认可结算金额释放到商户余额或形成出款。
- 资金结算/到账：真实资金在银行、清算账户或目标账户完成划拨并取得权威证据。

### 内部清结算事实链

```text
冻结业务范围和规则版本
  -> 计算费用、分账与应收应付
  -> 生成可审查清算候选
  -> Owner/规则门禁确认
  -> 形成账务事实和可结算口径
  -> 生成结算批次与出款指令
  -> 获取外部执行、到账和对账证据
```

清分快照和清算候选只是计算结果。确认前规则、数据或授权发生变化时必须失效或重算。结算规则至少说明对象、方向、周期、时区、cutoff、日历、币种、费用、最低金额、风险冻结、出款路径和失败恢复。

## 7. 账务

### 账务事实链

业务事实、账务交易、posting plan、分录和余额投影是不同对象：

1. 业务事实提供来源、主体、类型、金额、币种和幂等键。
2. posting plan 按已确认规则生成待记分录并先校验平衡。
3. 过账追加不可变分录，不覆盖原事实。
4. 余额是分录的投影，按可用、冻结、待结算、在途等口径展示。
5. 错账通过冲正、更正、调账或挂账追加修复，再由对账重新证明。

### 在线与日终

- 日间联机处理支付、退款、冻结/解冻、授权占用和即时余额要求。
- 日切确定业务与会计日期归属，不只是修改日期字段。
- 日终处理批次汇总、渠道结转、总账汇总、试算平衡、总分核对、差错和报表。
- 缓冲或异步记账必须保留批次、幂等、余额可见性、风控限制、补偿和人工兜底，不能以性能为由牺牲账务平衡。

## 8. 对账

### 对账对象

对账至少可能覆盖业务订单、平台支付、账务分录、通道交易、清算文件、结算文件、银行流水、商户账单和财务总账。对账双方、粒度和权威来源随场景变化，不固定为一种“四段式”命名。

### 对账运行

1. 冻结对账项目、业务日、范围、数据来源和规则版本。
2. 保留原始字段与加工字段，支持一对一、一对多、多对一、手续费拆分和跨日匹配。
3. 生成不可变匹配结果和差异对象，区分单边、金额、状态、手续费、重复和延迟。
4. 将差异原因、处理动作、Owner、审批和证据追加记录。
5. 补事实、冲正、调账、挂账或核销后发起新的对账运行。

对账目标不是机械清空差异列表，而是证明一致，或让每个重大差异拥有可解释原因、责任、规则化处置和证据。不得删除单边记录、覆盖历史结果或只把状态改成已核销。

## 9. 资金处理

### 能力范围

- 资金账户和头寸：识别真实账户、币种、余额、可用性和归属主体。
- 调拨与归集：在有授权的账户之间调整资金位置，记录申请、审批、执行、到账和记账。
- 线下汇入：获取银行到账事实，匹配付款人、附言和业务义务，处理无法识别、重复和退款。
- 结算与出款：将可结算金额转化为出款指令，处理审批、限额、失败、退汇、重复和回单。
- 流动性与风险：按预测、保证金、准备金、争议、退款和运营要求管理可用资金。

### 控制边界

- 内部账本余额不能替代银行或外部资金事实。
- 资金调拨、出款和结算账户变更必须有权限、审批、幂等、回读、对账和审计。
- “二清”、客户资金、客户备付金、资金归集和跨境收付属于法律与监管高风险语境，不能只按资金经过次数判断，必须核验法域、主体、资质、合同和资金控制权。

## 10. 钱包

### 钱包是什么

钱包是面向用户、商户或平台提供余额、入金、出金、支付、转账和资金管理体验的产品层。钱包账户通常是内部虚拟账本的产品投影，不天然等于银行账户、支付账户、客户备付金账户或央行账户。

### 三层职责

1. 产品层：开户/销户、余额展示、充值、提现、消费、转账、冻结、限额和明细。
2. 账本层：账户、交易、分录、可用/冻结/待结算/在途余额和不可变事实。
3. 外部资金与通道层：银行账户、支付通道、存管/客户备付金安排、出入金、回执和对账。

钱包设计必须说明余额归谁、为什么变化、何时可用、由什么真实资金支持、谁能冻结或出款，谁承担充值拒付、退款争议、负余额、通道失败和资金缺口，以及由什么外部回执、账本和对账证据最终确认。退出时还要处理冻结、未结交易、退款争议、余额退回、权限吊销及数据和证据留存。银行钱包、非银行支付账户、商户余额、企业内部钱包和数字人民币钱包不能共用一套法律、账户或资金结论。

## 11. 支付产品方法论

### 先收敛问题

设计前用一条主轴收敛：谁的钱，因什么业务，在什么主体和账户下，沿哪条支付轨道，以什么规则流转，何时可用，谁承担风险，谁最终确认。

### 六个设计面

1. 主体与责任：合同、资质、授权、资金、数据、风险和客服责任。
2. 业务与对象：场景、业务义务、订单、账单、支付、履约、逆向和退出。
3. 接入与执行：收银台、API/SDK、支付方式、支付核心、通道、事件和查询。
4. 资金与账务：账户、分录、清分、结算、出款、FX、费用和对账。
5. 风控与合规：身份、商户、交易、限额、欺诈、争议、数据和外部规则。
6. 运营与证据：权限、配置、报表、工单、审计、告警、人工处理和验收。

合规、资金安全、对账和异常恢复不是最后补齐的层。它们从场景和主体确定时就约束能力、接口、系统和上线范围。

### 收银台前后端联合观测

收银台体验与支付执行必须分别观测，再通过不携带敏感支付数据的关联标识对齐：

- 前端漏斗记录加载开始/完成、支付方式展示/切换、确认、调起/跳转、结果页展示、重试和离开，用于解释用户在哪一步流失。
- 服务端记录支付意图、支付尝试、路由候选与排除原因、通道请求、同步/异步/查询收敛、权威结果、耗时和恢复，用于解释交易为什么成功、失败或未知。
- 指标同时声明分母、时间窗、终端、商户、支付方式、通道和失败原因口径；页面展示成功不能替代通道、账务、结算或到账证据。
- 埋点只收集当前分析和风控所必需的信息，敏感账户数据、认证要素、密钥和不必要的完整身份/交易明细不得进入普通分析事件；前端事件也不能作为授权、扣款或履约的唯一证据。

支付方式展示排序、支付尝试路由、资金出款路由和清结算路由继续分别建模；联合观测只用于关联解释，不合并它们的责任和状态。

### 从需求到验收

```text
定义场景、主体和非目标
  -> 画四流并冻结资金责任
  -> 建模对象、状态、规则和完成证据
  -> 设计正向、逆向、异常和人工处理
  -> 补账务、清结算、对账、风控和运营
  -> 用真实轨道、事件、报表和资金证据验收
```

支付产品的最小版本可以缩小业务范围和用户范围，但不能删掉当前范围内防止错扣、重复出款、账务失衡、资金不可解释或合规违规的基本控制。

## 常见误区

- 用支付成功替代履约、清算、结算、到账或财务确认。
- 把优惠、卡券或价格减免直接当成真实支付工具。
- 用一个状态机承载订单、支付尝试、通道、退款、争议、结算和对账。
- 把客户可见余额、内部账本、外部清算结果和真实银行余额都称为“账户余额”。
- 按固定时效、费率、限额、借贷方向或外部规则设计通用产品。
- 通道超时后直接置失败或切换通道重试。
- 修改原交易、分录或对账结果制造一致。
- 把课程、极简版材料、sandbox 或本地测试当成会计、监管或生产证据。
