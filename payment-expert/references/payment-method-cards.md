## 按任务读取索引

| 任务 | 优先读取 | 跳过 |
| --- | --- | --- |

| 单一银行/卡网络状态、文件或协议 | `M09` | 不展开多通道抽象 |

## 统一答题协议

每张方法卡输出都必须区分：

1. `事实`：已有页码、正式设计、源码、测试或 Owner 证据。
2. `推断`：从事实外推的设计建议，说明推断链。
3. `待确认`：缺失规则、Owner、时效来源或责任边界。
4. `范围外不做`：不根据课程生成生产接口、会计分录、监管结论或渠道参数。

## M01 分层完成证据与事实分解

**来源候选**：`C02`。
**成熟度**：D2 方法草案。
**Owner**：支付产品/清结算 Owner。

### R 证据

[S1:p033-p090; p207-p220]；`PAY-003`、`TRD-004`、`PAYCORE-004`、`XBD-005`。

### I 方法骨架

将一个支付场景分解为交易承诺、支付执行、履约、清算、账务、结算和对账事实。每层使用自己的对象、状态、产生者和完成证据，不用上游或相邻层的“成功”替代本层结果。

### A1 案例

- 项目 2：外部已付订单仍需支付证据映射、履约、清结算和对账。
- 跨境代发：外部受理、在途、到账、失败和退汇不是一个状态。

### A2 触发

- 设计或评审支付状态机、完成条件、域间事件。
- 用户说“支付已成功，为什么还没到账/履约/结算”。
- 不用于决定必须拆成几个物理服务或表。

### E 执行

1. 列出业务承诺、参与主体和目标资金结果。完成标准：能说清“谁对谁承诺什么”。
2. 按层列出事实对象、状态与权威证据。完成标准：每个“已完成”都有可查证的记录或外部证据。
3. 标出跨层推进条件与失败分支。完成标准：不存在一个状态直接代替多层完成。
4. 输出已知事实、缺失证据与 Owner 问题。判停：本层权威证据或 Owner 不明时，停止自动推进。

### B 边界

- 业务语义分层不强制物理拆分。
- 不以卡授权、同步返回或外部受理代替结算到账。
- 不用课程模型裁决法律、会计或机构最终性。

**已有压测**：`PT-001`、`PT-002`、`PT-010`、`PT-025`、`PT-027`。

## M02 稳定资金内核与通道差异适配

**来源候选**：`C03`。
**成熟度**：D2 方法草案。
**Owner**：支付/通道架构 Owner。

### R 证据

[S1:p049-p055; p193-p222]；`PAYCORE-001`、`CHN-004`。

### I 方法骨架

先提取不随单一通道变化的请求、幂等、路由、单据、资金动作和结果收敛，再把报文、文件、鉴权、外部状态和 return 规则留在通道适配层。资金底座只接收已解释、可审计的内部事实。

### A1 案例

- 支付核心主流程：通道差异进入明确扩展点。
- ACH/VCC 资金边界：资金域不承接银行协议、issuer 协议或 PCI 系统。

### A2 触发

- 比较两个及以上卡、钱包、A2A、VA、ACH 或代发场景，提取稳定内核和差异扩展点。
- 单一通道的协议、字段或外部状态解释转交 `M09`。
- 不用于共享不变量尚未识别的单一局部需求。

### E 执行

1. 列出跨通道稳定的内部动作与不变量。完成标准：能用内部语义描述，不依赖供应商字段。
2. 列出通道特有的协议、文件、状态、安全与重试规则。完成标准：每个差异有明确适配 Owner。
3. 定义“外部事实 -> 内部事实”映射契约，保留来源引用、版本和核验状态。
4. 定义同步、异步通知、主动查询和文件的收敛顺序。判停：正式通道契约未取得时，不生成生产映射。

### B 边界

- 不因一个通道做过就提前建通用抽象。
- 不把外部未核验状态直接转为账务事实。
- 不让资金底座吞入通道协议、文件和密钥责任。

**已有压测**：`PT-019`、`PT-030`、`PT-031`。

## M03 退款原事实、累计额度与外部幂等

**来源候选**：`C06`。
**成熟度**：D2 方法草案。
**Owner**：退款/资金 Owner。

### R 证据

[S1:p057-p063]；`S2-REFUND-001`、`S3-VCC-001`、`REFUND-002`。

### I 方法骨架

退款必须从可证明的原支付或授权事实出发，分开退款请求与外部执行记录，以累计可退额约束多次执行。重复回调只有在外部事实语义完全一致时才能幂等，同一标识下的金额或结果冲突必须停止。

### A1 案例

- 部分退款：多次退款的累计金额不得超过原支付可退额。
- 退转付：原路不可用时仍不能脱离原退款义务，但替代履行本身仍是 D1/D2 混合候选。

### A2 触发

- 部分退款、多次退款、重复 webhook、原支付关联和可退额计算。
- 用户问“这条重复通知能不能直接幂等”。
- 不用于赔付、补偿或无原支付的独立债务。

### E 执行

1. 核验原支付/授权、主体、币种、成功金额和可退资格。
2. 计算可退余额：原可退额减已成功与已锁定退款。判停：本次金额超额时拒绝。
3. 分离退款请求和外部执行事实，保留原支付号、外部事实号和金额/状态。
4. 处理通知：标识与语义一致则幂等；标识相同但金额或结果冲突则停止并留证。

### B 边界

- 不把受理或处理中当成最终退款成功。
- 不把赔付、营销补偿或债务清偿写成原路退款。
- 退款时效、次数和替代产品以目标通道与 Owner 规则为准。

**已有压测**：`PT-007`、`PT-032`、`PT-033`。

## M04 清分/清算候选、确认与资金动作分离

**来源候选**：`C08`。
**成熟度**：清分/清算范围为 D2 方法草案；提现预计算与 FX 报价仅作待验证类比。
**Owner**：清结算/FX/资金 Owner。

### R 证据

[S1:p072-p078]；`CLR-002`。

### I 方法骨架

把清分快照和清算候选视为可审查的计算结果，不视为已入账资金事实。只有在快照、规则、授权和门禁均通过后的清算确认动作，才能触发账务或余额变化。

### A1 案例

- 清分/清算：清分批次和清算候选无账务副作用，清算批次确认才产生资金变化。
- 提现预计算和 FX 报价具有相似的“先计算、后执行”外观，但当前 D2 证据不证明它们采用相同确认语义。

### A2 触发

- 清分批次或清算候选。
- 用户问“计算结果已生成，是不是已经可用/可结算/已扣款”。
- 对 FX 报价、提现预计算或批量付款计划，仅用于提出核验问题，不能直接套用本方法结论。
- 不用于不产生资金副作用的普通展示计算。

### E 执行

1. 标记当前产物是清分快照、清算候选、已确认事实还是已过账事实。
2. 冻结来源、规则版本、金额、币种、时效和计算结果。
3. 定义确认主体、授权和失效/重算条件。判停：规则或快照已变化时不允许确认。
4. 确认动作产生独立资金事实，再由账本过账并进入对账。

### B 边界

- 是否自动确认、是否预占和由谁授权属于目标产品决策。
- p093 不证明提现应采用“最少账户”或“最低费用”，`XBD-004` 也不证明 FX 报价的确认与交割语义。

**已有压测**：`PT-027`。

## M05 结算产品规则完整性门禁

**来源候选**：`C09`。
**成熟度**：D2 方法草案。
**Owner**：结算产品 Owner。

### R 证据

[S1:p079-p084]；`S3-SETTLEMENT-001`、`STL-001`。

### I 方法骨架

结算产品不是一个“T+N”标签，而是结算方向、T 定义、时区/cutoff、周期、模式、去向、触发、费用、起结/最小金额、准备金和失败门禁的合同。

### A1 案例

- 商户结算：到户内部结转和到卡外部付款需要不同完成证据。
- 分销结算：业务应得、结算周期、计费/计税与付款需分层。

### A2 触发

- 设计、评审或验收商户、代理、分销或资金结算产品。
- 用户只给出“T+1”、“周结”或“自动结算”。
- 不用于查询既有契约的单一字段值。

### E 执行

1. 确认结算主体、方向、币种、模式与去向。
2. 定义 T、时区、cutoff、业务日/自然日、节假日和首个可结算时点。
3. 定义触发、费用扣减、起结金额、最小出款、准备金/垫资和失败门禁。
4. 定义到户和到卡的完成证据、账单与对账。判停：任一资金风险 Owner 规则缺失时，不产出最终结算契约。

### B 边界

- 不从“T+1”猜时区、工作日或到账承诺。
- 不默认平台垫资、负余额出款或准备金政策。
- 不以结算批次完成替代外部资金到账。

**已有压测**：`PT-001`、`PT-028`。

## M06 账本事实链、平衡、不可变与幂等过账

**来源候选**：`C10`。
**成熟度**：D2 方法草案。
**Owner**：账务/财务 Owner。

### R 证据

[S1:p103-p110]；`S3-LEDGER-001`、`ACC-005`。

### I 方法骨架

用“业务事实 -> 账本交易 -> posting plan -> 分录 -> 余额投影”检查记账完整性。计划必须平衡，已过账分录不覆盖，同一幂等语义不重复改变余额。

### A1 案例

- 课程账务：业务流水、凭证、账务明细与余额变化是相关但不同的事实。
- S3 账本：posting plan 平衡、分录不可变、重复 post 无重复资金影响。

### A2 触发

- 评审记账、冲正、冻结/解冻、余额投影或重复消息。
- 用户问“余额对了，是不是账就完整”。
- 不用于自动生成会计科目或借贷政策。

### E 执行

1. 确定唯一业务事实和幂等键，保留来源 Owner 与类型。
2. 根据已确认规则形成 posting plan，校验币种、借贷/方向与金额平衡。判停：不平衡或规则未确认时不过账。
3. 追加不可变分录，计算余额投影，保留 plan/分录/投影关联。
4. 重复请求返回既有过账事实；同键不同语义视为冲突，不重复改余额。

### B 边界

- 账户余额正确不能单独证明分录与核算完整。
- 错账通过冲正或更正事实修复，不覆盖原分录。
- 课程与 S3 不是目标项目会计政策。

**已有压测**：`PT-011`、`PT-034`、`PT-035`。

## M07 不可变对账结果、追加修复与重新证明

**来源候选**：`C11`。
**成熟度**：D2 方法草案。
**Owner**：对账/资金 Owner。

### R 证据

[S1:p120-p134]；`S3-RECON-001`、`REC-001`、`REC-005`。

### I 方法骨架

对账是在冻结范围、规则和两侧来源上生成不可变的匹配结果与差异。差错处理通过补事实、冲正、调账、挂账或核销追加证据，再用新对账运行重新证明，不改写旧结果。

### A1 案例

- 四段对账：平台账务、平台支付、渠道清算和渠道结算数据依次形成三组核对。
- 余额调节：双方单边账是未达事实，不删除记录制造一致。

### A2 触发

- 设计对账运行、匹配结果、差错、核销、调账或出款放行门禁。
- 用户问“差额已归零/手工已核销，能否直接关闭或放行”。
- 不用于不需要两侧或多侧事实核对的单系统数据校验。

### E 执行

1. 冻结对账项目、业务日、范围、规则版本和两侧来源。
2. 保留原始字段与加工主键，逐笔或按已确认规则匹配，生成不可变结果。
3. 将差错与处理动作分开；每个补单/冲正/核销保留 Owner、原因和证据。
4. 追加新事实后发起新对账运行；每个重大差异必须形成状态、原因、Owner、规则化处置和证据。判停：缺少这些证据时，不以“已处理”或差额归零替代对账完成；是否必须归零由目标项目规则决定。

### B 边界

- 不删除单边记录、不改写历史结果来达到差额归零。
- 自动核销必须有可审计原因与 Owner 批准规则。
- 5-7 段的课程标签不稳定，不强制用于生产命名。

**已有压测**：`PT-009`、`PT-010`、`PT-029`。

## M08 FX 金额换算的显式报价契约

**来源候选**：`C12`。
**成熟度**：D2 方法草案。
**Owner**：FX/资金 Owner。

### R 证据

[S1:p172-p173; p214-p217]；`S3-FX-001`、`XBD-004`。

### I 方法骨架

FX 金额不能只保留一个“汇率”。必须同时明确源/目标币种、价格类型或方向、报价快照、有效性、费用、舍入模式和结果金额；具体取值属于产品契约，不从单一项目默认值外推。

### A1 案例

- 课程换汇：报价、换汇和提现/付款是可关联但不同的对象。
- S3 FX：显式记录币种对、应用价格类型、快照和舍入，测试验证不同类型与结果。

### A2 触发

- 设计或评审 FX quote、conversion、跨境收付款或多币种账务。
- 用户只给一个 rate，或问“默认 `HALF_UP` 是否通用”。
- 不用于获取当前实时汇率；实时数据必须查外部权威源。

### E 执行

1. 确认源币种、目标币种、买卖方向与价格表达方式。
2. 确认报价号、价格类型、时间快照、有效期、点差/费用与交割语义。
3. 确认目标币种精度、舍入模式和最小单位，按显式等式计算。判停：方向、快照或舍入未定时不输出确定金额。
4. 保留输入、应用价格、舍入前后结果和产品契约版本。

### B 边界

- 不把 S3 的 `HALF_UP` 外推为行业或币种统一规则。
- 不用课程代替当前外汇、监管、报价或会计规则。
- 报价生成不等于换汇已交割或资金已到账。

**已有压测**：`PT-021`、`PT-024`。

## M09 通道协议解释与资金事实承接边界

**来源候选**：`C13`。
**成熟度**：D2 方法草案。
**Owner**：通道/资金架构 Owner。

### R 证据

[S1:p193-p222]；`S3-CHANNEL-001`、`CHN-004`。

### I 方法骨架

把银行、卡网络或钱包的协议、文件、回单、状态码和授权规则留在业务/通道适配层。适配层核验后生成内部资金事实、脱敏来源引用与对账证据，资金底座只对这些已解释事实执行账本和余额动作。

### A1 案例

- ACH：资金域不负责协议、文件、授权和 return 规则。
- VCC：资金域不负责发卡对象、issuer 协议、卡主状态、争议或 PCI 系统。

### A2 触发

- 设计通道适配层、资金底座输入或银行/卡网络状态映射。
- 用户问“资金域已有对应动作，是否可以跳过通道适配”。
- 不用于宣称通道已具备全生命周期生产能力；该结论仍为 D1/D2 混合。

### E 执行

1. 列出外部协议对象、文件/回单、状态、授权、逆向和安全规则。
2. 标记哪些字段必须由适配层验签、解析、去重和解释。
3. 定义内部资金事实：主体、金额/币种、动作、最终性、外部引用、规则版本和核验状态。
4. 资金底座只消费已核验事实，并保留账本与对账关联。判停：外部规则未核验或引用不足时，不自动处理。

### B 边界

- 不用本地资金契约代替正式银行、卡组织或通道规范。
- 不在资金底座保存不必要的敏感协议数据、PAN/CVV 或密钥。
- 不以局部 API 或资金动作证明完整通道生产能力。
