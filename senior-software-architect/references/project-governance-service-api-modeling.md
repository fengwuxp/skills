# 项目治理：服务、API 与模型

本文只承载服务职责、接口契约、模型边界和兼容性的架构建模与裁决，不复制 Java/Wind 方法命名、框架注解、模块放置或查询 API 细则。

## 使用时机

- 编码中新增或修改接口、方法，准备写回代码前。
- 需要评审服务职责、用例编排、事务边界、接口契约或模型泄露。
- 需要判断某个接口、模型或服务拆分是否有真实业务责任。

- 纯 Java/Wind 约规检查交给 `wind-coding-conventions`。

## 能力价值与架构裁决

设计、编码、代码 CR 和架构审查共用本节，将 `../SKILL.md` 的核心原则落到能力价值、责任归属、可信契约、复杂性封装和结果证据。公共 API、模块服务和内部方法均适用，不要求用户额外提出“从提供者视角分析”。先依据模块定性、对象/资源语义、架构分层和稳定职责识别问题类别，再用源码、代表性需求与验证检验；不能以“调用方要求加方法”“已有设计通过”或“测试全绿”代替价值判断。

### 能力提供者定性

**能力**是模块针对一类问题，在其职责与适用条件内提供的稳定操作、组合方式及可观察保证。**能力提供者**是从实现者视角，依照模块定性、面向对象封装和架构分层，组织相关行为、状态或资源协作以解决这类问题的承责单元。它可以是函数、对象、模块、适配器或服务；维护与风险责任仍由人或组织承担。提供者不必拥有全部相关数据或独占物理资源，无状态计算也不需要为成立能力而增加对象与生命周期。

提供者设计的起点是“这个模块是什么、应当解决哪类问题”，具体需求是该问题类别的实例。能力应覆盖已定范围内的主要变体，并对所有符合其契约的使用兑现保证；变化的需求优先通过参数、既有操作组合或上层编排解决。需求暴露类别内缺口时补足能力，超出模块定性时重新划界；既不因当前未调用而删去职责内必要操作，也不以“覆盖所有需求”为由无限扩大问题域。本轮实施仍服从授权范围，不把识别到的能力空间一次性全部实现。

| 概念 | 定性边界 |
| --- | --- |
| 消费者与能力 | 消费者组合能力完成具体任务；提供者依据问题类别形成稳定契约。使用者可以是已接入调用方，也可以是由模块定位确定的适用角色；后者须标明尚未接入，不冒充真实采用。 |
| 接口与提供者 | 接口表达双方可依赖的协议，提供者兑现它；相同名称、签名或统一入口不足以证明行为等价。 |
| 资源与访问引用 | 数据、会话、连接、文件等是被使用或管理的对象；名称/句柄用于定位或引用。资源身份、每次使用的状态、共享范围和关闭责任须按实际契约区分，不能由标识相同推出状态独立或权限相同。 |
| 能力与授权 | 能实现某操作、持有对象标识或拿到工具，不自动获得执行权限；按现有授权模型判断谁可在何时操作什么。Linux 的 capabilities 是特权拆分机制，不等于这里的软件能力。 |

定性时同时保留两面：向消费者给出足够稳定、完整的承诺，向实现保留兑现承诺所需的控制与变化空间。**名实相称**用于核对名称与结果，**察同辨异**用于划定共享协议与真实差异，**知止有度**用于收缩无依据的承诺；这是工程判断镜片，不替代源码、契约、验证或授权，也不产生新检查卡。

### 判断与执行

- **设计**：先定模块性质、问题类别、所属层次与责任边界，提炼共同语义、不变量和必要操作，再选择最小实现结构；用代表性需求检验覆盖与组合，不按每个需求新建一套接口和类。
- **编码**：新增或修改接口、方法时，在首次写入该变更前完成分析，不能等代码写完后只补一次 CR。快速编码可以缩短说明，但不跳过判断。
- **写回门槛**：涉及接口、公开方法、跨边界模型或跨模块重构时，写回前应有可回读的最小变更记录：实际调用方或有模块定位依据的适用使用者、责任 Owner、稳定职责、不变量、兼容语义、写入范围和验证引用。它可以放在现有任务 / 评审载体中，不要求新增规划文档；缺少职责、适用范围或验证依据时保持 `candidate` / `pending`。尚无消费者接入不阻止职责明确且获授权的提供者实现，但不能声称已被消费者采用。
- **代码 CR**：在已约定的 diff 或源码范围内，重新核对现有及变更后的能力是否值得提供、职责是否合适、契约是否解决真实问题；写前结论只作输入，不能代替审查。
- **架构审查**：先核对模块定性、问题类别与分层职责，再用代表性场景和边界反例检查操作组合、覆盖与协作；方案尚无实现时，以职责依据和可验证契约判断，不虚构调用方或把未实现本身判为无价值。

分析回答以下问题，详细契约检查复用下文，不另造一套清单：

1. **问题类别与能力价值**：模块是什么，负责哪类对象、规则或机制，适用范围与非目标是什么？该定位可以从已有架构、对象/资源语义或已确认边界获得，不要求新增定位文档。必要能力由稳定职责和不变量推导，不以当前调用清单为全集；具体需求用于检验，不先按调用链生成服务再用新调用点自证价值。
2. **职责与架构**：先确认结果责任、数据所有权、不变量、事务与失败恢复边界，再决定模块、对象和层次。按下文“业务语义与软件结构”和“服务职责裁决”核对高内聚、低耦合、依赖方向和信息隐藏，选择必要的最小可见性，避免职责错层、重复规则或泄露实现细节。
3. **复用与成本**：已有接口、方法、标准库或组合是否能解决问题？既有基础服务或应用服务能在自身责任、数据和事务边界内承接时，优先复用、增强或合并重复职责。新方法是否封装了稳定职责、复杂度或明确语义，收益能否覆盖调用、实现、测试、运维和兼容成本？单实现、短方法、调用点或接口数量均不直接决定抽象价值，也不为想象中的复用扩成通用接口。简化须保持必要的不变量、权限、事务、幂等与失败恢复，不以更少代码或层次取代正确性。
4. **契约与边界**：按下文“契约与模型裁决”说明调用者可以依赖的行为；涉及状态、副作用或跨边界调用时，落实失败、恢复与兼容责任。不能让调用方拼装提供者内部步骤才能完成本应由提供者承责的结果。
5. **验证与取舍**：用问题类别的代表性变体、不变量、边界及失败场景检验能力覆盖，再用真实消费者检验采用与组合；新需求仍在类别内时，哪些可由既有操作直接表达，哪些暴露职责内缺口？据此选择保留、复用、组合、增强、新建、收缩或不提供。有限样例不能证明任意未来需求，提供者验证也不等于消费者已采用；本轮验收满足且无新的范围内缺陷时收口。

同一稳定职责的一组方法可以合并分析。编码中沿用已确认设计时，只核对本轮变化及影响，不按每次文件保存重做评审；进入 CR 或架构审查仍须基于当前证据独立判断。简单任务用一两句给出问题、归属、取舍和验证即可；行为保持的内部整理也要说明其语义或复杂度收益。不默认新增设计文档、独立评审者或用户确认环节。

提取共享能力时，用实际调用者对照业务含义、前置条件、结果、权限、副作用和一致性要求；相似步骤或字段不能证明同一职责。若合并后调用方需要辨别内部模式、补做约束或传入一组开关恢复原行为，应重评边界，必要时只共享稳定算法、保留各自用例。调用者确需选择且语义清楚的业务策略可以公开，不把所有参数差异都当作泄露；也不以“两处重复”强制抽取，或以单一调用者否定承责能力。

审查发现必须连接具体接口或方法、事实证据、真实后果与最小建议；没有写前分析记录、单实现、只有一个调用点、方法很短、接口数量或缺少原则名称，均不能单独成为缺陷或阻塞理由。有调用不等于值得独立抽象，无当前调用也不等于能力无价值；模块定性推导出的必要操作、已确认用例、稳定公共契约、外部消费者与兼容承诺都属于依据。证据不足时标明缺口，不编造业务价值，也不把完整调用范围尚未查清写成“无人使用”。只读审查不自动修改、删除或扩大扫描范围；判定可接受时，简述保留依据，不为展示检查而制造 finding。

缺少模块定性、问题类别或职责依据时，不凭需求联想新增能力；先复用已成立的路径或补齐依据。未决的业务、安全、兼容或架构取舍继续按既有项目授权规则处理，不借分析扩大本轮写入范围。

### 业务语义与软件结构

系统设计围绕目标选择必要抽象，把业务事实、责任、关系、状态和约束映射为可执行、可验证、可演化的软件结构。新增或调整接口、方法、模型时，核对它承接的事实或结果责任、必须共同成立的不变量，以及真正会一起变化的规则；现有消费者、源码与用例已经说明这些关系时直接复用，不另建映射卡。

- 业务对象、部门、页面和流程步骤不与表、类、服务或 Agent 一一对应。拆合依据是职责、生命周期、一致性边界和已知变化轴；同一现实对象可有不同责任视图，不同角色也可共享同一承责能力。现行组织或流程存在问题时先区分现状与已确认目标，不将其机械固化，也不擅自改变业务责任。
- 合并字段或模型前确认是否同一事实、同一适用时点与同一权威；当前值、历史承诺与派生结果不因值相等而合并。语义歧义回产品权威核对；已确认语义直接落实到更新边界、版本、一致性和兼容行为，不能由表形或类名反推业务含义。
- 用已确认的变化场景检查结构：某条规则或状态改变时应影响哪些责任、哪些历史事实必须保持、调用者依赖的结果是否仍成立。实现与测试反例用于校正设计；不把图形相似、形式规范化、代码生成速度或模型自述当成设计质量证明。

## 服务职责裁决

服务和接口是否成立，先看它是否承担至少一项真实责任：用例编排、业务规则、事务或一致性边界、权限审计、状态迁移、跨资源协调、外部适配或稳定公共契约。

评审时回答：

1. 该职责由哪个业务用例或不变量驱动，谁对结果负责。
2. 调用链中谁拥有事务、失败恢复和外部副作用。
3. 新增层次是否隐藏复杂度，还是只改名转发并增加跳转。
4. 读写职责、状态变化和数据所有权是否清楚。
5. 依赖方向是否让核心规则脱离外层实现独立验证。

检查结果责任是否完整时，沿一次真实调用确认：调用者表达意图后，提供者能否在自身权限、数据与事务边界内保护该结果。完整性以本层承诺为准：允许部分进展的原语应准确返回进度，承诺完整结果的上层能力才负责组合和收口；受理、可读取、完成与持久化不能混同。仅把 `check`、`update`、`record` 包进一个方法，并不能证明并发下不变量成立；检查与写入须由实际事务、条件更新或约束保护。跨能力的用例编排留给用例责任方，不为“完整承责”扩大基础服务的数据所有权或假定外部副作用可原子回滚。

保留、合并或删除按责任裁决：

- **合并重复职责**：已有服务能在同一责任、数据和事务边界内完成结果时，将重复能力收回该服务并调整调用方。不能为满足分层新增 `AggregateService`、`Loader`、新包或一行转发，再以“已被调用”作为保留依据；包装包含多步代码也不自动证明它拥有独立职责。
- **保留独立边界**：稳定解析、不变量保护、外部适配或公共契约确有独立责任时，可以保留最小内部组件或接口；一个实现、一个调用方或短方法均不否定该价值。多个用例共享组件时，核对是否共享同一语义与一致性要求，不按调用方或应用服务数量机械拆分，也不把不同的数据、事务和失败边界强行合并。
- **区分合并与删除**：合并的是重复承载，职责内必要能力与有效契约必须保留。只有核对模块定性、问题类别、当前用途、已确认需求、公共契约、外部消费及兼容义务后，确认该能力既非职责内必要组成，也无有效用途，才在授权范围内删除。只有测试引用不能证明生产采用，也不能单独证明无价值；尚未接入的基础能力按其职责与契约验证，不借此保留无问题域依据的扩展。
- **验证结果与边界**：合并前后验证调用者可观察结果、状态与持久化事实、事务原子性、锁或版本约束、失败恢复和兼容语义；不能只统计调用点、接口数量或类文件减少量，也不能为通过测试把原职责换名留在新包中。

## 契约与模型裁决

接口契约必须让调用方能够判断输入、输出、前置条件及适用的失败、权限、幂等、分页、一致性、副作用、兼容和版本语义；不适用的项目不机械添加。稳定指承诺可信、变化可预期，不等于签名永远不变。模型是否可以跨边界，不按类型名机械判断，而按业务所有权、稳定性、序列化契约和持久化耦合判断。

重点检查：

- 对外契约是否泄露数据库、ORM、消息中间件或第三方 SDK 的实现细节。
- 同一业务概念是否在接口、模型、状态和错误中保持一致命名。
- 破坏性变化是否有兼容窗口、迁移路径、调用方清单和退役条件。
- 转换、默认值、空值和错误映射是否改变业务语义。
- 签名未变时，结果口径、时间窗口、排序、默认策略、错误和可见性保证是否仍兼容；不能用编译通过代替契约验证。
- 接口是否有契约测试、集成验证或可复核样例。

### 完整使用过程与跨域协作

接口组合须让真实消费者完成已确认任务。只展开当前出现的批量、分页或异步流程：

- 批量结果用稳定项身份关联输入与结果，说明整体原子还是逐项生效、哪些可重试、哪些待核对；恢复遵循原身份及幂等作用域，不因响应顺序变化错配结果，不把部分成功或结果未知整批重做。
- 连续分页核对排序、游标/偏移和数据变化下的可见性承诺；异步受理核对任务身份、状态查询、终态结果与失败后的合法动作。按业务需要选择一致性与恢复方式，不为普通列表强制快照或游标，也不为同步接口增加任务平台。
- 跨域协作明确事实提供方、消费方所需视图、转换责任与共同维护的契约。已有语义一致的类型可以共享；只有单位、状态、时点、生命周期或发布责任有真实差异时才转换，不按每个调用方复制模型。
- 转换验证实际业务含义：金额/数量单位、时间基准、状态含义、空值和未知信息是否保真；当前值不能覆盖已确认的历史承诺，未知不能默认为合法零值或明确否定。协议改名可封装在承责适配处，语义变化则先核对契约与兼容；不替业务补转换规则。

验证从输入、调用、结果识别走到下一合法动作，保留内部真实实现，仅在不可控外部边界用替身；接口格式正确或字段一一对应不证明使用过程正确，替身通过也不证明供应商已接受。

### 模型约束与校验责任

新增或调整模型、解析入口与校验代码时，先按已确认契约分清合法值、合法状态组合及变化责任，再选择现有类型、构造入口或状态转换能承载的最小表达。例如合同只允许“成功且有结果”或“失败且有原因”，模型就不应任意组合成功标志、空结果和错误；但业务允许的处理中、未知或部分结果不能为简化类型被删掉。

- **按信任边界复用稳定约束**：不可信外部输入在入口完成必要的运行时解析与校验，不能仅凭类型标注、强制转换或忽略编译错误认定已验证。受信任内部可依赖具体语言的类型系统及项目已采用的静态契约，不为重复证明既有保证增加构造器或逐层校验。若可变字段、反序列化、独立入口等实际路径会破坏该保证，再在承责边界检查；具体语言规则沿用对应约规，不把静态契约与运行时校验混同。
- **变化中的事实由承责处判断**：格式与构造合法不代表当前权限、余额、库存、版本或状态仍有效。这些条件在执行或更新边界按现有事务与并发契约核对，不把早先的校验结果当成永久许可，也不让每层重复承担同一责任。
- **表达收益决定模型成本**：优先调整已有模型或构造方式；确能减少矛盾状态、重复分支或调用者误用时，再引入局部类型。现有表示已清楚可靠就保留，不为每个原始值造包装类、接口、工厂或新框架；公开表示变更仍遵守兼容契约。

验证合法输入、非法组合和实际状态变化后的外显结果；校验前移涉及 Java/Spring 分层防御测试时，复用 `testing-practices-java-spring-common.md` 的“校验边界前移后的分层防御”，不为构造非法测试数据给生产模型新增旁路。

### 契约与实现对齐

- **名称表达可依赖的承诺**：结合适用上下文核对名称、返回值和实际效果，尤其区分已受理、处理中、已完成，及查询与有副作用的动作。命名困难时先辨概念与职责，不靠泛化名称掩盖歧义，也不直接推导出应拆服务。名称误导必须回到调用者误判或契约风险；已发布名称的调整遵守兼容边界，不为字面统一批量改名。
- **能力承诺先于类型形式**：调用方依赖稳定行为，实现选择类、函数、模块或接口类型。真实隔离、公共兼容或替换责任可以支持单实现接口；纯函数或内部类已有清晰契约时不强加接口、工厂和注册器。可替换实现不得收紧原合法输入/前提、削弱结果/失败保证或破坏状态约束；符合原契约的差异可以保留，不要求内部算法或所有返回值完全相同。
- **统一协议保留适用范围**：只统一确有共同语义的操作；资源支持范围、可选操作与失败边界应由契约说明。协议已允许明确的不支持结果时可保留；若调用者依赖必需行为，实现不能临时返回空值、伪成功或“不支持”冒充可替换。按实际消费者选择小接口、适配或既有能力声明，不默认新增注册器、探测框架、任意动作入口或庞大继承树。
- **责任落到实现所有者**：由拥有状态与不变量的对象或模块维护合法变化，应用层组合既有能力完成用例；无状态计算可保留纯函数，不为面向对象堆叠实体或继承层次。编排者只消费某项能力时采用组合委托，不为转发或代码复用强行实现该能力接口或继承其实现。
- **资源使用范围可见**：涉及有状态资源时，明确创建/取得、共享/借用、有效期、并发访问及释放责任；借用不自动转移关闭权，释放一个引用不等于资源已销毁或在途动作已取消。只展开当前确有的生命周期，不给无状态函数增加会话对象；已确认约束由承责对象及操作边界保护，不要求调用者修改内部字段维持不变量。
- **隐藏机制、保留业务可见性**：存储布局、协议适配、执行顺序、路由算法和缓存键由提供者封装；时效、一致性、部分成功和失败状态按调用者决策需要公开。不能把超时、未完成或无数据统一伪装成正常零值，也不能要求调用者理解物理表或内部中间状态才会使用公共能力。
- **用变化检验封装**：先指出调用者具体不再需要知道的表示、步骤或机制，再对本轮已确认的存储、协议或算法变化，检查哪些调用方必须修改、哪些承诺须重新验证。语义保持时将改动集中在责任边界内；语义改变时显式处理兼容和迁移。新增名称、参数、配置与调用顺序仍让调用者承担原有内部细节时，不能只凭包装层称为抽象；但调用者确需选择的业务策略和可观察状态仍应公开。对外接口简单不豁免内部可维护性，不把多个无关责任塞进统一入口，也不为证明可替换性虚构第二种实现。

以指标查询为例：调用方表达指标、维度、时间与必要的版本语义，提供者承接查询结果；DSL 编译、物理绑定和查询执行可以封装在内部。契约按实际需要区分无数据、零值、失败与未完整结果；调用方不负责拼接“定位物理表、选路由、查快照、决定回退”的内部流程。此例用于判断责任和语义，不规定各项目必须采用的字段、类名或实现技术。

### HTTP API / RESTful 契约裁决

面向 Web 的资源 API 默认先按 RESTful 语义设计，再处理项目兼容约束。这里的“优先”是审查顺序，不是为形式重命名或破坏已有消费者；现有协议已经稳定时，先保留兼容语义，并记录为何不能迁移。

- URI 表达资源和层级关系，优先使用名词、集合与资源标识；普通 GET 查询的过滤、分页、排序和时间范围使用 query 参数。敏感筛选条件不放进 URI；复杂查询受真实协议或长度限制时，可依据契约采用 POST 请求体，说明查询语义、缓存和重试边界，不仅因“实现方便”切换方法。业务动作路径须有真实职责，并说明前置条件、幂等、权限和失败恢复。
- HTTP 方法必须与意图相符：`GET` 只读资源，`POST` 按资源语义处理请求体，可用于创建、命令或有依据的查询，`PUT` 全量替换且幂等，`PATCH` 局部修改，`DELETE` 删除。不能把所有读写都包装成 `POST`，也不能把所有 POST 都认定为业务写操作或天然不可去重；既有例外若需迁移，写清兼容窗口与退役条件，有正当理由的查询契约不强制退役。
- HTTP 状态码表达协议结果：成功、客户端输入 / 权限 / 资源不存在、状态冲突、前置条件失败和服务端 / 上游失败要能区分；业务错误码可以补充领域语义，不能用统一 `200` 把失败伪装成成功。
- 写操作明确幂等键或等价去重、并发 / 前置条件（例如版本或 ETag）、超时后的未知状态、重试和人工接管。方法名“看起来幂等”不能代替服务端实际保证。
- 对外表示使用稳定的资源 / DTO 视图，不暴露 ORM、数据库、内部 DSL、物理绑定或执行步骤。响应的分页游标、排序稳定性、空结果、部分结果、版本和可见性必须能被调用方判断。
- 业务数据定义、派生交付和原型对齐属于不同责任：业务定义负责稳定语义与 Owner；若存在预计算、快照或异步交付，由承责方说明输入、状态、刷新与失败边界；HTTP API 表达已定资源能力及结果保证；原型标注引用同一业务标识和 revision，不反向发明接口或数据口径。既有路径按源码与兼容契约核对；新增路径依据模块/资源定性、适用使用者及实施授权确定，无需等待具体业务接入。

审查结果至少记录：资源 / 动作语义、方法与状态码、幂等和并发边界、兼容例外、模型暴露边界、实际调用方或有定位依据的适用使用者，以及对应验证证据。职责、契约或必要授权未定时保持 `candidate` / `pending`；尚未接入只限制采用声明，不阻止已授权的提供者实现与验证，不以“符合 RESTful”或接口数量作为完成证明。

## 规则结果消费

项目本地规范和 `wind-coding-conventions` 输出的规则结论只作为输入。架构师不复制规则正文，只做三项裁决：

1. 规则是否适用于当前技术栈和上下文证据。
2. 偏差是否破坏业务不变量、边界、兼容、可测试性或生产恢复能力。
3. 修复应落在当前源码、项目约规还是规则 Skill，并由谁验证。

规则与项目事实冲突时，不静默选边；记录冲突、风险、owner 和裁决依据，必要时进入 ADR 或项目约规修订。

## 评审清单

- 本轮编码是否在写回前完成分析，CR 或架构审查是否基于当前证据重新裁决能力价值与架构合理性。
- 服务和接口是否有真实职责，而非透传包装。
- 既有服务能承接的重复职责是否已收敛，保留或删除是否依据需求用途与责任边界，而非调用、实现或接口数量。
- 数据、事务、权限、状态和失败责任是否归属清楚。
- 对外契约是否稳定、可判定、可兼容、可验证。
- 模型是否泄露外层实现或制造跨模块耦合。
- 规则偏差是否已映射到源码风险、最小修复和验证证据。
