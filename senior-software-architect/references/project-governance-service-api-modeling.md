# 项目治理：服务、API 与模型

本文只承载服务职责、接口契约、模型边界和兼容性的架构建模与裁决，不复制 Java/Wind 方法命名、框架注解、模块放置或查询 API 细则。

## 使用时机

- 编码中新增或修改接口、方法，准备写回代码前。
- 需要评审服务职责、用例编排、事务边界、接口契约或模型泄露。
- 需要判断某个接口、模型或服务拆分是否有真实业务责任。

## 不适用场景

- 纯 Java/Wind 约规检查交给 `wind-coding-conventions`。
- 单文件语言或框架用法先读项目本地规范与规则 Skill。

## 读取后必须产出

- 编码、代码 CR 和架构审查均给出能力价值、职责归属、取舍及验证依据的简短结论；审查结论按实际风险定级，简单任务不另建文档。
- 服务职责、接口契约、模型边界、兼容性风险、源码锚点和验证建议。

## 需要继续读取的 reference

- 代码 Review 定级读 `coding-review-deep-dive.md`。
- 数据与安全边界读 `project-governance-data-security-quality.md`。

## 能力价值与架构裁决

编码、代码 CR 和架构审查共用本节；公共 API、模块服务和内部方法均适用，不要求用户额外提出“从提供者视角分析”。以当前需求、源码、实际调用方和测试为依据，不能以“调用方要求加方法”“已有设计通过”或“测试全绿”代替价值判断。

- **编码**：新增或修改接口、方法时，在首次写入该变更前完成分析，不能等代码写完后只补一次 CR。快速编码可以缩短说明，但不跳过判断。
- **代码 CR**：在已约定的 diff 或源码范围内，重新核对现有及变更后的能力是否值得提供、职责是否合适、契约是否解决真实问题；写前结论只作输入，不能代替审查。
- **架构审查**：沿已确认用例核对能力、模块、接口与方法的职责分配及协作；方案尚无实现时，用明确的消费者、调用场景和验收条件判断，不虚构源码或把未实现本身判为无价值。

分析回答以下问题，详细契约检查复用下文，不另造一套清单：

1. **实际问题与价值**：谁使用这项能力，解决哪个真实问题或已有证据支持的一类问题，产生什么可观察结果？没有它时现有方案的具体缺口是什么？消费者可以是外部调用方，也可以是当前模块内的调用者；拟新增调用应能回指已确认用例，不能虚构消费者。
2. **职责与架构**：能力应归属哪个模块、对象或层次，持有哪些不变量？按下文“服务职责裁决”核对高内聚、低耦合、依赖方向和信息隐藏，选择必要的最小可见性，避免职责错层、重复规则或泄露实现细节。
3. **复用与成本**：已有接口、方法、标准库或组合是否能解决问题？新方法是否封装了稳定职责、复杂度或明确语义，收益能否覆盖调用、认知、维护和兼容成本？单一调用点或短方法不自动判为无价值，也不为想象中的复用扩成通用接口。
4. **契约与边界**：按下文“契约与模型裁决”说明调用者可以依赖的行为；涉及状态、副作用或跨边界调用时，落实失败、恢复与兼容责任。不能让调用方拼装提供者内部步骤才能完成本应由提供者承责的结果。
5. **验证与取舍**：用哪个真实用例、边界或失败场景检验能力价值和契约？据此选择保留、复用、组合、增强、新建、收缩或不提供，并说明依据；写回前明确验证方式，写回后及审查时区分已有证据、待验证判断和真实结果。

同一稳定职责的一组方法可以合并分析。编码中沿用已确认设计时，只核对本轮变化及影响，不按每次文件保存重做评审；进入 CR 或架构审查仍须基于当前证据独立判断。简单任务用一两句给出问题、归属、取舍和验证即可；行为保持的内部整理也要说明其语义或复杂度收益。不默认新增设计文档、独立评审者或用户确认环节。

审查发现必须连接具体接口或方法、事实证据、真实后果与最小建议；没有写前分析记录、只有一个调用点、方法很短或缺少原则名称，均不能单独成为缺陷或阻塞理由。证据不足时标明缺口，不编造业务价值，也不把完整调用范围尚未查清写成“无人使用”。只读审查不自动修改、删除或扩大扫描范围；判定可接受时，简述保留依据，不为展示检查而制造 finding。

缺少真实问题或职责依据时，不新增能力；先复用已成立的路径或补齐事实。未决的业务、安全、兼容或架构取舍继续按既有项目授权规则处理，不借分析扩大本轮写入范围。

## 服务职责裁决

服务和接口是否成立，先看它是否承担至少一项真实责任：用例编排、业务规则、事务或一致性边界、权限审计、状态迁移、跨资源协调、外部适配或稳定公共契约。

评审时回答：

1. 该职责由哪个业务用例或不变量驱动，谁对结果负责。
2. 调用链中谁拥有事务、失败恢复和外部副作用。
3. 新增层次是否隐藏复杂度，还是只改名转发并增加跳转。
4. 读写职责、状态变化和数据所有权是否清楚。
5. 依赖方向是否让核心规则脱离外层实现独立验证。

## 契约与模型裁决

接口契约必须让调用方能够判断输入、输出、失败、权限、幂等、分页、兼容和版本语义。模型是否可以跨边界，不按类型名机械判断，而按业务所有权、稳定性、序列化契约和持久化耦合判断。

重点检查：

- 对外契约是否泄露数据库、ORM、消息中间件或第三方 SDK 的实现细节。
- 同一业务概念是否在接口、模型、状态和错误中保持一致命名。
- 破坏性变化是否有兼容窗口、迁移路径、调用方清单和退役条件。
- 转换、默认值、空值和错误映射是否改变业务语义。
- 接口是否有契约测试、集成验证或可复核样例。

## 规则结果消费

项目本地规范和 `wind-coding-conventions` 输出的规则结论只作为输入。架构师不复制规则正文，只做三项裁决：

1. 规则是否适用于当前技术栈和上下文证据。
2. 偏差是否破坏业务不变量、边界、兼容、可测试性或生产恢复能力。
3. 修复应落在当前源码、项目约规还是规则 Skill，并由谁验证。

规则与项目事实冲突时，不静默选边；记录冲突、风险、owner 和裁决依据，必要时进入 ADR 或项目约规修订。

## 评审清单

- 本轮编码是否在写回前完成分析，CR 或架构审查是否基于当前证据重新裁决能力价值与架构合理性。
- 服务和接口是否有真实职责，而非透传包装。
- 数据、事务、权限、状态和失败责任是否归属清楚。
- 对外契约是否稳定、可判定、可兼容、可验证。
- 模型是否泄露外层实现或制造跨模块耦合。
- 规则偏差是否已映射到源码风险、最小修复和验证证据。
