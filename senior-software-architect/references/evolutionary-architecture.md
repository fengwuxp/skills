# 演进式架构与遗留系统改造
本文用于遗留系统治理、模块化改造、服务拆分、技术栈升级、核心链路替换、数据迁移和平台能力沉淀。目标是小步、可验证、可回滚地改善系统体质，而不是一次性推翻重来。
## 使用时机
- 遗留系统难以维护、难以测试、边界不清、公共模块膨胀或上线风险高。
- 需要从单体演进到模块化单体、从模块化单体演进到微服务，或反向收敛过度拆分。
- 需要替换核心依赖、SDK、中间件、数据库、搜索、缓存、网关或认证体系。
- 需要迁移历史数据、历史接口、历史客户端或跨团队契约。
- 需要评审系统是否已经长期只加不减、不敢删除、局部性丧失、出现承重行为、废弃 API 堆积、概念膨胀或治理规则失效。

## 改造原则
- **先止血再手术**：先加测试、监控、边界和发布保护，再做结构性迁移。
- **小步可逆**：每一步都能独立发布、验证、暂停和回滚。
- **契约先行**：先固定外部行为、接口、消息、数据口径和验收场景。
- **防腐隔离**：新模型不要直接继承旧系统坏味道，用 Anti-Corruption Layer 隔离旧接口和旧数据。
- **业务连续性优先**：迁移期间保证用户体验、数据一致、客服可解释和运营可处理。
- **先排熵再扩建**：新增能力前先看是否能删除、归档、收敛概念、下线旧路径或恢复失效的治理守卫；只会新增兼容层的改造会继续放大腐朽。
## 常用策略
| 策略 | 适用场景 | 关键动作 |
| --- | --- | --- |
| 契约测试 | 外部行为不能破坏 | 固定 API、消息、错误码、字段语义和兼容性。 |
| 防腐层 | 新旧模型差异大 | 旧接口适配为新领域语言，隔离旧枚举、状态和异常。 |
| 绞杀者模式 | 逐步替换大单体能力 | 按业务能力切路由，旧链路逐步收缩，新链路灰度扩大。 |
| 双写 | 新旧数据并行过渡 | 明确主写方、失败处理、幂等、对账和回滚策略。 |
| 回填 | 历史数据迁移 | dry-run、分批、校验、差异修复和审计。 |
| 读切换 | 新读模型验证成熟 | 影子读、结果比对、灰度读、异常自动回退。 |
| 模块化单体 | 边界未成熟或团队运维不足 | 先用模块边界、依赖规则和架构测试治理。 |
## 迁移设计顺序
1. **现状建模**：当前能力、数据、接口、依赖、痛点、事故、维护成本和不可动边界。
2. **目标边界**：目标模块/服务边界、数据归属、接口契约、权限和运行形态。
3. **兼容策略**：历史客户端、老接口、老数据、配置、消息、报表和运营工具如何共存。
4. **迁移路径**：防腐、双写、回填、影子读、灰度切流、停止旧写、下线旧读。
5. **验证与回滚**：契约测试、数据校验、对账、监控、开关、回滚和前滚修复。

## 废弃与迁移责任

先声明废弃是建议性还是强制性。建议性废弃只提供更优替代，不伪造截止日期或强制消费者迁移；强制性废弃会终止兼容，必须由公共契约 Owner 批准，并由提供方承担消费者识别、兼容窗口、迁移说明 / 工具、问题响应和退出证据，不能把迁移成本单方面转给消费者。

废弃契约至少包含：旧能力与替代能力、提供方 Owner、已知消费者、建议 / 强制类型、兼容窗口、通知渠道、代码 / 数据迁移路径、使用遥测覆盖、例外、暂停 / 回退条件、移除验收和最终批准人。消费者完成迁移后独立验证自身契约；提供方负责汇总跨消费者证据。

移除前必须证明观察窗口和遥测覆盖足以代表所有已知入口，并取得零活跃使用证据、契约测试、生产观测和消费者确认。没有日志不等于没有使用；无法覆盖离线客户端、批任务、外部集成或长周期调用时，继续兼容、补证据或显式接受残余风险，不得静默删除。
## 微服务拆分门槛
只有同时满足以下条件，才建议拆服务：
- 业务边界稳定，领域语言清楚，数据归属明确。
- 调用关系、事务边界、失败路径和一致性方案清楚。
- 团队具备独立发布、监控、告警、容量、值班和故障处理能力。
- 拆分后收益大于网络、运维、数据一致性、测试和协作成本。
- 有灰度、回滚、兼容和迁移方案，不是一次性大爆炸。
不满足时优先模块化单体、包边界治理、依赖规则、领域服务提取和架构测试。
## 遗留系统评审清单
- 是否先定义目标和非目标，避免“顺手重构整个系统”。
- 是否有旧行为的契约测试、回归用例或可比对样本。
- 是否识别公共模块垃圾桶、循环依赖、框架绑架、贫血分层和隐式业务规则。
- 是否有防腐层隔离旧模型，而不是让新代码继续传播旧坏味道。
- 数据迁移是否有 dry-run、分批、备份、校验、对账、审计和回滚。
- 切流是否有开关、灰度比例、监控指标、暂停条件和回退路径。
- 是否定义旧能力下线标准和清理计划，避免新旧两套长期并存。
## 架构腐朽与排熵评审
当系统的删除风险长期高于保留成本时，优先做排熵评审，而不是继续叠加新抽象。排熵评审的目标是恢复可删除性、局部推理能力和治理规则可信度。
Architecture Entropy Review 字段：评审目标/非目标、可删除性下降、局部推理边界丢失、承重行为、废弃路径堆积、废弃 API / dead path、概念膨胀、事实源分裂、治理自腐、守卫自检、最小正确实现 / 过度设计候选、可执行约束 / 可追溯理由链、时间边界三问、棘轮基线、熵增仪表、理由保鲜、非对称稳定性、下线候选、真实契约、最小排熵计划、验证命令、契约测试、灰度/回滚、owner、停止条件。
架构规则要同时有执行点和理由链：CI、测试、静态检查、类型/数据模型、脚本、监控或 CR 清单负责持续执行；ADR、事故复盘、业务不变量、源码锚点、运行指标、合规要求或 owner 确认负责解释为什么存在。理由死链、owner 缺失或守卫长期失效是维护缺口，不证明原约束已经失效；旧报告或未经核实的规则解释不再直接作为架构否决依据，但仍有效的约束继续保护。按下文“门禁的维护、例外与退役”回读当前契约、补责任承接并校验替代证据；无法核定时只暂停依赖该判断的准出，不静默撤销保护。
时间边界三问必须覆盖涉及外部副作用、异步、重试、回调、支付/资金、批任务和状态机的改造：重启之后系统还记得什么？重放之时如何避免重复副作用？状态不明时如何继续、补偿、隔离或人工接管？如果没有持久化意图、完成事实、幂等键、业务唯一约束或状态机证据，不得把方案判为可靠。排熵机制要形成棘轮：复杂度基线只能收敛不能随意反弹；熵增仪表持续暴露 dead path、废弃 API、无主适配、重复概念、跳过检查和治理规则失效；理由保鲜要求规则、适配层和兼容分支定期复审；非对称稳定性要求新增概念自带退场方式，删除和下线必须经过更高证据门槛。
最小排熵计划先给无主规则、无主适配层、无主脚本和废弃 API 标 owner、保留原因、使用证据和复审日期；再补契约测试、调用统计、日志锚点或只读扫描，证明旧行为是否仍被依赖；随后收敛命名和事实源，低风险清理 dead path、文档误导、失效检查和重复配置。Ponytail-style 过度设计检查只能提出可删除复杂度候选，例如单实现抽象、无主配置、重复造轮子和无真实变化轴的扩展点；生产路径删除、公共契约变更、数据迁移、核心依赖替换和旧能力下线须核对影响、有效授权、验证与恢复边界。正式 ADR 按 `adr-and-tradeoff.md` 的准入条件决定，灰度按实际部署风险选择；只有存在新的 Owner 决策或必要授权缺口时交还确认，不因变更类别重复审批已授权动作；规则失效时先修守卫，不用失效守卫作为架构否决依据。

## 架构治理的持续验证

治理对象是持续影响变化成本、质量与风险的决策和约束，不是组件数量、代码行数或架构师头衔。先从真实变更、事故或反复协调中定位代价与结构原因，在当前授权范围内选择最小修复；没有结构问题证据时，不以提效为由启动平台化、拆服务或全面重写。

### 关键决策与跨层假设

对本次触及的关键决策，在已有 ADR、系分、规则或代码旁核对适用范围、责任方、成立前提、保护的结果、执行点与复审信号；正式 ADR 的准入与替代仍按 `adr-and-tradeoff.md`，不另建通用卡片。难改说明后果和迁移成本显著，不证明决策永远正确或初始架构决定了质量上限。

沿实际调用和数据链检查上层保证依赖的下层承诺：数据持久化、并发可见性、提交完成、幂等及错误传播由谁实现，跨边界如何验证。提供方测试、接口声明或历史批准不能替代真实消费者与目标环境的证据；需求、规模、团队、依赖或故障模式改变时，只复核受影响前提，不重开所有已确认决定。

### 门禁的维护、例外与退役

- 每个会阻断交付的门禁应能回指受保护约束、适用路径、维护责任及检查局限；先使用编译、类型、依赖或行为证据，语义尚不确定的启发式只产生待裁决提示。接入 CI 是持续执行方式，不把有脚本等同于规则正确，也不以关键词命中直接证明职责或业务语义。
- 守卫误报、漏报、输入版本失配或启动失败时，先区分规则不适用、规则已变和实现失效。用真实违规负例与合法对照验证修复；不能删掉失败断言、扩大忽略范围或将退出码改成成功来恢复绿灯。仍有效的权限、安全、兼容与数据不变量继续保护，必要时采用项目允许的替代证据或只暂停受影响的准出。
- 例外须有具体范围、理由、责任人、残余风险以及到期或复审触发条件；审批与授权按项目已有机制，不默认每次变更都新增人工审批。删除门禁前证明原约束已失去适用性，或其必要保护已由可执行替代覆盖，并核对引用和准出路径；“长期全绿”“噪声很多”或“规则来自旧版本”都不足以单独支持退役。

### 用真实变更核对收益

在同一责任范围内对照相近的实际变更，观察理解与修改涉及的模块、跨团队等待、验证耗时、返工、缺陷或故障恢复；按当前问题选择少量指标，记录口径、任务难度、暴露量及工具/人员等同时变化。没有可比基线时只报告当前观察和待验证收益，不把一次成功归因于某个架构或 AI 工具。

代码减少和生成提速须同时核对转移到依赖、迁移、运维、审查与使用者的成本；没有真实消费者、稳定共性和维护责任，不以平台化作为治理终点。分别说明保持可观察行为的重构、实现替换/迁移和行为修正，避免用“重构”掩盖兼容变化。达到本轮目标后停止，后续真实变化或反例再触发复审。

## 红线
1. 不得以“重构”为名混入无关功能变更。
2. 不得在没有契约测试、灰度和回滚方案时替换核心链路。
3. 不得把边界不清的单体直接拆成多个边界更不清的服务。
4. 不得在双写期间忽略失败处理、幂等、对账和主写方定义。
5. 不得让临时适配层长期无主；必须有下线条件、负责人和清理计划。
6. 不得把自动扫描结果直接等同于可删除、可迁移、可重写或可上线结论；排熵动作必须有源码锚点、契约证据、owner、验证和回滚边界。
7. 不得用“最小实现”删除必要校验、错误处理、安全/权限/资金兜底、审计、持久化意图、幂等或测试。
