# 产品判断动作链

本文把产品专家已有的产品洞察、Backlog、PRD、合议评审和 AI Native 产品上下文能力串成可调用的判断动作链。它参考 `pm-skills` 的“让产品判断成流程”思路，但不安装、复制或照搬外部 Skill。

## 使用时机

- 用户提到 `pm-skills`、产品判断成流程、产品动作链、产品判断动作链、路线图取舍、发布复盘或增长实验。
- 用户要求别一上来写 PRD，先判断产品定位、商业成立、核心用户、场景、触点、产品阶段、资源取舍和验证方式。
- 用户的访谈、工单、竞品、数据、路线图、PRD、发布材料散在多处，需要判断现在做什么、为什么做、先不做什么。
- 用户希望从反馈 / 资料进入机会、Backlog、PRD、验收种子或 AI Native 工程交接，而不是只写一份漂亮文档。
- AI Native 要判断产品事实、取舍结论和验收种子是否足以进入系分、TDD、编码或质量门禁。

## 不适用场景

- 只写普通 PRD 或产品方案，且方向、链路和取舍已有可信权威时，直接读 `product-prd-template.md` 和 `product-design-and-prd.md`；存在缺口时仍先走本动作链。
- 只做 Backlog 排序，直接读 `po-backlog-manager.md`。
- 只做产品洞察 / 机会雷达，直接读 `product-insight-analyst.md`。
- 只做系统设计、代码、测试或 CR，交给 `资深架构师`。
- 不安装 `phuryn/pm-skills`，不照搬其 68 个 skills、42 个 workflows、slash commands、plugins 或 PM 工具包。

## 读取后必须产出

- 当前处于产品判断动作链的哪一段、哪一道门禁，以及为什么。
- 已知事实 / 证据、合理推断、待确认项、范围外不做。
- 判断动作、取舍结论、不做项、下一产物、owner、验收 / 停止条件。
- 是否交给 `product-insight-analyst.md`、`po-backlog-manager.md`、PRD reference、合议评审 reference 或 AI Native 工程交接。

## 需要继续读取的 reference

- 反馈、访谈、工单、竞品、行业资料或知识库资料进入产品洞察时，读 `product-insight-analyst.md`。
- 产品定位、商业成立条件或产品阶段尚未收敛时，读 `product-architecture-methodology.md`；需要把多触点问题画成用户旅程或服务蓝图时，再读 `diagram-output.md`。
- 机会清单、优先级、路线图、User Story 或 AC 决策时，读 `po-backlog-manager.md`。
- 需要正式 PRD / 产品方案时，读 `product-prd-template.md` 和 `product-design-and-prd.md`。
- 需要多角色产品评审或 PRD 预扫描时，读 `product-deliberation-workflow.md` 和 `product-prd-quality-gates.md`。
- 需要交给 AI Native 或架构师时，读 `ai-native-product-context.md`，端到端编排交给 `wise-agent`。

## 1. 判断框架

用老祖宗的三层思维收敛复杂产品工作：

- **不易**：产品判断必须守住用户 / 主体、问题、证据、取舍、owner、验收和停止条件。
- **变易**：访谈、PRD、Backlog、路线图、发布和增长实验只是不同阶段的动作，不是孤立文档。
- **简易**：小团队优先固化四个高频入口：访谈 / 反馈总结、需求优先级、PRD / Product Context Card 准入、发布复盘 / 增长实验。

产品专家的职责不是把输入材料整理得更好看，而是把材料转成判断：现在解决什么问题，为什么值得做，为什么不是别的方案，先不做什么，下一步交给谁。

### 三层产品判断主轴

| 层 | 回答什么 | 最小产出与停止条件 |
| --- | --- | --- |
| 第一层：定方向 | 产品定位、商业成立条件、核心用户 / 非用户、真实问题 / 当前替代方式、目标结果 / 非目标，以及决定优先解决哪些问题与结果的**产品策略** | 方向事实或待验证假设；关键事实缺失时停止写完整 PRD，先给验证动作与 owner |
| 第二层：通链路 | 端到端用户场景、关键触点与断点、前台 / 后台 / 支撑责任、对象 / 状态 / 规则，以及如何提供体验和服务的**方案 / 服务策略** | 可恢复、可运营、责任闭合的链路；断点或责任无主时不进入完整方案 |
| 第三层：定取舍并形成可验证方案 | 资源与机会成本、Backlog 取舍、最小切片、PRD / 原型范围、验收种子、指标、owner、停止条件和反馈回流 | 可评审、可验收、可停止的方案；未达门禁时退回前层补证据 |

三层不是固定瀑布。既有产品的方向已有当前权威和证据时直接继承，从第二层或第三层进入，不为流程完整而重做发现；发现或实验也允许得出“不做、延后或停止”。发布复盘从第三层进入，但必须回看原始目标与验收种子，并按新证据修正前两层。

产品策略回答“为哪些用户优先解决哪些问题、追求什么结果、暂不做什么”；方案 / 服务策略回答“用什么体验、触点、后台和支撑方式兑现”。两者不得混成页面功能清单。

### 四门禁与六阶段收敛

需求明确与定性、目标与概念、流程与概要、用例与详细设计、产品-系分-原型对齐、业务 / 产品架构重构不是六份平行文档，而是四道判断门禁下的六类工作。门禁状态只取 `ready / blocked / stale / not_applicable`，保存在评审、任务或决策载体；正式 PRD 只吸收准出后的当前结论，不保留门禁流水。

| 门禁 | 对应工作 | 准出条件 | 未通过时 |
| --- | --- | --- | --- |
| 定义门 | 1. 需求明确与定性；2. 目标与概念整理 | 真实问题、影响主体、失败成本、当前替代、产品定性、目标 / 非目标、核心概念、Owner、证据和成功口径相容 | 停止画流程和写详细方案，只补当前主 blocker 与验证动作 |
| 设计门 | 3. 流程与概要设计；4. 用例驱动的详细设计 | 产品架构主脊、场景关系、责任推进、对象状态、规则权限、异常恢复和验收种子能双向追踪 | 缺场景先补场景，不用页面、字段、规则表或接口堆叠冒充详细设计 |
| 对齐门 | 5. 产品设计、系分设计与原型对齐 | 同一目标、场景、对象、规则和状态分别追到原型可见锚点、系分模块 / 接口 / 数据及 AC / 测试；各自 authority 和 revision 清楚 | 冲突项 `blocked / stale`，回到对应 Owner 裁决，不按篇幅、代码现状或多数材料投票 |
| 架构反馈门 | 6. 综合产品设计重构业务架构和产品架构 | 当前投资决策、范围、Owner、证据与验收明确；多个已确认场景或运行证据支持稳定能力、真实变化轴、重复建设或能力缺口 | 只交候选与补证据动作，不预建平台，不自动发起系统重构或执行授权 |

设计门内先确认代表性场景和验收种子，再让详细设计回答场景怎样成立。至少覆盖主链路、边界、异常、人工兜底和不可接受结果；场景推导责任、对象状态、业务规则、权限、数据和失败恢复，不能在详细设计完成后才让用户或 QA 补几个用例装饰结论。

四门禁不是固定瀑布：上游结论有当前权威时直接继承；只有来源 revision、产品不变量、场景结果或运行证据变化时，才把受影响门禁标为 `stale` 并按依赖回退。原型落后只重开对齐门；新证据推翻真实问题或核心概念时才回到定义门。任何单门准出都不自动产生下一门的业务确认、工程准入、测试通过或执行授权。

## 2. 七步动作链

| 阶段 | 输入 | 产品判断动作 | 输出 | 下一 owner |
| --- | --- | --- | --- | --- |
| 资料归集 | 访谈、工单、竞品、数据、政策、运营反馈 | 去重、分层、标注证据来源和置信度 | 资料资产表 / 问题候选 | 产品专家 |
| 问题地图 | 资料资产和业务目标 | 判断真实问题、影响面、失败成本和当前替代方式 | 问题地图 / 非标问题卡 | 产品专家 / 业务 owner |
| 机会判断 | 问题地图和证据链 | 判断机会是否足够强、是否有 owner、是否需要继续验证 | 机会雷达 | 产品专家 |
| 假设与风险 | 机会候选 | 写清解决方案假设、反例、风险、非目标和可证伪实验 | 假设卡 / 验证动作 | 产品专家 / UED / 业务 owner |
| Backlog 取舍 | 机会和验证结果 | 做 BV/EE、业务 / 用户 / 工程三桌校验、拒绝或延后理由 | Backlog 决策包 | 产品专家 / PO |
| PRD / 上下文 | 已选 Backlog | 补对象、流程、状态、规则、验收种子和待确认项 | PRD / Product Context Card | 产品专家 |
| 发布与回流 | 上线结果、数据、客服、运营、事故、复盘 | 判断是否达成目标、是否继续、收缩、废弃或进入下一轮 | 发布复盘 / 增长实验结论 | 业务 owner / AI Native |

“假设与风险”按当前决策真正存在的未知项选择，不要求每次机械填满四类：

| 风险 | 核心问题 | 常见证据 |
| --- | --- | --- |
| 价值风险 | 目标用户是否真有问题，结果是否值得争取 | 访谈、行为、替代方式、承诺或付出 |
| 可用性风险 | 用户能否理解、完成并恢复关键任务 | 原型任务、可用性观察、失败路径 |
| 商业成立风险 | 组织能否持续承担并获得相称价值 | 收入 / 成本 / 风险 / 效率 / 采用率 / 责任归属；内部平台不强制套收入模型 |
| 可行性风险 | 技术、数据、运营、法务或供应能力能否兑现 | 技术试验、数据核验、运营演练、规则确认 |

每个被选中的风险至少记录 `证据 / 置信度 / 验证动作 / 停止条件`；未验证的只能写成假设，不得升级为产品结论。

## 3. 知止者前置门禁

进入 AI Native 工程交接前，产品专家只回答产品侧是否足够：

- 产品定位、商业成立条件、核心用户 / 非用户、核心场景 / 当前替代方式、关键触点与断点、产品阶段 / 阶段证据是否已有事实，或由 owner 标为待确认。
- 业务目标和非目标是否能被验收。
- 核心对象、状态、流程、规则和异常是否能交给架构师消费。
- 验收种子是否覆盖正常、边界、异常、运营、数据和风险路径。
- 取舍结论是否说明了为什么做、为什么现在做、为什么不做其他项。
- 待确认项是否有 owner、影响范围和停止条件。

任一项不足时，输出补齐清单和下一 owner，不进入系分、TDD、编码或 Execution Grant。

## 4. 取舍规则

- 路线图是取舍账本，不是愿望清单；每个进入项必须有证据、owner、验收和拒绝 / 延后对照。
- 没有证据的机会只能进入待验证，不写成 PRD 结论。
- 没有 owner 的需求只能进入待确认，不交给研发排期。
- 没有验收种子的需求不能进入 TDD、编码或发布准出。
- 外部 workflow、文章观点或 AI 生成内容只能作为检查项，不能替代产品 owner 判断。

## 6. 回流规则

- 发布复盘必须回看原始目标与验收种子、上线结果、返工、缺陷、运营成本和用户价值；活动量、页面访问或功能上线本身不等于目标达成。
- 产品、系分或原型 revision 变化时，只把受影响门禁标为 `stale`；通过目标、场景、对象 / 状态、规则、原型锚点、工程资产和 AC / 测试的追踪关系重算影响，不整链重做。
- 多个产品设计或运行结果反复暴露稳定能力、真实变化轴、重复建设、责任断点或能力缺口时，才进入架构反馈门；重构结论回写业务 / 产品架构权威，并分别向受影响 PRD、系分、原型和验证载体传播，不把汇总分析变成系统改造授权。
- 增长实验必须说明假设、变量、样本、观察指标、停止条件和下一动作，不能只报数据涨跌。
- 已验证的产品经验可回流到 PRD 模板、Backlog 规则、Product Context Card 或 AI Native source-map；不得把一次性偏好、未确认推断或私有材料写入 Skill。

## 7. 不吸收边界

- 不把 `phuryn/pm-skills` 的 commands、plugins、slash command、PM toolkit、resume / NDA / privacy 等通用工具包搬入本仓库。
- 不新增固定九步模板；外部产品清单只用于发现判断缺口，现有动作链和专项 reference 仍是权威。
- 不把“AI 写 PRD 更快”当产品能力提升；判断链的价值在证据、取舍、owner、验收和回流。
- 不让 AI 替产品 owner 做最终路线图取舍、商业优先级、合规判断或上线承诺。
