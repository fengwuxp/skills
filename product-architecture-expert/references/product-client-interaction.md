# 客户端交互契约

## 使用时机

当需求要做原型、交互方案、页面任务流或多端体验设计，并同时出现 PC、手机、浏览器、APP、H5、响应式、适配、可用性、触控、键盘、弱网、通知或中断恢复时读取本文。

本文承接产品语义，不替代 `ui-design-expert` 的视觉、布局、组件、tokens 和可点击原型，也不替代平台工程对生命周期、权限和系统 API 的确认。

## 页面路径草图输出契约

用户只给页面跳转或服务调用、却要求称为完整用户旅程时，先输出“结论：仅为路径草图，完整旅程不成立”，随后原样列出最小字段骨架：`任务阶段 | 用户目标 / 负担 | 当前对象与状态 | 规则 / 权限生效点 | 前台 / 后台 / 人工责任 | 用户可见反馈 | 失败恢复 | 证据 / Owner | AC`。缺少这行骨架时，不能用“状态、责任、异常等”概括带过，也不能补写未确认的退款资格、状态或处理规则。

## 先拆开客户端名词

PC / 手机描述设备与使用情境；浏览器 / H5 / APP 描述运行载体。它们不是同一维度，也不是互斥清单。常见组合包括 `PC + 浏览器`、`PC + APP`、`手机 + H5` 和 `手机 + APP`。若只写“做移动端”或“做 PC 端”，先标记为待确认。

| 形态 | 先确认的输入与环境 | 产品级交互约束 |
| --- | --- | --- |
| PC | 键盘/鼠标、窗口大小、并行任务、显示器和打印/导出需求 | 支持可预测的焦点顺序、快捷操作、列表-详情或多栏工作流；窗口缩放不能丢失主任务和当前上下文 |
| 手机 | 触控、单手可达、方向变化、安全区、软键盘、系统打断 | 主任务短而聚焦，操作目标和手势按平台规范核验；返回、关闭、保存草稿和恢复路径必须明确 |
| 浏览器 | URL、历史、刷新、新标签、键盘、权限、浏览器差异和网络 | 深链、前进/后退、刷新、焦点和错误恢复可解释；不能只验证首屏截图 |
| APP | 前后台生命周期、系统权限、推送、深链、原生返回、缓存和离线策略 | 处理挂起、恢复、权限拒绝、通知进入和版本差异；涉及系统能力时交平台能力确认 |
| H5 | 移动浏览器视口、浏览器返回、分享/登录回跳、弱网、浏览器权限和安全区 | 不假定原生 API 或常驻通知；首屏、表单、回跳、刷新、失败重试和离开页面后的上下文必须可恢复 |

## 交互设计门禁

在画页面或写组件前，先形成一份客户端交互契约：

1. **任务**：角色、触发、目标结果、主路径、逆向路径、失败成本和停止条件。
2. **客户端**：应用、设备情境、运行载体、输入方式、窗口/视口、系统能力、网络和会话约束；事实未知时写假设和确认方。
3. **导航**：入口、当前位置、返回/取消、跨应用跳转、深链、刷新、重进和跨端续办；每次导航都说明是否保留上下文。
4. **输入**：键盘、鼠标、触控、手势、语音或系统选择器；关键动作必须有可发现的替代操作，不把悬停或复杂手势作为唯一入口。
5. **反馈**：提交中、成功、失败、部分成功、空数据、无权限、超时、离线、重复提交和不可用状态；反馈要靠近动作、说明下一步并允许恢复。
6. **中断与恢复**：来电/通知/切后台/刷新/返回/网络切换/会话过期后，说明数据是否保存、如何回到原任务、是否允许重试或撤销。
7. **可访问性**：Web/PC 检查键盘可用、焦点可见且顺序有意义、内容可重排；移动端检查触控目标、文字放大、方向、安全区和辅助技术语义。具体门槛以当前平台规范和 `WCAG 2.2` 核验，不把一个尺寸或颜色数字硬套所有端。
8. **可观察性**：任务成功、误操作、错误恢复、退出、回跳失败和跨端续办都要有事件或人工观察方式；指标只验证结果，不把埋点当成体验证据。

任务跨多个阶段时，优先使用一张用户路径—系统责任双向表：`阶段 | 用户目标 / 状态 / 负担 | 规则 / 风险 | 系统状态 / 责任 | 用户可见反馈 | 恢复动作 | 证据 / Owner`。每个阶段都要同时填用户侧与系统侧，并从用户等待、疑虑和失败反查系统承接，再从规则生效、状态变化和异常反查用户是否能理解、确认或恢复。只有页面跳转或服务调用时，必须标为未完成并按这张表列出缺口，不得命名为完整用户旅程。

页面跳转图或服务调用图若要进入完整旅程评审，至少先补一行字段骨架：`任务阶段 | 用户目标 / 负担 | 当前对象与状态 | 规则 / 权限生效点 | 前台 / 后台 / 人工责任 | 用户可见反馈 | 失败恢复 | 证据 / Owner | AC`。缺少其中的责任、状态、异常或恢复字段时，只能交付为页面 / 服务路径草图，不能用成功页或接口名补足业务闭环。

## 状态矩阵

每个关键页面或任务节点至少补齐：

`客户端 | 承接 ID | 前置状态 | 输入 | 系统响应 | 用户可见反馈 | 下一步 | 可恢复性 | AC`

状态至少按任务裁剪覆盖：`loading`、`ready`、`empty`、`partial`、`submitting`、`success`、`error`、`offline/timeout`、`permission denied`、`disabled`、`expired`。不能用一张“成功页面”代表完整交互，也不能把错误只写成 toast；需要用户继续操作时，错误应指出范围、原因类别和恢复动作。

## 多端适配策略

先按内容、任务和输入约束决定变化点，再选择策略：

- **fluid**：内容和间距随可用空间连续变化，适合不改变任务语义的场景。
- **reflow**：改变排列、栏数或阅读顺序，必须保留语义和焦点顺序。
- **show/hide**：隐藏次要信息或延后披露，不能隐藏完成主任务所需的状态和操作。
- **re-architect**：在小屏改成单列、分步、列表-详情或底部主操作；这是交互重构，不是把桌面页面缩小。
- **progressive enhancement**：H5/浏览器先保证基础任务，再按能力增加分享、通知或设备集成；能力不可用时仍有可解释的回退。

断点应由内容和任务在何处失效来证明，不按设备型号堆断点。跨端不变的是业务对象、状态、权限、规则和验收；可变的是导航、信息密度、输入、反馈位置、生命周期、网络和系统能力。

## 原型交付物

产品专家至少交付以下产品级材料，随后再交给 `ui-design-expert` 绘制视觉或可点击原型：

1. **客户端策略表**：`应用 | 设备情境 | 运行载体 | 输入 | 系统约束 | 导航策略 | 失败/恢复 | 证据 | Owner`。
2. **任务与路由图**：标出入口、页面/状态、非页面能力、跨应用跳转、上下文和返回路径。
3. **交互状态矩阵**：覆盖正常、空、加载、错误、权限、离线/超时、重复提交和恢复。
4. **多端差异表**：`稳定语义 | 端侧变化 | 变化理由 | 证据 | 影响 | 回退 | AC`；无证据的差异只能是待观察，不直接复制。
5. **原型验收卡**：每端至少一条主任务和一条失败恢复任务，列出目标视口/设备、输入方式、可观察结果、指标或人工走查方式、停止条件。

产品专家定义必须呈现、可操作、可观察的业务事实；不在此处决定布局像素、组件 API、视觉 token 或具体原型工具。

## 验证与停止条件

- PC/浏览器：用真实窗口尺寸走查键盘、焦点、前进/后退、刷新、深链、长内容和错误恢复。
- 手机/APP：用真实触控与方向走查单手主任务、软键盘遮挡、系统返回、权限拒绝、切后台恢复和安全区。
- H5：额外走查浏览器返回、分享/登录回跳、弱网、刷新、离开页面、无原生能力回退和目标浏览器。
- 只看静态截图、组件文档或首屏通过，不足以证明交互可用；至少要有可操作原型、真实页面或受控走查证据。
- 缺少目标客户端、关键任务、用户证据或平台能力确认时，止于假设、问题清单和最小试片，不声称“用户体验好”。

## 公开参考的吸收边界

本文只吸收公开规范中的适配、输入、焦点、重排、触控和系统情境检查项。W3C、Apple、Material 和 Fluent 的设计语言、组件名、尺寸和实现方式不自动成为本项目标准；具体产品仍以用户任务、项目事实、平台版本和 Owner 验收为准。来源与读取日期见 `references/source-map.md`。
