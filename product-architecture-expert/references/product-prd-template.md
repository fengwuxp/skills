# 产品 PRD 文档模板

本文是产品架构专家的 PRD 主模板，用于把需求整理成可评审、可开发、可测试、可运营的产品文档。默认目标是让人先读懂问题、判断和方案，不是把写作检查项铺成全量手册。产品定义在正文讲清，执行与证据明细优先使用项目已有承接文档；复杂度决定展开深度，不决定标题数量。

使用前先明确文档目标、目标读者和文档类型。主文档只回答：为什么做、要达到什么目标、这是什么性质的问题、总体与详细方案是什么、流程如何运转、遵循什么规则、向角色或上下游承诺哪些业务结果、还有哪些风险及如何判断结果。生成前先裁剪，不能把轻量需求写成无人评审的长文，也不能只用功能名替代范围、规则和验收。

模板占位符使用 `〈...〉` 表示。实际输出时，正文段落和表格单元格默认保持普通文本；只有接口路径、技术字段、配置键、协议字段、风险等级或需要强调的结论才使用加粗或代码背景。

## 文档标识与文件命名

创建正式产品文档前，先确定规范主题、文档类型和目标路径，优先级为：用户明确指定 > 项目 `AGENTS.md` / `README.md` > 仓库已一致执行的约定 > 本模板回退规则。仓库现有文件名相互冲突时，不把单个历史文件当成规范；将冲突列为待确认并询问 owner。只有用户明确授权项目约规治理时才修改 `AGENTS.md` / `README.md`；未授权时，更新既有文档保持原路径，新建文档使用本模板回退规则并说明。

- PRD、产品需求文档和需求说明书统一使用 `〈主题〉-产品设计.md`，一级标题使用 `# 〈主题〉产品设计`。
- 其他正式产品产物使用 `〈主题〉-〈明确产物类型〉.md`，产物类型优先使用 `产品架构`、`业务架构`、`产品评审报告` 或 `产品上下文卡`，不得只写模糊的“方案”“设计”或“说明”。
- 主题和文档类型之间只使用一个 ASCII 连字符 `-`；主题内部保留稳定领域术语和 `API`、`DSL` 等既有缩写，不用空格、下划线或中文破折号做结构分隔。
- 文件名默认不包含序号、日期、版本、`草稿`、`最终版`、`新版` 等状态；顺序、版本和状态进入索引、文档头与 Git 历史。
- 产品专家负责给出规范主题；同一能力交给架构师时必须传递“规范主题 + 产品文档精确路径”，不得让下游自行改写业务概念。
- 更新既有文档默认保持原路径。只有用户明确进入命名迁移任务时才改名，并同步 Markdown 链接、任务材料、脚本、测试和其他硬编码路径。

## 使用时机

- 用户要求写作、生成、完善、补全、改写或评审 PRD、产品需求文档、需求说明书、需求文档模板、PRD 模板或产品方案模板。

## 不适用场景

- 仅做产品架构方法分析时读 `product-architecture-methodology.md`。
- 支付资金、PRD 评审、运营数据发布等专项内容按需读取独立附录，不在主模板展开。

## 读取后必须产出

- 当前任务需要的 PRD 或模板修改；裁剪依据、待确认项和补充材料只在影响判断时说明，不额外输出空骨架或完整组件目录。

## 需要继续读取的 reference

- PRD 写作标准读 `product-design-and-prd.md`。
- 产品方案交给架构师继续设计、业务驱动架构交接或 TDD 承接时读 `product-architecture-methodology.md`。
- 正式评审、提交前检查、CR、触发验证或符合性评审时读取 `product-prd-quality-gates.md`。
- 支付资金专项由 `payment-expert` 提供。
- 运营后台、通知、数据指标、埋点、报表、导出、发布后验证读 `product-prd-operations-and-data.md`。

## 信息传递流程

PRD 的正文按读者理解顺序组织：背景与问题 -> 目标与非目标 -> 定性与范围 -> 概要设计 -> 详细设计（业务场景与流程、能力对象、产品需求陈述）-> 业务规则 -> 风险与待确认 -> 验收摘要。设计生成仍可按“名 -> 事 ->（图）-> 法 -> 器 -> 验”由虚入实检查，但完整性框架不等于可见目录：

1. 事实：原始反馈、数据线索、业务背景、现状约束和真实问题。
2. 判断：问题是否成立、影响多大、证据强度如何、哪些仍是假设。
3. 决策：本期做什么、不做什么、优先级为什么这样排。
4. 承诺：产品能力、用户场景、流程规则、权限数据和风险处理。
5. 验证：验收种子、可观察结果、确认方、交给架构师或测试的依据。

其中“名”定义产品名相、主体、对象和边界；“事”说明真实场景与流程；“图”按复杂度用最小关键图暴露关系、状态、边界和冲突；“法”说明状态、不变量、规则和异常；“器”说明产品能力、前后台和数据载体；“验”说明可观察结果。它只用于作者和评审者检查是否贯通，不直接变成章节名、卡片数量或表格数量。

华夏经世智慧只作编辑内核：正名检查场景、能力、规则、页面是否名实相符；审时按阶段、复杂度和评审问题选择文字或图；知止删除未命中的字段、图和附录；行验要求不同角色无需作者口头补充即可复述同一业务结果、边界、规则、异常承接和完成标准。详细镜片仍以 `huaxia-practical-wisdom` 为准，不把经典名词写成新的 PRD 目录或产品事实。

描述可靠性必须可见：已确认、假设、待确认、不适用要分开写；无法确认的信息不得写成确定结论。

同时按角色分层消费：决策层服务业务 / 管理者，说明为什么做、做什么和成功标准；方案层服务产品 / 设计 / 架构，说明方案取舍、范围、成本和风险；实现层服务开发 / 测试 / 发布，说明输入输出、边界异常、接口事件、验收和验证证据。

权威来源各守一处：PRD 是当前产品语义的权威来源；协同主记录承载状态、排期、过程决策和阶段门；执行计划承载详细验收映射、验证命令、执行 owner 和任务状态；Decision Log 承载历史取舍。PRD 只链接其他载体的适用版本和当前状态，不复制易漂移内容；没有对应载体时说明不适用，不为填模板新建台账。

## 表达结构选择

- 背景、定性、方案和取舍优先用短段落讲清因果；结论、范围和风险用项目符号帮助扫读。
- 单个问题、规则、验收和待确认项直接写成段落或列表；只有同类条目反复出现、需要稳定引用或横向比较时才使用卡片和 ID。
- 业务流程优先用编号步骤或文本流程，便于读者理解先后关系。
- 流程、规则和异常优先用主动责任句表达：“谁在什么条件下做什么，产品产生什么可观察结果，失败后谁承接”；不得用“进行处理”“相关方负责”等无主体表述隐藏责任。
- 多角色、多对象、多状态、多团队协作或评审者难以凭文字建立共同理解时，优先补一张最小关键图；图形是 PRD 的阅读入口，不替代规则、验收和待确认项。
- 表格只用于比较、矩阵或追踪；不要把所有信息都塞进表格。
- 多条目只有确需横向比较时才合并成表格。条件、例外或责任需要长句才能讲清时，按场景或规则改成纵向条目；不靠压缩条件、缩小字号或固定字数来保住宽表。

## 图形化视图选择

图不是新的产品事实源。图形按问题选择，不要求每份 PRD 固定画全套；普通轻量 PRD 可以只保留文本流程，不必把“不需要单独画图”写进正文。每个场景默认选择一种主表达，只有不同图分别解决独立评审问题时才组合：

| 要回答的问题 | 优先表达 |
| --- | --- |
| 单一角色、线性路径 | 编号文字，不画图 |
| 条件判断、循环或失败分支 | 流程图 |
| 多角色、跨团队交接和 SLA | 泳道图 |
| 角色权限、系统边界和核心用例 | 产品全貌或概要设计中的用例图 |
| 核心对象生命周期和禁止迁移 | 状态机图 |
| 能力边界、前后台和外部依赖 | 能力地图或产品架构图 |

用例图不表达先后顺序和异常分支，不逐场景机械绘制；流程图、泳道图和状态机也不能替代正文中的规则、业务结果和异常责任。

每张图必须说明图形目标、目标读者、对应 PRD 章节、关键假设、待确认项和与验收/规则的追踪关系。需要正式图形化交付时读取 `diagram-output.md`；默认输出 SVG，Mermaid/Markdown 草图、PNG/PDF/截图等其他格式需用户明确提出。

## 使用与裁剪原则

PRD 使用轻量 / 标准 / 增强三种文档强度，强度只决定展开深度，不降低事实、责任和验收要求：

- 轻量：单一主体、对象或流程，低风险、可逆、协作面小；保留背景、目标范围、一个场景、原子需求、适用规则和验收摘要，可合并相邻章节。无独立规则时与需求合并，不强制规则卡、ID、矩阵或图。
- 标准：多主体、对象、状态、团队或需要工程交接；展开产品摘要、场景、产品需求陈述、对象状态、核心规则、异常人工和验收摘要。
- 增强：资金、合规、安全、隐私、跨组织公共契约、不可逆或高失败成本；在标准内容上增加外部规则版本、规则冲突、命中策略、专业确认和完整风险。高风险需求直接使用增强模式。
- 模板中的必填 / 条件必填约束语义覆盖，不要求一个问题对应一个可见模块。生成前为每项内容确定用途和唯一权威位置：已在场景、规则或范围讲清的内容只引用；未命中项不保留空标题或“不适用”占位。项目已有章节名、路径和稳定 ID 继续兼容，不为模板升级全库改名。
- 正式正文必须先形成背景、目标、定性、概要与详细设计、流程、规则和必要协作约定的连续叙述；不得以问题卡、追踪表、需求 ID 或验收矩阵开篇。
- 多角色、多对象、多状态、多团队依赖或高风险需求，才展开核心概念、业务抽象、对象、流程、状态、规则、权限、审计和附录。
- 术语含义可能冲突、新业务对象首次进入 PRD、业务抽象会影响研发建模、或需要交给架构师/TDD 承接时，展开“核心概念与业务抽象”；轻量 PRD 可合并为 3-5 行术语说明。
- 未知信息写“待确认”，同时说明影响、确认方和未确认前处理方式。
- 正式 PRD 以最终标准版本为主，只保留当前有效的目标、范围、规则、风险、待确认、验收和必要版本元信息；讨论过程、迭代草稿、AI 推理轨迹、多角色争论、被拒方案的讨论展开和修订流水进入任务计划、产品合议评审报告、Decision Log 或中间任务文档，不复制进正文。
- 文档控制采用下方“文档状态与责任”的紧凑入口；较长的来源核验、评审结论摘要和过程记录链接放页尾。治理内容不按全文比例配额裁剪，必要责任和状态不能省略。
- 只有目标、范围、对象、流程、规则、权限或验收等产品语义变化才升级 PRD 版本；排期、任务状态、协作拆分或纯格式变化只更新对应载体，不升级 PRD 版本。
- 需求变更必须补影响清单，覆盖目标/范围、流程/交互、规则/字段、接口/事件、验收种子、测试用例、发布风险和通知对象；影响清单进入过程资产，正式 PRD 只保留当前有效结论和链接。
- 验收摘要放在正文末尾，保留业务结果、关键边界、异常、红线和产品确认方。详细验收及执行证据按第 8 节归位；不能用外置测试文档代替正文中的产品定义。

优先级口径：

- P0：没有它不能上线、不能验收或会造成关键业务/资金/合规/安全风险。
- P1：核心体验或主流程必须具备，但可以通过灰度、人工兜底或明确限制降低上线风险。
- P2：增强体验、运营效率或后续扩展能力，不应阻塞当前版本核心目标。

## 默认 PRD 主模板：读者主线

标准 / 增强 PRD 在紧凑元数据之后、正文主线之前使用不编号的“产品摘要”；轻量需求可并入背景，但产品定位、目标、范围和关键待确认仍必须能被读者直接理解。

### 文档状态与责任（正式 PRD 必填）

正式输出将状态入口放在标题下，不必单列治理章节；通常合并为以下三项，使用显式短列表或独立段落，不依赖源码换行保证预览分行，也不把行数当门禁：

- 当前版本：〈当前生效版本〉；文档状态：〈草稿 / 评审中 / 已确认 / 已废弃〉；更新时间：〈YYYY-MM-DD HH:mm + 时区〉。
- 产品 owner：〈负责产品判断、范围和版本〉；业务 owner：〈负责业务目标、规则和结果确认〉。
- 文档强度：〈轻量 / 标准 / 增强〉；依据：〈风险、复杂度、不可逆性和协作面〉；权威来源：〈本 PRD 的权威位置〉。

### 产品摘要（标准 / 增强必填）

先用一段话说明〈这是什么产品或能力，服务谁，解决什么问题，提供什么业务价值〉；再按实际复杂度用短段落或少量条目说明：

- 本期范围：〈承诺交付什么，以及防止误解所必需的非目标〉。
- 核心链路：〈主要参与方如何从业务触发取得可观察结果〉。
- 异常与边界：〈关键失败如何承接，哪些责任或结果不能越界〉。
- 关键待确认：〈会影响当前判断的未决事项、确认方和未确认前处理〉；没有真实未决事项时不占位。

上述是语义覆盖，不是新增四个必填小节；内容简单时可以合并，不能只改标题却仍写“去哪里读”。摘要压缩正文的产品结论，不新增规则或提升未决状态，也不复刻完整对象清单、需求注册表或治理台账。架构主脊和能力关系在第 4 节展开，不要求在摘要中重复；具体未决项在第 7 节维护。

阅读导航只在长文确有定位需要时提供简短链接，不能代替产品摘要，也不另建同义摘要章节；版本、责任人和评审状态仍归紧凑元数据，完整治理明细归文末。

### 1. 背景与问题

用连续短段落说明为什么现在要做、谁受到影响、现有处理方式在哪里受阻，以及判断依据来自哪里。先讲事实，再讲产品判断；不要以追踪表、问题 ID 或功能清单开篇。

- 现状与背景：〈当前业务、用户或运营处境〉
- 真实问题：〈用户任务、业务流程或经营目标受到什么阻碍〉
- 影响对象与代价：〈影响谁，不处理会发生什么〉
- 证据与可信度：〈访谈、数据、工单、事故、会议结论；已确认 / 假设 / 待确认〉

不把“用户要某功能”直接写成真实问题。来源较多、观点冲突或需要审计时，再在按需附录中建立反馈证据与问题地图。

### 2. 目标与非目标

先用一段话连接〈业务目标：希望改变的业务结果〉和〈用户目标：用户因此能够完成的任务〉；两者有不同判断用途时再分列，不机械写两组同义清单。

- 成功标准：〈指标或可观察结果、当前基线、目标值 / 目标状态、观察窗口和确认 owner；无历史基线时说明基线建立方式，不虚构数字〉
- 本期非目标（按需）：〈容易被误认为已承诺、或会影响当前设计的排除项及原因〉；范围在第 3 节已完整定义时只引用，不另列“本期不做”的平行清单。
- 停止或拆期信号（按需）：〈何种真实条件变化需要重新评审范围〉。用户流程中的停止条件写入场景；未确认事项造成的设计或开放停止线写入第 7 节，不混成一组泛化风险。

成功标准衡量上线后是否达成业务、用户和产品目标；第 8 节验收摘要判断产品是否按当前定义正确交付，两者不得混用。

目标只保留业务结果、用户能力、风险边界和可观察成功状态。业务条件、对象状态和稳定能力承诺下沉到核心概念、业务规则或必要协作约定；接口路径、协议字段、Provider 路由和内部对象装配等实现细节进入系分。目标可以引用稳定边界，但不复制精确规则。API 或数据本身是商业供给时可以进入目标，精确技术协议仍不进入目标层。

### 3. 定性、范围与总体判断

本节回答“这究竟是什么问题，应该在什么边界内解决”，避免未定性就堆功能：

- 名实：
  - 定性对象：〈产品 / 商业供给 / 产品能力 / 业务主体 / 业务对象 / 业务流程 / 业务规则 / 业务状态 / 业务指标 / 交互载体 / 协议 / 技术机制〉
  - 本期变化：〈新建 / 增强 / 治理 / 风险约束 / 运营提效 / 迁移 / 退役 / 验证〉
  - 责任边界：〈服务谁、稳定提供什么、负责到哪里、不负责什么〉
- 范围：〈目标用户、业务主体、规则 / 风险 / 验收责任主体，本期做与不做、上下游和人工承接〉。
- 架构（能力提供者视角）：〈共性与核心要素：跨场景共同的目标、能力、对象、流程、规则和不变量〉；只有存在多个真实场景或演化要求时，再说明〈特殊性 / 变化轴、稳定点 / 变化点〉。
- 取舍：〈总体判断与可信度、推荐方案及理由、阶段 / 能力差距、机会成本 / 依赖顺序、不采用项及复审条件〉；不存在真实备选或跨阶段依赖时不凑项。

察同用于发现稳定能力，辨异用于保护真实场景边界。一次性、局部或尚未证明复用价值的需求直接做最小方案，不强行抽象成平台能力。

产品资格判断不能省略，但独立“产品资格声明”只在产品、能力、对象或交互载体容易混淆时展开；本节已讲清定性和责任边界时，不另写重复声明。

产品应先形成自己的判断和推荐方案；只有资源投入、商业取舍、合规、安全、财务等超出产品权限的事项才交给对应 owner，不把产品应完成的方案选择抛给需求方。

#### 核心概念与业务口径（条件必填）

术语存在歧义、新业务对象首次进入 PRD、概念语义发生变化，或概念会影响跨团队理解、工程建模、规则和验收时展开；否则删除本节并引用当前有效术语库。概念选择范围只决定当前 PRD 需要列出哪些概念，不改变概念定义的效力；被选中的概念采用项目或产品域统一定义，不复制完整术语库。

| 概念 | 类型 | 统一定义 | 边界 / 不等于 |
| --- | --- | --- | --- |
| 〈名称〉 | 〈产品 / 商业供给 / 产品能力 / 业务主体 / 业务对象 / 业务流程 / 业务规则 / 业务状态 / 业务指标 / 交互载体 / 协议 / 技术机制〉 | 〈整个项目或产品域统一使用的一句话业务定义〉 | 〈容易混淆但不属于它的内容〉 |

术语只是概念的名称，业务概念承载团队共同语义，系统别名只记录代码、字段、接口或历史系统中的称呼。代码、旧页面和历史叫法只能作为现状证据，不能反向定义业务概念。概念废弃或迁移语义写入边界或独立生命周期卡，业务对象状态进入对象状态章节；Owner 和权威来源进入文档责任、参与方、规则、外部事实或待确认项，不在概念表逐行重复。

复杂 PRD 在详细设计中可以继续区分本域事实、关系事实、产品视图、请求时派生投影、外部事实引用、协作契约和受控操作事实；这些是当前模型中的概念角色，不新增一级语义类型，也不要求修改上述概念表结构。非目标或废弃概念若仍以当前对象、状态、需求或验收出现，必须先消除冲突。

### 4. 概要设计

用一段方案概述和一张按需关键图，让读者先建立整体认识，再进入细节：

- 方案概述：〈产品如何解决前述问题，为什么选择这条路径〉
- 产品架构主脊：〈目标 -> 场景 -> 能力 -> 对象 / 状态 -> 规则 -> 业务结果〉
- 核心能力：〈面向用户、运营、上下游提供哪些稳定能力〉
- 核心对象与关系：〈对象、归属主体、生命周期和关键不变量〉
- 关键交互与边界：〈用户端、运营端、外部参与方如何协作〉
- 方案取舍：〈真实备选、选择理由、放弃理由和复审条件〉
- 产品视图：〈核心关系、状态与边界；按需配用例图 / 流程图 / 泳道图 / 状态机 / 能力地图〉

图不是新的产品事实源。多角色、多对象、多状态、多团队或跨系统时，选择一张最小关键图暴露关系、状态、边界和冲突；编号文字已经清楚时不必补图或在正文解释不画图理由。

参与方与责任只在多方交接或职责易混淆时单列；简单需求在场景中使用主动责任句即可。参与者与用例映射只回答角色覆盖、权限差异或缺失用例等具体问题，不复刻场景清单和需求注册表。

### 5. 详细设计

按场景展开能力如何被使用，不按页面控件或 AI 卡片展开：

#### 5.1 业务场景与场景内流程

业务场景是主体在明确触发和前置事实下，为解决一个真实业务问题，经过规则约束的流程取得可观察结果的过程。它不是页面、按钮、CRUD、API 或笼统功能名。

轻量、单主体、单流程需求可以用一段结构化文字表达；标准 / 增强 PRD 的 P0/P1 场景应逐项闭环。业务场景与场景内流程使用同一份叙述，不另设同义流程章节。稳定 ID 只用于确有跨章节追踪需要的场景。

##### 场景总览（多场景时）

- 场景清单：〈本期场景名称及其业务结果〉
- 场景关系：〈串联 / 并行 / 分支 / 互斥 / 独立；说明关系依据和关键交接〉

多场景必须先声明关系。`独立` 表示各场景分别闭环，不增加共享流程；`串联`、`并行`、`分支` 或 `互斥` 表示场景共同构成一个端到端结果，继续展开跨场景端到端流程。场景数量本身不证明存在共享流程。

##### SCN-001 〈业务场景名称〉

- 业务情境：〈谁因为什么问题，在什么状态下要取得什么业务结果〉
- 责任推进：〈谁先做什么，产品依据什么继续，谁接收反馈或承接异常〉
- 裁决与状态：〈引用规则；对象发生什么状态变化，关键边界或禁止结果是什么〉
- 异常与收口：〈失败后看到什么、谁接管、怎样恢复、什么证据证明完成〉

四段按“情境 -> 行动 -> 裁决 -> 收口”连续展开。旧有六标签场景卡仍可读取，但新 PRD 默认使用四段式；对象状态、共享规则、非目标、待确认和原型索引在各自权威位置维护，场景只引用，不为局部完整重复全文。

场景特有的数据输入、可见范围、操作权限、通知、失败恢复和人工接管就近说明；跨场景复用的约束放第 6 或第 7 节。不能让读者为理解当前动作来回拼接多个尾部章节。

##### 跨场景端到端流程与图形视图（条件必填）

只在场景关系为串联、并行、分支或互斥，或存在共享对象生命周期、跨团队协作、高风险状态变化时展开；单场景和关系为独立的多场景删除本节。使用编号步骤或按问题选择的关键图讲清：

1. 覆盖场景：〈哪些场景共同组成该流程，以及先后、并行、分支或互斥关系〉
2. 参与者与交接：〈谁在何种条件下把什么责任交给谁〉
3. 前置事实与状态变化：〈输入、关键裁决、共享对象状态和禁止迁移〉
4. 异常与收口：〈失败、超时、中断、外部不可用、人工处理和可观察结果〉

正文直接说明实际覆盖场景之间的顺序、条件、交接与共享状态，引用已有场景、规则、风险和验收入口即可；追踪可以经场景回到权威章节，不重复维护一套局部清单。“本节不重复什么”和“为何选择编号或不补图”是作者取舍，不要求进入读者正文，也不要求凑齐主流程、逆向流程、异常流程和人工处理。

确需独立交付图形时，按图形化视图约定补充必要元数据；既有 `视图元数据` / `图形元数据` 继续兼容。使用节章称谓时与标题层级一致。是否需要补图由实际理解问题决定，不由标题是否包含“图形视图”决定；新旧标题采用相同的业务内容检查。

跨场景流程只表达场景之间的关系和共享状态，不复述各场景四段。图只降低关系、顺序或状态的理解成本，不替代规则、业务结果和异常责任。已有 PRD 的独立一级“关键流程”仍可读取；新建或按本模板重写时移入本节，不为纯格式迁移改写已确认业务语义。

同一 PRD 同时包含业务主流程、配置治理、请求时判定、外部协作、高风险生命周期或迁移恢复等不同责任与时间尺度时，应按实际流程族分组并声明它们的关系；共享对象不等于首尾串联。单场景线性流程不强制分组。

#### 5.2 产品能力与对象设计

- 能力职责：〈解决什么稳定业务问题，不负责什么〉
- 核心对象：〈定义、归属、字段口径、生命周期、状态和不变量〉
- 用户端与运营端：〈入口、查询、处理、复核、通知和人工兜底〉
- 扩展边界：〈真实变化轴如何扩展；无证据的未来需求不预埋〉

同类能力、对象或需求较多，需要稳定引用时再增加 `REQ-001` 等 ID；每个 P0/P1 需求仍须能回到问题、目标、场景、规则和验收，不要求正文处处展示追踪编号。

#### 5.3 产品需求陈述

详细语义、规范强度及检查器支持范围以 `product-design-and-prd.md` 的 Requirement Statement Contract 为唯一权威。少量需求默认按业务句展开，而不是把完整性清单挤成一段：

需求名称：〈名称〉；需求类型：〈功能 / 质量 / 约束〉。

在〈场景 / 前置状态〉时，〈责任主体〉必须〈可观察行为或结果〉。
需求边界：〈单位、次数、时间、状态或临界值〉。

- 来源与可靠性：〈事实来源与确认状态〉；关联规则：〈当前规则入口〉。
- 验收样例：〈可观察完成证据〉。

禁止结果改用“不得”；其他规范强度按语义合同表达。一条需求只表达一个主要业务结果。只有多需求需要横向比较、跨文档追踪或版本治理时才使用表格和稳定 ID；表格过宽时按业务场景分组，不删除关键条件来维持单表，也不把九类语义字段机械打印成连续段落。

### 6. 业务规则

#### 6.1 业务规则

详细字段、升级条件和例外规则以 `product-design-and-prd.md` 的 Business Rule Contract 为唯一权威。本节维护需要独立引用的规则；场景引用规则，不复制第二份正文。

默认使用短标题与纵向段落，不要求一个字段占一行。下列标签可在段落中保留，兼顾扫读与现有结构检查；需要稳定交叉引用时增加规则编号：

规则名称：〈名称〉；规则性质：〈不变量 / 场景裁决 / 派生计算 / 版本化或外部规则〉；业务动机：〈为什么存在〉。适用场景 / 步骤：〈场景及步骤〉。

适用对象与范围：〈主体、渠道、时间等边界〉；输入事实：〈裁决依据〉。当：〈明确条件及组合关系〉；则：〈可观察结论或状态〉；Owner：〈业务责任人〉。

存在多个分支时，每个条目就近写成“〈条件〉时，〈结果〉。”或“当：〈条件〉；则：〈结果〉”，纵向排列；不要先用斜杠串起全部条件，再让读者与另一串结果按位置配对。适用范围、输入事实和 Owner 等共性说明只保留一次；分支优先级仍以已确认规则为准，不由排版顺序新增。

- 正例：〈对应条件与结果〉。
- 边界例：〈对应条件与结果〉。
- 反例：〈对应条件与禁止结果〉。

版本化 / 外部规则继续补来源、版本、生效期、适用范围和未确认前处理；例外必须有独立规则或人工裁决门禁，不写“特殊情况另行处理”。

重复规则先归一权威位置，冲突先澄清优先级或保留待确认；二者都不自动触发矩阵。确需横向比较才使用窄表，多输入、多输出和命中策略复杂时才使用决策表。表格中的长条件、例外和恢复说明回到对应规则段落，不删减业务条件来迁就版面。

#### 6.2 对外能力与协作约定（按需）

仅按 `product-design-and-prd.md` 的“按需对外能力与协作约定”判断是否保留本节；已由场景、规则或共性约束清晰承载的业务事实不再复述。没有独立承诺时直接删除本节，不新增作者声明或选择器。需要独立承诺时按能力逐条表达，以下语义可用短段落或必要的比较表承载：

- 能力名称：〈稳定业务能力名称〉
- 使用方：〈谁通过该能力完成什么任务〉
- 输入与前置：〈业务材料、对象状态、权限和规则前提〉
- 结果与状态变化：〈返回什么业务结果，改变什么对象或状态〉
- 失败承接：〈拒绝、挂起、恢复或人工处理，由谁承接〉
- 责任边界：〈本产品、使用方、外部机构或运营分别负责什么〉

技术协议、字段、错误码和幂等实现由系分继续设计；产品侧只固定会影响用户、业务规则和跨团队承诺的语义。

### 7. 数据、权限、风险与待确认

本节只补跨场景共性约束和真实未决事项，不作为兜底大章。数据、权限、运营和风险按当前需求选用，不逐类铺满：

- 共性约束：〈尚未在场景或规则中定义的指标口径、数据分级与留存、审计、运营承诺及责任〉。能力地图回第 4 节，责任边界回第 3 节；不再增加第二份需求索引。
- 待确认：〈尚未决定什么、当前已确认边界、影响、确认方、未确认前处理和必要复审条件〉。条目较长时用纵向段落，稳定编号继续保留。

风险已有处置结论时，把有效约束固化进场景或规则；仍有参数、开放条件或专业签收未确认时继续显式保留。部分确认不等于全部关闭，产品结论已确认不等于工程完成或生产准出。

历史决定仅在正文已承接全部有效条件、确认方与稳定引用后退出主阅读路径，过程追溯使用已有记录；无法证明等价时继续保留。不得因状态写着 ACCEPT、章节过长或降低比例而批量删除。

### 8. 验收摘要与产品到架构交接

验收摘要放在正文末尾，按业务场景判断产品是否按当前定义正确交付；它不重复第 2 节成功标准对上线后目标效果的衡量。每组摘要先注明“对应场景”，再用紧凑段落覆盖以下语义，不要求逐字段列八行：

对应场景：〈SCN-001 或明确场景名称〉。正常结果：〈可观察的成功状态及证据〉；边界结果 / 禁止结果：〈关键临界条件及不得发生的结果〉。

失败后的可观察状态：〈用户和运营看到什么〉；恢复或人工处理：〈谁在什么条件下接管、如何恢复及何时完成〉；验收 Owner：〈业务 / 产品 / 运营 / 专业确认方〉。

正文必须足以判断产品结果，不用“见测试用例”代替关键边界和恢复定义。详细 AC、Given / When / Then、测试映射、验证命令、执行 owner、任务状态和运行证据优先进入项目已有验收清单或执行计划，保留原编号、条件和追踪；没有独立生命周期不新建文档。法规、审计、合同或项目约规要求单文档追踪时，可放末尾附录。长条件按条目纵向表达，不把宽表原样搬到附件。

产品到架构交接默认只写：

- 权威输入：〈规范主题、PRD 精确路径与版本，场景、规则、接口和验收的定位入口〉。
- 不得自行补定：〈尚未确认的假设、专业边界、确认方和未确认前处理〉；已在第 7 节定义时直接引用。
- 承接位置：〈已有系分、验收或执行计划，以及各自接收范围〉；未建立时明确待承接，不创建空链接。

不另维护一份缩小版 PRD。仅当独立下游无法直接消费正文时，按 `product-architecture-methodology.md` 输出 Product Context Card，注明来源版本和适用边界；它是只读交接投影，规则变化必须先回 PRD 评审。

## PRD 按需组件库

以下组件只在命中复杂度或风险时展开；主文档保留组件摘要，避免默认模板过长。

### 核心概念与业务抽象卡

核心概念卡 C-001：

- 概念名称：〈业务概念〉
- 语义类型：〈产品 / 商业供给 / 产品能力 / 业务主体 / 业务对象 / 业务流程 / 业务规则 / 业务状态 / 业务指标 / 交互载体 / 协议 / 技术机制〉
- 一句话定义：〈它是什么，用一句产品语言说明〉
- 适用范围：〈在哪些场景、对象、流程或规则中使用〉
- 不等于：〈容易混淆但不是它的概念、功能、对象或技术字段〉
- 术语/系统别名：〈业务别名、运营说法、英文名、API/字段名，按需填写〉
- 关联项：〈关联需求ID、对象、规则编号、验收种子ID或待确认项〉
- 替代、退役或复审条件：〈何时替代旧概念、停止使用或重新确认〉
- 可靠性标记：已确认 / 假设 / 待确认 / 不适用

概念责任、外部来源和业务对象状态继续进入对应责任、外部事实和状态章节；核心概念卡不复制这些治理字段。

业务抽象卡 A-001：

- 抽象名称：〈能力、对象、规则或关系抽象〉
- 抽象目的：〈把哪些业务现象、角色动作或规则差异归一，为什么需要抽象〉
- 归属边界：〈属于哪个业务主体、能力域、流程阶段或系统交接面〉
- 关键关系：〈与用户、主体、对象、状态、规则、数据或外部参与方的关系〉
- 生命周期/状态锚点：〈是否有创建、变更、冻结、关闭、失效、回滚等状态〉
- 不变量：〈任何实现、页面或流程都不能破坏的业务约束〉
- 不抽象范围：〈本期不归一、不平台化、不泛化的内容，防止过度抽象〉
- 验收/交接：〈关联验收种子、架构交接项、待确认项或专项附录〉

产品 DNA 卡 D-001：

- 核心对象：〈围绕哪些业务对象提供价值，它代表什么事实、不代表什么〉
- 业务不变量：〈任何页面、流程、规则、实现都不能破坏的业务事实〉
- 生命周期 / 状态：〈创建、变更、冻结、完成、失败、取消、归档及禁止流转〉
- 责任边界：〈本产品负责 / 合作方负责 / 外部系统负责 / 人工运营负责 / 本期不做〉
- 演化规则：〈新增角色、渠道、策略、规则、状态或上下游协作时如何扩展〉
- 验收方式：〈关联 AC、流程图、状态机、规则卡、数据口径、运营后台、审计或架构交接〉
- 可靠性标记：已确认 / 假设 / 待确认 / 不适用

## 精简输出规则

- 默认不展开文档控制、完整状态机、字段字典、规则矩阵、权限矩阵、非功能、发布运营和金融资金全表。
- 默认不强制每份 PRD 生成图片；多角色、多对象、多状态、多团队交接或高风险评审时，至少选择一张关键图帮助建立共同理解。
- 命中多团队协作、高风险、强合规、生产发布、用户明确要求或正式评审时，再展开相关附录。
- 主文档优先用短段落讲清因果，用项目符号和编号流程帮助扫读；重复条目才使用卡片，历史过程和明细矩阵移入附录或执行计划。
- 表格只用于比较、矩阵或追踪；单个问题、规则、验收和待确认项优先用段落或列表。
- 复杂并不等于写长，必须让评审者能在 5 分钟内看懂背景、目标、定性、总体方案、关键流程、规则、风险和验收摘要。
- 最终 PRD 不保留“第一版/第二版怎么改”“某角色建议过什么”“哪些方案曾被讨论后拒绝”等过程内容；只在必要时用一句当前结论或链接指向过程记录。

## 质量门禁指针

- PRD 进入正式评审前运行 `python3 product-architecture-expert/scripts/check_product_qualification.py --file <PRD.md>`，只验证定性与概念定义结构；通过不代表业务分类正确。
- 正式评审、提交前检查、CR、触发验证或符合性评审时读取 `product-prd-quality-gates.md`。
- 涉及支付资金、账户账本、清结算、对账、银行卡、ACH、VCC、跨境或金融合规时协同 `payment-expert`。
- 涉及运营后台、通知、数据指标、埋点、报表、导出或发布后验证时读取 `product-prd-operations-and-data.md`。
