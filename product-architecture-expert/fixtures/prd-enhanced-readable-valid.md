# 外部资质审核产品设计

当前版本：1.0。
文档状态：评审中。
文档强度：增强；依据：涉及外部版本规则、专业确认、不可错误放行和跨角色人工承接。
产品 owner：资质审核产品负责人。
业务 owner：资质运营负责人。
更新时间：2026-09-01 10:00 +08:00。
权威来源：本文件；外部规则以专业 Owner 确认的版本记录为准。

## 阅读摘要

- 当前结论 / 为什么现在：外部资质规则版本不一致会造成错误放行，本期统一版本化审核和待专业确认路径。
- 产品定义 / 产品架构主脊：降低错误放行风险 -> 提交与规则失效两个场景 -> 版本裁决和专业确认能力 -> 资质申请 / 规则版本及状态 -> R-EXT-001 -> 可追踪结论。
- 本期承诺 / 非目标：承诺保存申请、裁决所用版本和审核结论；不提供监管解释或替代专业审批。
- 主链路 / 异常承接：提交、版本校验、裁决、通知；规则失效或来源不可用时转资质专业 Owner。
- 关键待确认 / 责任与来源：外部规则来源、生效范围和版本由资质专业 Owner 确认；未确认时保持待专业确认且不得形成通过或驳回结论。

## 一、背景与问题

不同运营人员使用的外部资质规则版本不一致，平台无法说明某次通过结论基于哪个版本。错误放行会产生高失败成本，现有处理也缺少规则失效后的统一承接入口。

## 二、目标与非目标

目标是让每个审核结论都能追溯到有效规则版本，并在版本失效时停止自动裁决。非目标是不解释外部政策、不替代专业 Owner。成功指标：缺少规则版本的结论比例按“未保存有效版本引用的通过或驳回结论数 / 全部通过或驳回结论数”计算；当前基线为上线前连续 30 天审核审计记录中的 12%，上线 30 天内目标降至 0%，观察窗口为上线后连续 30 天，Owner 为资质运营负责人。

## 三、定性与范围

- 定性对象：业务流程。
- 本期变化：风险约束。
- 责任边界：平台执行已确认规则并保存事实，资质专业 Owner 解释和确认外部规则，运营承接待确认申请。
- 范围：资质申请、规则版本、审核结论和人工确认；不覆盖监管解释、历史结论重算或通用规则平台。
- 架构：申请与规则版本分离；通过或驳回结论必须引用有效版本，待补充、待专业确认和已停止均不等于审核结论。
- 取舍：先支持一个资质类型和一个专业确认组；出现第二类已确认规则后再复审共性。

## 四、概要设计

- 方案概述：平台先校验规则版本，再让审核员依据有效版本形成结论；无法确认版本时进入专业确认。
- 产品架构主脊：降低错误放行风险 -> SCN-001 / SCN-002 -> 版本裁决 / 专业确认 -> 申请和规则版本状态 -> R-EXT-001 -> 可追踪结论。
- 核心能力：申请受理、版本选择、规则裁决、待专业确认、通知和审计查询。
- 核心对象与关系：资质申请处于待审、待补充、待专业确认、通过、驳回或已停止之一；规则版本处于有效、失效或待确认之一；只有通过或驳回结论保存有效版本引用。
- 核心概念：待专业确认；定义：规则适用性尚未被专业 Owner 确认的申请状态；不是什么：审核通过；归属主体：平台。
- 关键交互与边界：审核员只裁决材料完整且版本有效的申请，平台阻止无有效版本形成通过或驳回，专业 Owner 确认规则，运营承接升级和通知。
- 方案取舍：不建设规则编辑器；当前版本只消费专业 Owner 发布的版本事实。
- 关键图 / 不画图理由：下方状态机用于说明申请状态及其与规则版本的迁移约束；规则版本自身状态由专业 Owner 的版本记录持有。

## 五、详细设计

场景关系：分支。材料完整且有有效版本才进入 SCN-001，材料不足先进入待补充，版本失效或不明时进入 SCN-002。

### 申请状态机

```mermaid
stateDiagram-v2
    [*] --> 待审
    待审 --> 待补充: 材料不完整
    待补充 --> 待审: 材料补齐并重新校验
    待审 --> 待专业确认: 版本失效、来源不可用或范围不明
    待专业确认 --> 待审: 专业 Owner 发布适用且有效的版本
    待专业确认 --> 已停止: 专业 Owner 明确无法确认且通知已收口
    待审 --> 通过: 材料完整、权限有效、版本有效且裁决通过
    待审 --> 驳回: 材料完整、权限有效、版本有效且裁决驳回
```

通过、驳回和已停止是终态，不得回到待审；待专业确认期间不得形成通过或驳回。迁移条件以 R-EXT-001 和对应场景为准，图不新增独立规则。

### SCN-001 使用有效版本审核

- 业务情境：审核员处理待审申请，平台已取得适用且有效的规则版本，需要形成可追踪结论。
- 责任推进：平台展示版本和材料，审核员裁决，平台保存结论、版本、操作者和时间，运营通知申请方。
- 裁决与状态：依据 R-EXT-001，申请由待审变为通过或驳回；结论必须引用本次有效版本。
- 异常与收口：材料不足时进入待补充且不形成审核结论；材料补齐并重新校验后回到待审。结论和版本引用可查询，且通知送达，或通知失败已留痕并由运营接管重试，才完成本轮收口。

### SCN-002 规则失效转专业确认

- 业务情境：审核员处理待审申请，但规则版本已失效、来源不可用或适用范围无法确认。
- 责任推进：平台停止自动裁决并把申请交给资质专业 Owner；运营告知申请方当前仍在处理中。
- 裁决与状态：依据 R-EXT-001，申请进入待专业确认，不得形成通过或驳回结论；专业 Owner 发布适用且有效的版本后，申请才能回到待审并重新进入审核。
- 异常与收口：人工 SLA 从进入待专业确认时起算，资质专业 Owner 应在 4 个工作小时内接单，并在 8 个工作小时内发布适用且有效的版本或明确无法确认；4 小时未接单时告警资质运营负责人，8 小时无结论时保持待专业确认并升级，不得自动形成审核结论。无法确认时进入已停止；通知送达，或通知失败已留痕并由运营接管重试，才完成收口。

### 跨场景端到端流程

1. 平台受理申请并校验材料、权限和候选规则版本；材料不足时进入待补充，不形成审核结论。
2. 材料完整、权限有效且版本有效时进入 SCN-001，由审核员裁决并保存版本引用。
3. 版本失效、来源不可用或范围不明时进入 SCN-002，申请转待专业确认。
4. 专业 Owner 发布适用且有效的版本后，平台记录版本事实并让申请回到待审；材料未变化且仍在有效期内可以沿用，否则转待补充。无法确认时进入已停止并通知申请方。

### 产品接口抽象

- 产品接口名称：资质申请裁决。
- 接口使用方：审核员和资质专业 Owner。
- 接口输入与前置条件：待审申请、材料、权限和候选规则版本。
- 接口业务输出与副作用：材料完整、权限有效且版本有效时形成通过或驳回，并保存有效版本引用和审计记录；材料不足时形成待补充，版本无效或不明时形成待专业确认，二者都不产生审核结论。
- 接口失败语义：版本无效、来源不可用或适用范围不明时不得形成通过或驳回并转专业确认；通知失败时审核状态不变，记录失败并生成运营重试任务。
- 接口责任边界：平台执行并保存状态、版本和通知事实，专业 Owner 在 4 个工作小时内接单并在 8 个工作小时内给出版本事实，运营负责超时升级和通知失败重试。

## 七、数据、权限、风险与待确认

数据记录申请状态、结论、版本引用、操作者、状态时间、专业接单时间、版本确认时间、告警和通知结果，不记录外部规则全文。审核员只能裁决材料完整、权限有效且版本有效的待审申请；专业 Owner 可以发布版本事实；运营只能查询、升级和重试通知。外部来源、生效范围和最终版本为待确认项，Owner 为资质专业 Owner，评审结束前未确认则保持待专业确认且不得形成通过或驳回。人工确认 SLA 为 4 个工作小时内接单、8 个工作小时内给出版本事实或无法确认结论。

## 八、验收摘要

对应场景：SCN-001、SCN-002。

- 正常结果：材料完整、权限有效且版本有效时形成通过或驳回，结论、有效版本引用、操作者和时间可查询。
- 边界结果：材料不足转待补充；版本到期、来源不可用或范围不明转待专业确认；两种状态都不产生审核结论。
- 禁止结果：无有效版本不得形成通过或驳回，待专业确认不得跳过待审直接进入终态。
- 失败后的可观察状态：待专业确认显示承接 Owner、进入时间和 SLA 截止；通知失败保留审核状态、失败记录和运营重试任务。
- 恢复或人工处理：专业 Owner 发布适用且有效的版本后，申请回到待审；材料仍有效则沿用，否则进入待补充；无法确认则进入已停止。
- 数据、审计或运营证据：版本引用、操作者、状态时间、专业接单、告警、通知结果和重试任务可查询。
- 验收 Owner：产品、运营和资质专业 Owner。
