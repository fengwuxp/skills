# 产品专家业务表达、需求与规则能力增强设计

日期：2026-08-24
目标 Skill：`product-architecture-expert`
状态：设计已由 Owner 确认

## 一、目标与定性

本设计增强 `product-architecture-expert` 对业务表达、需求说明和业务规则描述的能力，使其能够把真实业务材料转化为业务可理解、研发可承接、测试可验证的产品语义。

产品专家继续作为单一产品语义能力，不新建 `business-requirements-author`、`business-rule-writer` 或其他平级 Skill。业务表达、需求和规则是同一产品职责中的三种契约，不是三个角色、三个流程或三份权威文档。

增强后的核心定性为：

> 产品专家把业务事实转成可共同理解、可裁决、可追踪、可验收的产品语义；业务表达说明事实与判断，需求规定需要实现的业务结果，规则规定业务活动必须遵守的约束或推导。

本设计不把模板完整、结构检查通过或 Agent 自述当作语义正确证据。

## 二、问题与证据

### 2.1 已知事实

- 现有 Skill 已形成 `语义 -> 目标 -> 角色 -> 能力 -> 对象 -> 流程 -> 规则 -> 验收` 主线。
- `product-prd-template.md` 已规定读者主线、业务场景、规则与验收摘要。
- `check_product_deliverable.py` 能检查 PRD 章节、场景字段、规则与场景引用、验收覆盖等结构事实。
- 现有业务架构专项行为评测已有重复响应、独立盲评和准入证据。
- 产品专家当前没有覆盖业务表达、原子需求和业务规则语义质量的独立行为评测。

### 2.2 已复现缺口

将有效 PRD fixture 的规则判断改成“按相关业务规则处理”后，当前检查器仍返回无缺失、无警告。这证明结构命中不能识别空洞、模糊或不可执行的规则表达。

现有规则结构还分散在三个位置：

- `product-architecture-methodology.md` 维护触发、动作、优先级、版本、例外和验收样例。
- `product-prd-template.md` 主模板维护规则性质、适用范围、状态、冲突和兜底。
- 同一模板的规则卡只维护对象、触发、判断、结果、验收和可靠性。

三套字段没有单一权威，导致不同任务可能产出不同完整度的规则。

### 2.3 根因

根因不是 PRD 模板章节不足，而是：

1. 业务表达、需求、规则、流程、执行机制和验收证据没有统一正名。
2. 模板、方法论和规则卡重复持有规则结构。
3. 确定性检查承担了结构验证，但缺少明显模糊表达和关键语义字段检查。
4. 业务表达、需求和规则没有独立行为证据，无法证明模型能在新场景中稳定应用这些规则。

## 三、设计原则

### 3.1 经世校准

- **察实**：先分事实、推断、待确认和范围外不做，不从用户愿望、页面、竞品或技术实现反推业务事实。
- **正名**：业务目标、业务表达、需求、规则、流程、执行机制和验收证据各守其名。
- **审时**：轻量需求使用短契约；只有复杂、跨团队、高风险或多规则冲突场景才升级为完整矩阵或决策表。
- **权衡**：增强现有 Skill，不安装外部 PM Skill，不创建平行权威。
- **行验**：先用负例、行为 fixture 和独立盲评证明歧义减少，再扩大准入范围。
- **知止**：脚本只检查可确定结构和明显反模式，不宣称自动理解业务正确性。

### 3.2 单一权威

`product-architecture-expert/references/product-design-and-prd.md` 是 Business Expression Contract、Requirement Statement Contract 和 Business Rule Contract 的唯一权威。

其它文件职责如下：

| 位置 | 职责 | 不再持有 |
| --- | --- | --- |
| `SKILL.md` | 触发、主流程、路由和红线摘要 | 三种契约详细字段 |
| `product-design-and-prd.md` | 三种契约、裁剪规则和验收边界 | 外部来源长说明 |
| `product-prd-template.md` | 面向使用者的 PRD 骨架和填写槽位 | 平行方法论和第二套规则定义 |
| `product-architecture-methodology.md` | 说明产品设计主线及何时使用契约 | 独立规则矩阵 schema |
| `product-prd-quality-gates.md` | 评审、读者走读和语义准出 | 生成模板正文 |
| `check_product_deliverable.py` | 确定性结构检查和有限反模式告警 | 业务正确性裁决 |
| behavior fixture | 证明新场景中的行为质量与克制 | 运行时产品事实 |

## 四、一体三契约

### 4.1 名相边界

| 名相 | 回答的问题 | 不得混入 |
| --- | --- | --- |
| 业务表达 | 事实是什么，问题为何成立，影响谁，产品建议什么 | 未确认事实、实现细节、营销口号 |
| 产品需求 | 在什么条件下，哪个主体必须得到什么业务行为或结果 | 规则来源推断、技术实现方案 |
| 业务规则 | 业务活动必须遵守什么约束、许可、禁止或推导 | 流程顺序、执行代码、规则引擎设计 |
| 业务流程 | 参与者按什么顺序行动和交接 | 隐藏在步骤里的未命名规则 |
| 执行机制 | 系统如何实现、存储、传输和恢复 | 产品专家提前设计的技术方案 |
| 验收证据 | 如何证明需求和规则已满足 | “测试通过”等无证结论 |

### 4.2 Business Expression Contract

业务表达用于把访谈、会议纪要、用户反馈、原型、历史 PRD 和运营材料转成目标读者能够作出判断的产品语言。

最小字段：

```text
目标读者 / 需要作出的判断：
已确认事实 / 来源：
真实问题 / 影响对象 / 代价：
产品判断 / 推荐方案 / 适用边界：
本期承诺 / 非目标：
推断 / 待确认 / Owner / 未确认前处理：
```

表达规则：

- 事实先于判断，判断先于决策，决策先于承诺和验收。
- 优先使用主动责任句：“谁在什么条件下做什么，产品产生什么可观察结果，失败后谁承接”。
- 不用“进行处理”“相关方负责”“按相关规则”“视情况”“及时”“合理”等表达隐藏主体、条件、尺度或责任。
- 技术问题优先翻译成业务问题。例如，不先问“幂等键是什么”，而问“同一请求重复提交时，应新建、拒绝还是返回原结果”。
- 业务表达服务产品语义，不承担营销文案、品牌文案或正式报告润色。

### 4.3 Requirement Statement Contract

一条产品需求只表达一个外部可见业务事实、质量要求或约束。最低字段：

```text
需求名称：
需求类型：功能 / 质量 / 约束
责任主体：
场景 / 前置状态：
规范强度：必须 / 不得 / 应 / 可
要求的行为或业务结果：
度量、时限或边界：
来源与可靠性：
关联规则：
验收样例：
```

规范强度定义：

| 术语 | 含义 | 使用约束 |
| --- | --- | --- |
| 必须 | 绝对要求 | 不满足即需求失败 |
| 不得 | 绝对禁止 | 出现即触发失败或红线 |
| 应 | 默认要求 | 偏离必须说明理由、影响和批准方 |
| 可 | 允许但非必需 | 不得被研发或测试解释为必须 |
| 建议 | 非规范性指导 | 不进入正式需求或验收判定 |

需求质量按价值和风险裁剪，但 P0/P1、跨团队、外部契约或高风险需求必须检查：

- 适切：描述真实且已同意的利益相关者需要。
- 必要：能回到问题、目标、风险或外部约束。
- 原子：一个主体、一个主要谓词、一个可判定结果。
- 无歧义：主体、条件、范围、单位、时区、次数和例外只有一种合理解释。
- 自包含：理解本条需求不依赖作者口头补充。
- 可理解：业务、产品、研发和测试共享同一含义。
- 可验证：存在可观察结果、度量或人工确认方式。
- 可追踪：能回到来源，并向前连接场景、规则和验收。

EARS 只作为复杂状态、事件、可选条件和异常行为的可选受控表达，不要求所有需求使用固定英文句式，也不把 EARS 形式完整等同于需求正确。

### 4.4 Business Rule Contract

业务规则是基于业务术语和事实，对业务行为施加的声明式约束、许可、禁止或推导。规则独立于流程和执行机制；流程引用规则，执行机制实现或执行规则。

简单规则最低字段：

```text
规则名称：
规则性质：不变量 / 场景裁决 / 派生计算 / 版本化或外部规则
业务动机：
适用对象与范围：
输入事实：
当：
则：
Owner：
正例 / 边界例 / 反例：
```

命中以下任一条件时增加完整字段：

```text
规则编号：
允许 / 禁止 / 必须：
状态变化 / 业务副作用：
优先级 / 命中策略：
例外规则引用：
异常 / 外部不可用 / 人工兜底：
来源：
版本：
生效期 / 适用法域或主体：
未确认前处理：
审批 / 灰度 / 回滚 / 历史追溯：
```

升级条件：

- 多条规则可能同时命中。
- 规则存在优先级、排他、首条命中、全部命中或聚合结果。
- 规则来自外部政策、合同、监管或会变化的业务版本。
- 规则影响资金、审批、身份权限、关键状态、合同结果或不可逆动作。
- 例外可能改变正常结论。

多输入、多输出或存在规则重叠时使用决策表；决策表至少声明输入、输出、规则行、命中策略，以及默认结果或明确的无匹配处理。不为简单规则强制使用 DMN 或规则引擎。

例外必须写成可追踪的规则或明确的人工裁决门禁，不得写成“特殊情况另行处理”。

### 4.5 Rule-Example-Question Mapping

需求或规则存在歧义、高风险或跨团队争议时，按最小映射澄清：

```text
业务场景 / 需求：
规则：
正例：
边界例：
反例 / 禁止结果：
未决问题 / Owner / 未确认前处理：
```

该映射用于澄清和验收种子，不要求安装 Cucumber、采用 Gherkin 或建立新的过程文档。正式 PRD 只吸收已确认规则和必要例子，讨论过程留在评审记录。

## 五、PRD 模板增强

### 5.1 主结构

增强后的 PRD 读者主线为：

```text
1. 背景、问题与证据
2. 目标、非目标与成功标准
3. 产品定性、主体与范围
4. 概要设计
5. 详细设计
   5.1 业务场景
   5.2 产品能力与核心对象
   5.3 产品需求陈述
6. 主流程、异常流程与人工流程
7. 业务规则与产品接口抽象
8. 数据、权限、运营、风险与待确认
9. 验收摘要与产品到架构交接
```

模板仍按人的理解顺序组织，不把追踪矩阵、验证命令、Agent 控制字段或任务状态提前到主阅读路径。

### 5.2 详细设计增强

`5.3 产品需求陈述` 使用 Requirement Statement Contract。单条或少量需求优先用结构化段落；只有多需求需要横向比较、跨文档追踪或版本治理时才使用表格和稳定 ID。

需求表格最多保留：

```text
需求 ID / 类型 / 主体与条件 / 规范强度 / 行为或结果 / 边界 / 来源可靠性 / 验收引用
```

表格过宽时按业务场景分组，不缩短关键语义以追求单表完整。

### 5.3 业务规则增强

`7.1 业务规则` 直接引用 Business Rule Contract。删除现有规则卡中的平行缩水结构，统一为简单规则卡和条件升级字段。

规则少且无冲突时使用短规则卡；规则重复、需要比较或存在冲突时使用规则矩阵；多输入、多输出和命中策略复杂时才使用决策表。

### 5.4 验收摘要增强

每个核心场景至少说明：

```text
正常结果：
边界结果：
禁止结果：
失败后的可观察状态：
恢复或人工处理：
数据、审计或运营证据：
验收 Owner：
```

完整 Given / When / Then、测试映射、验证命令和执行状态继续进入执行计划或 `requirement-acceptance-testing`，不塞入 PRD 主阅读路径。

### 5.5 文档强度

| 强度 | 最小要求 | 条件升级 |
| --- | --- | --- |
| 轻量 | 背景、目标范围、一个场景、原子需求、适用规则和验收摘要 | 允许合并相邻章节；无独立规则时与需求合并，不强制规则卡、ID、矩阵或图 |
| 标准 | 阅读摘要、场景、需求陈述、对象状态、核心规则、异常人工、验收摘要 | 多主体、多状态或跨团队时增加最小关键图和追踪 |
| 增强 | 标准全部内容，加外部规则版本、规则冲突、命中策略、专业确认和完整风险 | 高风险规则使用决策表、完整验收与变更影响 |

高风险需求不得以轻量模板规避规则来源、Owner、例外、验收或专业确认。

## 六、检查器与验证边界

### 6.1 确定性检查

`check_product_deliverable.py` 继续持有结构检查，并增加有限语义反模式识别。

可程序化检查：

- 标准 / 增强 PRD 是否存在产品需求陈述。
- 正式需求是否能发现主体、条件、规范强度、行为结果和验收引用。
- 规则是否声明性质、适用范围、条件、结论和 Owner。
- 版本化 / 外部规则是否声明来源、版本、生效范围和未确认前处理。
- 规则引用、例外引用、场景引用和验收引用是否指向已定义项。
- 决策表是否有输入、输出、命中策略，以及默认结果或明确的无匹配处理。
- 正式需求或规则是否出现明显模糊词。

首批模糊词：

```text
相关 / 适当 / 及时 / 合理 / 必要时 / 视情况 / 原则上 / 尽快 / 通常 / 等等 / 包括但不限于 / 按相关规则处理
```

处理方式：

- 普通低风险草案：输出可定位 warning，不把 warning 冒充业务错误。
- P0/P1、增强 PRD、高风险规则或正式提交前检查：缺少尺度、Owner 或例外处理时阻断。
- 若词语已在当前文档中被明确定义为量化口径，则不因字面命中阻断。

不可程序化裁决：

- 业务事实是否真实。
- 需求是否真的必要或最优。
- 规则结论是否符合业务、法律、合规或专业判断。
- 多个自然语言规则在所有可能输入下是否逻辑完备。
- 目标用户是否真正理解或接受方案。

### 6.2 Fixtures

保留现有 PRD 正反 fixture，并补充：

- 有效：业务表达、原子需求、简单规则、规则冲突决策表和验收摘要。
- 无效：空洞规则“按相关业务规则处理”。
- 无效：复合需求同时包含多个主体、条件和结果。
- 无效：规则缺适用范围、Owner 或验收例子。
- 无效：外部规则缺版本、生效期或确认方。
- 无效：规则冲突但没有优先级、命中策略或人工裁决门禁。
- 无效：成功指标只有“提升效率”“体验更好”或“可观察”。

fixture 只证明检查器能识别预声明结构和反模式，不证明产品语义正确。

### 6.3 行为评测

新增 `product-business-expression-requirements-behavior-cases.json`，至少覆盖：

1. 会议纪要转业务可读需求，不把假设升级为事实。
2. 把技术问题翻译成业务决策问题。
3. 识别并改写“及时、合理、视情况”等不可验收需求。
4. 拆分包含多个行为和结果的复合需求。
5. 识别规则同时命中并要求优先级或命中策略。
6. 外部规则缺版本、生效期或 Owner 时保持 PENDING。
7. 小需求不扩成完整 PRD、全量规则矩阵或 DMN。
8. 纯营销文案、技术实现或测试代码任务不误触发本能力。

评测沿用同一 runner/model 的 baseline/candidate 重复响应、独立盲评和可复核指纹。评分至少检查：

- 事实与推断边界。
- 业务可读性和责任主体。
- 需求适切性、原子性、无歧义和可验证性。
- 规则独立性、声明性、冲突处理和版本边界。
- 克制性，不机械扩模板、不发明业务事实。

新行为 suite 在真实响应、盲评和准入证据完成前不登记为已证明能力。不得只刷新 source hash 或自填分数绕过证据门禁。

### 6.4 读者走读

标准 / 增强 PRD 准出前保留三方走读：

- 业务 / 产品 Owner 能复述为什么做、做什么、不做什么以及规则含义。
- 研发无需作者口述即可说明主体、条件、状态、规则、例外和产品边界。
- 测试 / 运营能推导正常、边界、失败、禁止结果和人工兜底。

任一方必须依赖作者口头补充才能形成一致理解时，先修正文、规则或图，不以评审评论替代正式产品结论。

## 八、实施顺序与停止条件

### 8.1 实施顺序

1. 在 `product-design-and-prd.md` 建立三种契约唯一权威。
2. 更新 PRD 模板并删除平行规则 schema。
3. 更新质量门禁和方法论引用。
4. 先写或更新负例，再修改确定性检查器。
5. 运行 product fixtures、frontmatter、引用、trigger path 和 `git diff --check`。
6. 增加行为 case，并验证 case contract。
7. 收集 baseline/candidate 真实响应，完成独立盲评后再更新 evidence gate。

### 8.2 停止条件

- 三种契约仍存在两个权威 schema：停止，不进入检查器修改。
- 新模板明显增加轻量 PRD 的无关负担：回退为按需字段，不强制展开。
- 模糊词检查产生大量合理表达误报：保持 warning 或缩小词表，不升级为硬阻断。
- 检查器开始判断业务正确性、法律适用性或产品价值：停止并退回结构边界。
- 行为评测没有显示歧义、遗漏或规则冲突处理改善：不登记新 evidence gate。
- 现有业务架构或客户端交互能力出现正确性、安全性回退：阻断准出。

## 九、验收标准

设计落地完成必须同时满足：

- 三种契约只有一个详细权威来源。
- PRD 模板存在业务表达、产品需求陈述、业务规则和验收摘要的可裁剪槽位。
- 轻量 / 标准 / 增强三种强度不会机械生成同一套章节。
- “按相关业务规则处理”不能在正式高风险规则中静默通过。
- 规则卡、规则矩阵和决策表使用同一语义字段，不再互相缩水或漂移。
- 有效 fixture 说明真实主体、条件、结果、Owner 和验收；负例按预期失败或告警。
- 结构检查输出明确声明不代表业务语义、专业审批或生产准入。
- 行为 case 覆盖正向、边界、硬负例和相邻能力路由。
- 真实行为证据完成前不宣称业务表达、需求或规则能力已经提升。
- 未安装、同步、发布或执行任何外部 Skill。

## 十、公开来源与吸收边界

核验日期：2026-08-24。

- [IREB CPRE Foundation Level Syllabus 3.3.0](https://hub.ireb.org/media/pages/resources/cpre-foundation-level-syllabus/9c084b1cfd-1787039954/cpre_foundationlevel_syllabus_en_v.3.3.0.pdf)：吸收需求适切、必要、无歧义、自包含、可理解、可验证，以及多需求一致、非冗余、可修改和可追踪等质量维度；不复制课程正文、图表或完整方法。
- [Business Rules Manifesto](https://www.businessrulesgroup.org/brmanifesto.htm)：吸收规则独立于流程、基于术语和事实、声明式表达、业务可校验和一致性检查；不复制正文，不引入规则引擎或形式逻辑依赖。
- [OMG DMN 1.5](https://www.omg.org/spec/DMN/1.5)：吸收决策、输入数据、知识来源、决策表和命中策略作为复杂规则的可选表达；不要求所有 PRD 使用 DMN，不绑定实现平台。
- [RFC 2119](https://datatracker.ietf.org/doc/rfc2119/)：只借用规范强度分级思路并转译为项目内中文约定，不宣称 RFC 约规直接适用于所有 PRD。
- [Cucumber Example Mapping](https://cucumber.io/docs/bdd/example-mapping/)：吸收故事、规则、例子和未决问题的澄清关系；不安装 Cucumber，不强制 Gherkin。
- [product-on-purpose deliver-prd](https://github.com/product-on-purpose/pm-skills/tree/main/skills/deliver-prd)、[deliver-acceptance-criteria](https://github.com/product-on-purpose/pm-skills/tree/main/skills/deliver-acceptance-criteria) 和 [deliver-edge-cases](https://github.com/product-on-purpose/pm-skills/tree/main/skills/deliver-edge-cases)：吸收 PRD、故事级验收和全功能边界场景的职责分离；不复制模板、示例或完整 Skill 包。
- [linyindong/platform-product-skills](https://github.com/linyindong/platform-product-skills)：吸收 PM Input Normalizer、业务语言提问、具体矛盾优先评审和 flow evidence 思路；未单独核验其许可证，不复制正文或实现，不安装仓库。
- [Microsoft hve-core requirements-author](https://github.com/microsoft/hve-core/tree/main/.github/skills/project-planning/requirements-author)：吸收需求、验收、目标和来源追踪，以及 EARS 作为可选受控表达；不复制其模板、阈值、状态机或完整治理流程。
- [mattpocock/skills to-prd](https://www.skills.sh/mattpocock/skills/to-prd)：只参考领域词汇和现有事实源优先；拒绝“不访谈直接合成”、自动发布 Issue 和自动加标签等会越过事实与外部写入授权的行为。

所有外部来源只作为能力设计证据，不是运行时依赖、事实权威、安装授权或准出证明。

## 十一、完成定义

本设计已关闭以下分叉：

- 增强现有 `product-architecture-expert`，不新建平级 Skill。
- PRD 模板同步增强，但不机械增加固定章节和全量表格。
- `product-design-and-prd.md` 持有三种契约唯一权威。
- DMN、EARS、RFC 规范强度和 Example Mapping 都是按需表达，不成为默认工具链。
- 确定性检查只覆盖结构和有限反模式，语义质量由行为证据与独立走读证明。
- 外部 Skill 只读借鉴，不安装、不复制、不自动写外部系统。

进入实施计划前需由 Owner 复核本规格；未获得后续实施授权前，不修改 Skill 正文、reference、script、fixture 或 evidence gate。
