# 可用性验证与 Design QA

## 使用时机

当任务需要证明 Web 界面的关键任务是否可完成，设计方案是否经得起目标用户使用，或实现结果是否符合已确认设计契约时读取。它承接设计 brief，不重新定义产品规则或视觉方向。

## 不适用场景

- 产品对象、规则、权限或成功标准尚未确认；先交回产品 Owner。
- 只需实现已确认设计且没有独立 Design QA 或可用性验证请求；由工程能力负责。
- 没有可运行实现、原型或真实内容，却要求宣称已验证可用或符合 WCAG。

## 读取后必须产出

- 当前证据等级、验证问题、目标用户、任务、方法和成功/失败口径。
- 可复核的观察记录、Design QA 证据、findings、复测条件和 Owner。
- 不能由本轮证据支持的结论与停止条件。

## 需要继续读取的 reference

- 设计 brief、状态和评审严重度读 `design-and-review-workflow.md`。
- 视觉、tokens 与内容韧性读 `design-foundations.md`。
- 具体业务页面模式读 `common-scenario-patterns.md`。
- WCAG 与 ARIA 依据和时效边界读 `source-map.md`。

## 一、先声明证据等级

证据可以逐级累积，不能跳级宣称：

| 等级 | 已有证据 | 可以说明 | 不能说明 |
| --- | --- | --- | --- |
| E1 设计契约 | brief、结构、状态和验收约束 | 设计意图可实现、可评审 | 真实实现或用户可用 |
| E2 可操作原型 | 可点击原型、真实内容样本和任务走查 | 主要交互假设可被检查 | 浏览器、读屏或生产行为 |
| E3 实现证据 | 浏览器中的桌面/移动、状态、键盘、焦点和错误恢复 | 当前实现满足已检查契约 | 目标用户普遍能成功使用 |
| E4 用户/运行证据 | 目标用户任务记录或上线观测 | 特定人群和场景下的真实表现 | 未覆盖人群、长期因果或完整合规 |

交付开头写明当前等级和证据来源。设计稿、自动扫描、截图、用户口头偏好和单个生产指标都不能单独升级证据等级。

## 二、按问题选方法

| 问题 | 方法 | 主要证据 |
| --- | --- | --- |
| 结构和反馈是否有明显缺口 | 启发式评审 | 规则、页面/组件位置、触发条件和任务影响 |
| 新用户能否知道下一步 | 认知走查 | 每一步看到什么、会尝试什么、反馈是否足够 |
| 目标用户能否完成关键任务 | 任务测试 | 完成、错误、恢复、求助、用时和原话 |
| 实现是否符合设计契约 | Design QA | 浏览器、状态矩阵、响应式、键盘/焦点、内容和控制台证据 |
| 上线后问题是否持续存在 | 运行观察 | 漏斗、失败、回退、支持请求与定性反馈的联合证据 |

方法由验证问题决定。专家评审适合先找明显问题，不能替代目标用户任务证据；满意度和点击量不能替代成功、错误与恢复。

启发式评审可用 Nielsen 十项可用性启发式统一分类：系统状态可见、贴近现实世界、用户控制与自由、一致性与标准、错误预防、识别而非回忆、灵活与高效、审美与最简、帮助识别诊断并恢复错误、帮助与文档。它们是宽泛评审镜片，不是标准、目标用户证据或严重度；finding 可记录命中项，P0-P3 仍由任务影响、发生条件和恢复成本决定。

## 三、任务型验证计划

最小计划包含：

1. **验证问题与假设**：要降低什么不确定性，什么观察会支持或反驳假设。
2. **目标用户与招募**：按角色、经验、频率、设备和可访问性需要定义；排除设计者和只熟悉内部术语的人。
3. **任务与起点**：给情境和目标，不提示控件位置；使用真实对象、权限、数据范围和主要失败条件。
4. **成功、失败与恢复**：完成结果、误操作、重复提交、求助、无法恢复和中止条件必须可观察。
5. **环境与协议**：原型/版本、浏览器、设备、权限、网络、样本数据、主持规则和记录方式保持可解释。
6. **隐私与安全**：取得必要同意，只收集完成判断所需数据；不使用真实密钥、客户数据或生产写操作做常规测试。

使用 `scripts/check_ui_design_deliverable.py --kind usability-plan --file <path>` 检查计划结构；通过不代表招募、执行或结论有效。

## 四、记录与判断

- 逐参与者记录起点、完成结果、关键路径、错误、恢复、求助、用时、信心和原话；先记观察，再写解释。
- 用时用于定位阻塞，不做参与者排名；满意度用于解释体验，不覆盖任务失败。
- 区分“发生次数”“涉及人数”“任务严重度”和“恢复成本”，不把一次观察直接写成普遍规律。
- 小样本适合发现问题和验证路径，不输出无依据的总体比例；生产指标需同时核对口径、分群、版本和其他变化。
- 发现与产品规则冲突时停止 UI 归因，交回产品 Owner；实现不一致时先归为 Design QA finding。

## 五、实现后 Design QA

| 维度 | 最小检查 |
| --- | --- |
| 契约 | 主任务、信息层级、术语、权限、主行动与危险动作符合已确认设计 |
| 交互 | hover、focus、active、disabled、loading、error、success、撤销与重复提交 |
| 响应式 | 代表性窄屏/宽屏、200% 缩放、软键盘、安全区、长词和大数 |
| 可访问性 | 语义、名称、键盘、焦点、状态通知、对比和减少动效；自动化只作部分证据 |
| 内容 | 空、短、典型、极长、本地化、用户生成内容和媒体失败 |
| 环境 | 目标浏览器、控制台错误、失败请求、慢网、超时、权限和会话过期 |

证据优先使用带视口和状态说明的截图/录屏、DOM 或可访问性树、键盘走查、控制台/网络记录和可复现步骤。像素差异只能说明视觉变化，不能证明语义、行为、状态或任务正确。

## 六、findings 与复测

沿用 `design-and-review-workflow.md` 的 P0-P3。每条 finding 写明：证据等级、页面/组件、触发条件、任务影响、预期与实际、复现步骤、最小修复、Owner 和复测范围。

修复后重跑原任务、原失败条件和受影响视口/输入方式；不能只看改后截图。存在以下情况时停止升级结论：目标用户不匹配、样本数据失真、关键状态未实现、记录不可复核、产品规则待确认，或修复尚未进入可运行环境。
