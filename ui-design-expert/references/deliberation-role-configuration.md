# UI 场景化角色合议

本文拥有 Web UI 设计中角色、站位和视角的专业场景包，单一 UI 任务直接使用本文并仍由 `ui-design-expert` 负责。由 `wise-agent` 主持时，主持方另从 `../../wise-agent/references/deliberation-role-configuration.md` 提供通用角色语义、`Discussion Role Matrix` 和决策权分离；使用本文本身不等于启动 `wise-agent`。

## 使用时机

- 用户显式要求围绕 UI 做角色讨论、多视角评审、合议或设计碰撞。
- 同一界面决策同时影响产品权限、用户任务、内容结构、交互状态、视觉系统、可访问性或实现约束，且这些责任存在真实取舍。
- 新界面、重设计、重要流程或 Design QA 需要明确不同证据位如何共同形成结论。

## 不适用场景

- 当前问题只是已确认设计系统中的局部 token、文案、间距或单一组件修复。
- 产品对象、规则、权限或成功口径未确认，继续讨论会发明业务事实；此时先返回产品 Owner 补证。
- 用户只要求实现已确认设计，没有重新设计或独立 Design QA 目标。
- 只是想模拟设计师、用户和工程师轮流说话，没有需要裁定的 `decision_questions`。

## 读取后必须产出

- UI `task_phase`、`interface_type`、`domain_object` 和 `decision_questions`。
- 按当前任务裁剪的 UI 工作位、站位、视角、依据、决策权和退出条件。
- 设计冲突的裁决顺序、当前证据等级、待确认 Owner 和验证方式。

## 需要继续读取的 reference

- 新界面、重设计、结构交互和设计评审读 `design-and-review-workflow.md`。
- 可用性证据等级、目标用户任务测试和实现后 Design QA 读 `usability-validation-and-design-qa.md`。
- 视觉、tokens、响应式媒体与元素意图读 `design-foundations.md`；可操作原型和 Figma 交接读 `prototype-output.md`。

## 一、两轴选择

角色由设计阶段和界面类型共同决定：

- `task_phase`：方向探索、结构与交互、视觉成形、设计评审或可用性 / Design QA 验证。
- `interface_type`：任务型、转化型、阅读型或展示型；沿用 `ui-design-expert` 的现有定义。

任务型界面优先重复操作效率、状态辨识、失败恢复和熟悉感；转化、阅读或展示界面可提高内容、品牌、叙事和视觉表达权重。不能把营销页面的角色组合套到运营后台，也不能把后台的信息密度原则机械套到品牌展示页。

## 二、候选工作位

| 工作位 | 站位 | 主要视角与证据 | 边界 |
| --- | --- | --- | --- |
| 产品语义边界位 | 保护已确认对象、规则、权限和成功口径 | PRD、规则、权限、验收与 Owner 决议 | 只消费产品事实，不重新定义产品 |
| 用户任务位 | 保护目标用户在真实情境中完成任务 | 场景、频率、设备、当前替代、错误与恢复 | 无用户材料时只标 `stakeholder_need / hypothesis` |
| 信息架构位 | 保护信息可发现、可扫描、可比较 | 层级、导航、命名、内容关系和阅读顺序 | 不用页面数量或卡片数量冒充清晰度 |
| 交互与状态位 | 保护端到端任务闭环 | 操作顺序、反馈、撤销、loading、empty、error、success、权限和弱网 | 不只设计理想成功态 |
| 内容责任位 | 保护真实内容、术语和决策所需信息 | 内容样本、数据范围、长短文本、本地化与空缺 | 不编造产品规则或生产数据 |
| 视觉与设计系统位 | 保护视觉层级、品牌和体系一致性 | tokens、排版、颜色、密度、组件、图像和动效 | 不用审美覆盖任务、安全和状态 |
| 响应式与可访问性位 | 保护不同视口、输入方式和能力人群的可达性 | 触控、键盘、焦点、语义、对比、缩放、溢出和减弱动效 | 静态稿不能证明实际可达 |
| 实现约束位 | 保护设计可实现且工程成本与现有体系相称 | 当前组件、浏览器、性能、内容韧性和状态成本 | 不替工程 Owner 改技术边界 |
| 验证位 | 保护完成声明与证据等级相称 | E1 设计契约、E2 原型、E3 实现、E4 用户或运行证据 | 不参与设计投票，不把专家意见冒充用户证据 |

工作位是候选池，不是固定评审委员会。每个工作位必须回到至少一个当前 `decision_question`；没有独特责任、证据或约束时不入场。同一人可以承担兼容工作位，但设计者不能同时作为独立验证位自证准出。

## 三、按阶段裁剪

| 阶段 | 优先工作位 | 默认跳过 |
| --- | --- | --- |
| 方向探索 | 产品语义、用户任务、内容、视觉方向，必要时实现约束 | 不提前展开完整状态矩阵或 Design QA |
| 结构与交互 | 产品语义、用户任务、信息架构、交互状态、内容、可访问性 | 视觉位只提供承重约束，不用润色替代结构 |
| 视觉成形 | 用户任务、内容、视觉与设计系统、响应式与可访问性、实现约束 | 不重开已确认产品规则和主流程 |
| 设计评审 | 与 finding 直接相关的责任位、挑战位和设计 Owner | 不让所有工作位逐项复述全部页面 |
| 可用性 / Design QA | 任务证据、设计契约、响应式与可访问性、浏览器实现、独立验证 | 不重新发明产品和视觉方向 |

例如高频运营工作台通常需要产品语义、用户任务、信息架构、交互状态、可访问性和实现约束；品牌活动页通常提高内容、品牌视觉、响应式、性能和目标受众的权重。只有当前问题真实涉及另一责任时才增加角色。

## 四、裁决顺序

UI 角色意见冲突时依次服从：

`已确认产品事实与权限 -> 用户任务、安全和危险动作 -> 状态、失败恢复与可访问性 -> 信息结构与交互 -> 视觉表达`

- 没有产品权威时不能由界面角色补造业务对象、规则、角色或权限。
- 用户偏好、专家判断、点击数据和单个访谈不能互相替代；每种证据保留适用范围。
- 视觉识别、品牌叙事和情绪可以是合法职责，但不得遮挡关键信息、伪造状态或破坏操作。
- 实现成本只能作为取舍证据，不能单独取消已确认的安全、权限、可访问性和必要状态。
- 分歧由设计或产品 `decision_owner` 按责任范围裁决；验证位只证明，不拍板。

## 五、输出与停止

若由 `wise-agent` 主持，使用通用 `Discussion Role Matrix`。单一 UI 任务可以压缩为：

```text
任务阶段 / 界面类型 / 决策问题:
工作位 / 代表对象 / 保护结果:
检查视角 / 依据 / 证据缺口:
主张 / 反证 / 不可接受结果:
decision_owner / checker_required 与依据 / 验证位（如需要）/ 停止条件:
```

- 角色讨论只输出影响设计决策的差异、裁决、待确认和验证，不输出逐角色表演稿。
- 只有证据支持的结论进入设计 brief、状态矩阵或视觉契约；争论过程留在评审载体。
- 没有真实分歧、只剩局部继承修复时退出角色讨论并直接处理。
- 缺少真实内容、用户证据、产品规则或可运行载体时，按证据等级停止，不宣称可用、符合 WCAG 或生产就绪。
