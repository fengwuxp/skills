# UI 设计与评审工作流

## 使用时机

当任务需要从用户目标形成 Web 或浏览器应用的界面设计契约，或对已有页面、组件、原型和实现做 UI/UX、响应式、可访问性与可用性评审时读取。

## 不适用场景

- 纯产品业务语义、PRD、业务规则或验收口径设计。
- 原生 iOS / Android 界面设计；应使用对应平台的设计规范与能力。
- 已确认设计的单纯 Figma-to-code、前端编码、源码 CR 或性能调优。
- 只要求生成或操作 Figma 文件且设计判断已经完成。

## 读取后必须产出

- 设计任务类型、事实边界和最小 brief。
- 信息架构、关键路径、状态矩阵、响应式和可访问性契约。
- 视觉方向或评审 findings，以及可复核的验证证据和停止条件。

## 需要继续读取的 reference

- 视觉基础、排版、tokens 和内容韧性读取 `design-foundations.md`。
- 数据工作台、搜索、表单、审批、设置和监控读取 `common-scenario-patterns.md`。
- 设计系统、组件库、无样式原语和开放代码方案读取 `ui-library-landscape.md`。
- 视觉风格或东方审美方向读取 `visual-style-directions.md`。
- 任务测试、证据等级和实现后 Design QA 读取 `usability-validation-and-design-qa.md`。
- 外部实践、版本、许可和吸收边界读取 `source-map.md`。
- 产品对象、业务规则和验收由 `product-architecture-expert` 的对应 reference 负责。
- 前端实现、源码 CR、测试和发布由 `senior-software-architect` 的对应 reference 负责。

## 一、任务与变更类型

先按界面上的成功方式分类：

| 类型 | 用户成功 | 设计优先级 |
| --- | --- | --- |
| 任务型界面 | 完成操作、判断或重复工作 | 扫描、比较、效率、状态清晰、熟悉的交互 |
| 转化型界面 | 理解价值并作出行动 | 证据、信任、叙事、主行动和真实资产 |
| 阅读型界面 | 找到并理解信息 | 层级、可读性、目录、搜索和连续阅读 |
| 展示型界面 | 浏览作品、对象或体验 | 内容先行、沉浸、节奏和媒介质量 |

再判断变更范围：

- 局部优化：继承产品语义、设计系统、组件和页面结构，只修当前问题。
- 体系扩展：保持现有视觉权威，补新页面、组件、状态和 tokens。
- 新界面：从已确认产品事实建立新的结构和视觉方向。
- 重设计：保留产品事实、内容、功能和约束，替换旧的结构或视觉体系；必须有明确授权。

## 二、最小 brief

稳定以下字段即可开始设计：

1. 用户与场景：谁在什么情境、频率、设备和注意力状态下使用。
2. 主任务与成功：必须理解或完成什么，失败后如何恢复。
3. 产品事实：对象、规则、权限、真实文案、数据和资产；设计不得自行补写。
4. 范围与非目标：目标页面/组件、保留项、禁止改动项和本轮不做。
5. 内容范围：空、短、典型、极长、大数、多项、不同语言和用户生成内容。
6. 关键状态：首用、默认、处理中、无数据、错误、成功、权限、弱网和人工兜底。
7. 约束：平台、视口、设计系统、品牌、性能、可访问性、本地化和交付格式。

信息足够时直接给出最可能的 brief 并标记假设；只有关键分叉会改变结果时才提问。

### 二 A、简单优先与过渡设计门禁

设计与原型默认服务一个当前可验证的任务闭环。先选择能回答当前问题的**最低原型层级**，收敛到最少页面 / 状态 / 组件和一条可走查的主路径；必要的失败恢复、权限、键盘、响应式和真实内容仍要覆盖，不能为了“简单”删掉任务成立所需的契约。

- 本轮范围只包含当前目标、成功结果和必要恢复路径；未来页面、角色、平台或技术路线先标为非目标、待观察或候选。
- **不为未来页面、角色或技术迁移预埋过渡结构**。只有迁移本身属于当前任务，且来源 / 目标、Owner、存续期限、移除条件和验证方式已确认时，才设计过渡层；否则保持当前页面与原型直接、可理解、可验证。
- 不以整站页面清单、完整设计系统、组件平台或多端矩阵制造“看起来完整”的交付。只有当前验证问题确实需要，且设计权威、内容、Owner 与验收输入足够时才扩展；扩展时同时写明本期切片与跳过项。

## 三、结构与交互

按“任务 -> 信息 -> 行动 -> 反馈 -> 恢复”设计：

- 信息架构：分组依据、层级、阅读顺序、导航、搜索、筛选和当前位置。
- 关键路径：入口、主要动作、必要输入、确认、结果和下一步；避免无意义的中间页与模态框。
- 行动层级：同一上下文只保留一个明确主行动；危险动作提供确认或可撤销窗口。
- 组件选择：优先平台和现有设计系统的熟悉模式；二元值用开关/复选框，模式用分段控件，选项集用菜单，工具按钮优先使用熟悉图标并提供名称。
- 反馈与恢复：处理中不重复提交，错误贴近原因并给下一步，保留用户输入，权限与网络失败提供可恢复路径。
- 可追踪状态：筛选、分页、tab 和可分享视图需要深链接时，将状态反映到 URL 或等价导航状态。

## 四、状态矩阵

每个重要组件至少检查适用状态，不机械要求无意义状态：

| 类别 | 状态 |
| --- | --- |
| 交互 | default、hover、focus、active、selected、disabled |
| 异步 | loading、progress、success、error、timeout、retry |
| 数据 | empty、partial、stale、overflow、large set |
| 权限 | unauthenticated、unauthorized、read-only、approval pending |
| 环境 | offline、slow network、safe area、virtual keyboard |
| 内容 | long text、CJK、RTL、text zoom、large number、locale formats |

状态说明必须覆盖用户看到什么、可以做什么、焦点去哪里、数据是否保留以及如何恢复。

## 五、响应式与可访问性

### 响应式

- 说明结构如何变化：列折叠、侧栏收起、表格替代视图、操作区换位和内容优先级，而不是只给断点数字。
- 固定格式元素使用稳定尺寸、`aspect-ratio`、grid tracks 或 min/max 约束，避免动态内容导致布局跳动。
- 验证窄屏、宽屏、软键盘、安全区、200% 缩放、长词和本地化扩展；不禁用浏览器缩放。

### 可访问性

- 默认以 WCAG 2.2 AA 为设计基线，记录适用成功准则；合同或项目要求更高时从其要求。
- 原生 HTML 优先于 ARIA；自定义 widget 按 ARIA Authoring Practices Guide 核对角色、属性、键盘和焦点。
- 所有功能可由键盘完成，焦点可见且顺序合理；打开、关闭和报错后的焦点移动有定义。
- 控件有可访问名称，图片有恰当文本替代；颜色、形状、位置和声音不作为唯一信息通道。
- 文本与非文本对比、触控目标、文本缩放、减少动效、错误识别和状态通知进入验证计划。
- 自动化检查只能发现部分问题；未经键盘、读屏或人工走查，不宣称完整符合 WCAG。

## 六、视觉系统

视觉方向必须能回答“为什么适合这个产品、受众和场景”：

- 先读取现有 tokens、组件、品牌资产和代表性页面；局部功能不新建视觉体系。
- 用排版、色彩、密度、间距、图像、图标和动效建立清晰层级；变量和 tokens 承载可复用决策。
- 需要系统化视觉基础时读取 `design-foundations.md`；需要东方审美时读取 `visual-style-directions.md`，不在本工作流复制风格清单。
- 任务型界面允许高信息密度、熟悉字体和标准导航，品牌通过克制细节表达；一致性高于惊喜。
- 转化与展示界面可以更有识别度，但真实产品、地点、对象或人物应在首屏可见，不能用纯装饰代替内容证据。
- 新建或重设计转化、展示界面时，对照同品牌或上一产物的结构指纹：首屏对齐与尺度、导航、区段顺序与节奏、内容宽度、证据顺序和 CTA 位置。记录刻意继承项与差异项；差异必须回指受众、内容、行动或真实资产，不能只做配色或字体换皮，也不随机套结构目录。任务型界面不为多样性改造熟悉结构。
- 动效只用于状态、空间关系、反馈或有明确价值的叙事；支持 `prefers-reduced-motion`，不让用户等待装饰动画。
- 避免无语境的紫色渐变、卡片套卡片、装饰性圆球、过度圆角、营销式大标题和模板化构图；这些是诊断线索，不是脱离品牌事实的绝对禁令。

## 七、交付契约

按任务规模交付最小集合：

```text
设计结论：
事实 / 推断 / 待确认：
用户、场景与主任务：
范围 / 非目标 / 继承项：
信息架构与关键路径：
状态矩阵与失败恢复：
响应式与可访问性：
视觉系统约束：
实现不可自行决定项：
验证证据与停止条件：
```

设计稿或 Figma 不是唯一契约；工程交接必须能从文字、状态和行为说明判断实现是否正确。

## 八、评审路径

评审先读需求、设计权威、实现和当前可见状态，再按严重度输出 findings：

- P0：关键任务不可完成、数据损失、权限误导或严重可访问性阻断。
- P1：主要路径高概率失败、错误不可恢复、移动端不可用或核心信息不可理解。
- P2：状态缺失、层级混乱、一致性问题或明显降低效率。
- P3：不影响任务的细节、润色或机会项。

每条 finding 包含对象/位置、触发条件、用户影响、证据和最小修复方向。主观偏好没有产品、用户、系统或标准证据时，不作为缺陷。候选只有同时通过三段证明才成为 finding：

- **Contract**：当前范围存在有约束力的设计决定，或同一任务表面存在直接可观察的内容 / 表现矛盾；偏好、命名相似、重复出现和未写例外都不单独构成契约。
- **Runtime**：通过渲染、导入、props、已解析配置、CSS 继承或真实生成产物，证明该 owner、token、variant 或行为确实到达被审表面；目录相邻或同名不能证明运行关系。
- **Correction**：证据唯一支持一个最小修复，并能指向现有 token、variant、primitive 或明确内容。若仍有多个同等方案、需要发明产品意图或不知道正确值，降为候选 / 待确认。

报告前执行一次**反证复核**：重开引用来源，检查规则是否真的约束该属性和表面、差异是否为已批准例外、运行关系是否成立、修复是否唯一，以及是否与其它 finding 同根。任一项失败就删除或合并，不为凑数量保留。

### 八 A、快速只读体检

只在用户要求对现有 Web 页面、原型或实现做一轮窄范围检查，且本轮不修改源码、Figma、tokens 或设计系统时使用。先读取真实页面任务、设计权威和当前可见状态；按实际可得的浏览器、截图、Figma 或源码记录**证据面**。只有源码时，只检查语义元素、明显交互反模式和其它高置信规则；浏览器布局、移动端、键盘焦点、可用性和视觉判断保持 `blocked / cant-tell`。

体检只覆盖会改变当前任务判断的层级与阅读顺序、间距和排版、布局稳定与内容韧性、适用状态与失败恢复、可访问性基础、动效目的与性能风险。紫色渐变、圆角、发光、大标题、留白和动效时长只是诊断线索，不把风格线索当成脱离语境的绝对缺陷；已有品牌或任务依据时维持现状，只有抢占主要判断、制造错误关系、破坏性能或可访问性时才形成 finding。

输出沿用 P0-P3，只给 finding、证据面和最小修复方向；没有发现时说明剩余验证缺口。快速体检不替代新界面 / 重设计、完整任务测试、WCAG 准出、代码实现或发布验证；metadata / SEO、Open Graph、canonical 和 JSON-LD 属于网站或工程任务。需要修改实现时，先取得写入授权，再把设计结论交 `senior-software-architect` 执行和验证。

## 九、验证矩阵

| 目标 | 最小验证证据 |
| --- | --- |
| 关键任务 | 从入口到成功及主要失败恢复的真实走查 |
| 布局 | 桌面与移动截图、无重叠/截断、真实内容范围 |
| 交互 | hover/focus/active/disabled/loading/error 等适用状态 |
| 键盘与焦点 | Tab 顺序、可见焦点、dialog/menu 等模式的进入与退出 |
| 可访问性 | 自动扫描 + 关键路径人工检查；需要时读屏验证 |
| 响应式 | 代表性窄屏/宽屏、200% 缩放、软键盘和安全区 |
| 韧性 | 空数据、长文本、大数、本地化、弱网、超时和权限失败 |
| 一致性 | tokens、组件、图标、术语和相同动作的跨页面对照 |

浏览器可用时优先用 Playwright 或等价工具批量采集桌面/移动证据并检查控制台；需要真实设计评审时仍由人工或独立 Checker 复核。没有运行环境时明确这是设计级或源码级结论，不升级为可用性已验证。

需要验证目标用户能否完成任务或核对实现是否符合设计契约时，继续读取 `usability-validation-and-design-qa.md`；专家评审、自动检查和截图不能替代目标用户证据或实现状态证据。
