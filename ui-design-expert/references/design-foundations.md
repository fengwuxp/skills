# UI 设计基础

## 使用时机

当任务需要建立或审查 Web 界面的视觉基础、tokens、排版、布局、图像、动效或内容韧性时读取。局部改动先服从项目现有设计系统，不借本文件发起无关重设计。

## 不适用场景

- 只需梳理产品对象、业务规则或验收口径。
- 已有设计定稿且本轮只做工程还原。
- 需要选择具体设计系统或组件实现；此类任务继续读 `ui-library-landscape.md`。

## 读取后必须产出

- 本轮继承、调整和禁止改动的视觉基础。
- 可落到 design tokens、组件状态和内容范围的设计约束。
- 桌面与移动、键盘与焦点、长内容和真实数据的验证方式。

## 需要继续读取的 reference

- 页面与任务流读 `design-and-review-workflow.md`。
- 常见业务界面读 `common-scenario-patterns.md`。
- 视觉风格与东方审美读 `visual-style-directions.md`。

## 一、层级、布局与空间

- 先用阅读顺序、任务顺序和分组关系建立层级，再使用字号、字重、颜色和空间强化；不靠卡片边框解决所有分组。
- 先区分注意顺序与操作顺序，再用大小、颜色、位置、对比和留白建立视觉权重。最醒目的不一定是主按钮，而应是当前任务首先需要判断的信息；确认页先显露待核对的金额、对象或风险，再让主行动清楚可达。
- 布局、栅格与留白表达对象关系。留白应帮助定位、阅读或转换任务，不以大面积空白牺牲数据扫描和重复操作效率。
- 使用稳定的 grid tracks、min/max、容器宽度和 `aspect-ratio` 约束固定格式元素；真实内容进入后不能因标签、数字或状态变化造成无意义位移。
- 密度由任务频率、比较需要、设备和注意力决定。后台工作台可以紧凑，阅读和展示页可以舒展，但关键操作与状态始终清楚。

## 二、排版与中英文混排

- 先定义正文、标题、标签、数据和代码等角色，不用大量字号制造层级。紧凑面板使用紧凑标题，真正的首屏叙事才使用展示字号。
- 中文正文优先可读的系统或已授权字体；建立 CJK、Latin、数字和符号回退链，核对字体许可、加载失败和字形缺失。
- 中文不依赖负字距压缩；正文行高、行长、段距和断行按真实文本验证，避免长段居中、孤行、标点挤压和最长词溢出。
- 财务、统计和比较场景可按项目字体能力使用等宽数字；金额、小数位、千分位、负数、单位和时区必须在真实数据下对齐。
- 文案是设计材料：标签说明对象，按钮说明动作，错误说明原因与下一步；图标按钮仍需可访问名称。

## 三、颜色与 tokens

- 先复用现有语义化 design tokens；新体系至少区分背景、表面、文本、边界、主行动、焦点、危险、警告、成功和数据序列等角色。
- token 名称表达用途而非当前颜色，例如 `text-danger` 优于 `red-600` 作为组件契约；主题切换改变值，不改变语义角色。
- 颜色不能成为唯一信息通道。状态同时使用文字、形状、图标或位置关系，并验证文本、非文本和焦点对比。
- 品牌色不自动等于主按钮色，装饰色不自动等于数据色。数据可视化需要检查相邻序列、色觉差异、打印和高对比模式。
- 主题定制优先调整全局或组件 token；不要在页面层叠加无法追踪的十六进制值和选择器覆盖。
- 只有跨工具交换或新建 token 基础确有需要时采用 DTCG v2025.10；用 `$type`、`$value`、别名、分组和扩展描述格式契约，组件仍消费项目的语义别名。
- DTCG 是交换格式，不是命名、Owner、版本、弃用或质量治理方案，也不是 W3C Standards Track；现有 token 体系稳定时不为形式一致发起迁移。

## 四、图像、图标与动效

- 图像应展示真实产品、对象、地点、人物或状态。需要用户判断对象时，不用模糊、过暗、过度裁切或纯氛围素材代替证据。
- 同一动作使用同一图标和名称；熟悉图标可独立显示但仍提供名称，不熟悉或高风险动作使用图标加文字。
- 动效只解释状态、反馈、空间关系或叙事变化；持续时间、打断、重复和等待成本必须与任务相称，并支持 `prefers-reduced-motion`。
- 阴影、圆角、材质和纹理只在表达层级、对象属性或品牌事实时使用，不作为“精致感”默认添加。

### 视觉元素意图审查

- 先单独写出 `页面任务 | 首要判断 | 信息优先级 | 目标受众 | 目标视口 / 设备`，再逐项记录 `元素 | 承担的信息或操作 | 对象 / 状态 | 依据 | 受众 / 跨视口 / 性能 / 可访问性影响 | 误导或噪音风险 | 保留 / 修改 / 删除`；未先确认任务和信息优先级，或不能说明元素职责的醒目元素，默认停在待补证据 / 降权，不直接给主观美化结论。
- 颜色、线、图标、动效、留白和视觉权重都要回指状态、关系、行动、品牌事实或可访问性。密度、装饰和品牌表达不是自动删除项，有真实任务或已确认品牌依据时应保留；保留前仍须核对目标受众、响应式变化、加载与动效成本、替代信息和辅助技术语义。
- 元素与真实状态不符、制造不存在的关系、抢占主要判断、重复表达却没有新增价值时修改或删除；不得用“更简洁”掩盖必要信息被删。
- 去色、模糊、移除分隔线或关闭动效可用于暴露层级问题，但只属于启发式检查；最终结论仍以任务完成、内容理解、状态辨识和可访问性验证为准。
- 没有真实页面、页面任务或信息优先级时，停止元素级裁决，只列需要补齐的证据，不输出主观美化方案。

## 四 A、Responsive Media Contract

本节是 Web 图片与多屏媒体适配的唯一 UI 权威。适用客户端包括桌面浏览器、超宽屏、移动浏览器/H5、响应式 Web 和嵌入式 WebView；原生 App、小程序和桌面原生客户端交对应平台能力。

### 1. 先判断图片职责

- **业务语义图片**：产品、SaaS 界面、质检缺陷、标签、文档、地图、图表、设施或需要用户检查的状态。使用 `<img>` / `<picture>` 语义、替代文本、固有尺寸和完整信息策略；不能为了铺满而裁掉业务含义。
- **内容说明图片**：案例、流程、团队协作或生活方式图。可按客户端准备裁切版本，但必须保留主体、动作和叙事关系。
- **纯装饰背景**：不承担独立信息的氛围或品牌背景。可使用 CSS background、`cover` 和焦点位置；替代文本应为空或由邻近内容承担语义。

### 2. 区分两类响应问题

- **Art Direction**：不同布局需要不同构图，例如超宽横图、普通桌面和移动竖图。设计契约给出独立 crop/source，并交工程通过 `<picture>` 或等价平台能力选择。
- **Resolution Switching**：构图相同但显示宽度、DPR、缩放或网络不同。设计契约提供分辨率资源，工程通过 `srcset + sizes`、`image-set()` 或框架图片组件选择。

Media query 负责页面级视口、方向、输入能力或用户偏好变化；同一组件在全宽、双栏和侧栏复用时，优先按可用容器设计并交接 container query。Flex/Grid 的自然换行已满足时不额外增加 query。

### 3. 背景图与固定尺寸边界

- 装饰性 Hero 可使用背景图、固定或受限高度、`background-size: cover` 和焦点位置；高度优先使用 `aspect-ratio`、min/max 或稳定区间表达，不按每个设备写散落常量。
- 固定高度只有在目标视口、最长内容、浏览器缩放和裁切均验证后才成立。单一 `background-position: center` 不能替代主体焦点和文字安全区。
- 超宽屏定义放大上限、最小有效分辨率、focal point token、文字安全区和必要的 ultrawide crop，避免人物、产品或设施被过度放大裁切。
- 商品图、产品截图、质检照片、地图、图表和文档默认不降级为背景图；需要完整展示时使用 contain、独立滚动/放大或专用裁切版本。

### 4. 最小媒体 Brief

每项关键媒体记录：职责、真实对象、来源与许可、原始尺寸、焦点、文字安全区、允许/禁止裁切、横/竖/超宽版本、目标容器、目标视口、1x/2x 资源、fallback、加载失败状态和 Owner。

官网或展示界面默认检查：移动目标视口、1280、1440、1920、2560 和 3440。项目未支持某视口时明确标为不适用，不用缺少设计稿推断已适配。

### 5. 业务场景差异

| 场景 | 媒体重点 | 不得丢失 |
| --- | --- | --- |
| 广告 / 创意 | 团队、创意、Campaign 材料和平台语境 | 主体动作、素材内容、平台身份边界 |
| 代采购 / 质检 | 产品、标签、缺陷、检查表和发运证据 | 产品细节、数量、缺陷、文字和文件关系 |
| 电商 | 商品主图、生活方式图、目录和平台状态 | 商品完整性、比例、变体和价格/库存语义 |
| SaaS / IT | 真实产品流程、界面和集成 | 操作状态、标签、数据关系和可读性 |
| 制造 / 工程 | 工艺、设备、设施、产品和项目状态 | 设备/产品主体、规格、现场关系和安全信息 |
| 物流 | 仓库、运输、地图、线路和追踪状态 | 地图标签、线路、节点、货物和状态 |

### 6. 实现与验收交接

- UI 契约说明选择逻辑和资源，不把 Next.js、React 或某个 CDN 写成跨项目唯一方案；工程能力按项目框架实现。
- 关键图片声明宽高或稳定比例，避免加载导致布局位移；LCP 候选说明优先级、文件体积和格式策略。
- 浏览器 Design QA 检查主体裁切、低分辨率放大、文字遮挡、加载失败、替代文本、1x/2x 清晰度、布局位移、LCP 和控制台/网络失败。
- Figma 画板和截图只能证明已检查视口的设计状态，不能证明浏览器选择了正确资源、性能达标或其它客户端已适配。

## 五、内容韧性

- 设计至少覆盖空、短、典型、极长、大数、多项、不同语言、用户生成内容和不可用媒体。
- 表格、卡片、标签、按钮、面包屑和导航需要明确换行、截断、展开与完整值获取方式；截断不能隐藏完成任务所需的信息。
- loading 保持结构稳定，error 保留用户输入，partial / stale 明确数据可信度，权限状态不伪装成空数据。
- 本地化验证日期、时间、时区、金额、单位、姓名、地址、复数和 RTL；只有项目实际支持 RTL 时才把它写成验收项。

## 六、最小验收

- 继承项与偏离项都有来源，未创建平行 tokens 或重复组件。
- 主要层级在去色、200% 文本缩放和窄屏下仍可理解。
- 第一视觉落点符合当前任务的注意顺序，主按钮不因控件类型自动压过待判断信息。
- 颜色、图标、动效和位置都不是唯一信息通道。
- CJK、长词、大数、错误、空数据和本地化不会遮挡或破坏任务。
- 设计系统组件的默认可访问性不被覆盖破坏；项目级关键路径仍完成键盘、焦点和人工验证。
