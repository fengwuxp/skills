本轮目标是先把本地知识库的可迁移认识、现有 Skill 覆盖情况、候选增量和验证方式固定下来，再逐项决定是否进入运行时资产。

本轮不做：

- 不复制原文、图表、练习答案、人物故事线或作者表达。
- 不把教学示例中的对象名、状态名、接口名或组织分工写成行业通则。
- 不把材料中的监管、费率、时效、厂商能力或卡组织规则当作当前有效事实。
- 不新增大而全的“支付培训 Skill”，也不改写已有来源独立公共核心。
- 不执行 Git 提交、同步、发布或安装。

## 3. 学习结果

### 3.1 支付认知主线

1. 支付不是一个 API，也不能由单一 `SUCCESS` 表达完成。业务事实、支付信息、账目/账本事实、真实资金和证据需要分层。
2. 业务流、支付信息流、账户/账本流、真实资金流既相关又不能互相替代；受理、授权、capture、清算、结算、银行入账、余额可用和对账关闭是不同完成层级。
3. 逆向与异常应作为独立事实处理：超时、重复、迟到、乱序、撤销、冲正、退款、退回、争议、拒付和调账不能覆盖原交易。
4. 对账不是“让所有数字相等”，而是让各权威事实源之间的差异可识别、可解释、可处置、可追溯。

这些认识与 `payment-expert` 当前对象、完成层级、恢复、清结算、账本和对账契约高度重合，应作为交叉确认，不重复写入。

### 3.2 产品与平台主线

1. 全球支付网络、全球支付平台、支付中台和支付开放平台是不同问题域，不能用系统清单代替能力地图。
2. 开放平台不是把内部接口直接暴露出去；至少需要应用与凭证、权限范围、API 产品、网关、事件、sandbox、报表、接入与上线证据共同闭环。
3. 状态、事件、报表和 sandbox 是对外能力能否被集成、恢复和验证的四类关键证据。
4. 产品套餐和服务等级应落到可测量承诺：能力、成本、时间、稳定性、支持和数据证据，而不是营销标签。

### 3.3 运营与组织主线

1. 支付事故闭环包括发现、分级、止损、诊断、修复/补偿、对账验证、沟通、复盘和规则回流。
2. 补偿应是有来源、范围、审批、执行、结果和复核证据的任务对象，不能退化为直接改库或“再跑一次”。
3. 组织协作要区分已批准、已配置、已发布和已验证；关键决策只有一个责任 Owner，并保留必要专业确认。
4. 这些组织与准出原则已由 `AGENTS.md`、`wise-agent` 和工程/安全 Skill 持有，本材料只提供支付场景交叉验证，不再复制治理正文。

### 3.4 企业卡、费用管理与 FX

1. 企业卡解决“如何支付”，费用管理解决“为何支付、谁负责、凭什么报销和如何入账”；两者可以组合但不能坍缩。
2. 审批、授权和费用审核是三个不同决策；预算也不等于真实资金、卡限额、授权占用或已入账费用。
3. 企业卡和员工报销需要跨路径查重，订阅型支出还需要责任人离职或岗位变化后的接管机制。
4. FX 事实应显式保留金额角色、币种、货币对方向、来源、时点、价格类型、有效期、精度、舍入和加价；退款金额不能默认等于原资金币种金额。

### 3.5 教学与能力形成

1. 有效知识资产不只是章节正文，而是渐进学习路径、角色路径、案例、图示、速查、练习、参考答案、讲师手册和演练的组合。
2. 能复述材料只证明知识清晰；能在异常、信息不全和角色冲突下给出证据化行动，才接近能力形成。
3. 可复用训练闭环是：阅读/诊断 -> 桌面推演 -> sandbox -> 历史案例 -> 受控真实任务。
4. 情景演练应有目标、角色、前置事实、角色私有信息、未知项、对象与状态、事件卡、交付物、红线、停止条件和检查点；每轮只压一个主能力，并由独立观察者或专业确认者复核。

## 4. 冲突与防误吸收矩阵

| 材料表达或风险 | 处理结论 |
| --- | --- |
| “支付本质是账”等教学缩写 | 只保留为帮助理解的镜片；运行时继续区分业务、支付、账本、真实资金和证据 |
| 示例对象、状态、接口和组织结构 | 视为教学模型，不升级为通用领域模型或目标项目契约 |
| 单一故事贯穿全部章节 | 吸收“连续案例降低认知成本”的方法，不保留故事名称和情节 |
| 训练等级与评分 | 只衡量当前训练任务证据，不作为人员能力、绩效或岗位等级判断 |
| 开放平台、全球平台和中台方案 | 作为能力完整性问题集，不作为唯一架构分层或服务拆分答案 |
| SLA、T+N、费率、FX、外部规则 | 必须补当前官方来源、合同、法域和 Owner；材料只能生成 `PENDING` 问题 |
| 本地材料的完整性 | 当前只完成结构全读与重点详读，不把 `read-with-limitations` 写成全文逐行核验 |

## 6. 建议吸收顺序

### Wave A：支付专家的真实缺口

只推进 `PKA-02`、`PKA-03`、`PKA-04`：

1. 先逐段对照目标 reference，删除与现有规则重复的候选。
2. 在 `payment-expert/references/source-map.md` 登记本地材料的 D1、读取范围、版本和非分发边界。
3. 每项只增加最小规则、一个正例和一个硬负例；不改来源独立公共核心。
4. 精确厂商、监管、会计、费率、时效和生产判断保持 `PENDING`，需要时另做当前官方来源核验。

### Wave B：文档能力的训练场景

推进 `PKA-06`：

1. 让 `document-authoring` 识别“课程/培训材料”和“情景演练手册”文种，先确定读者、能力目标、证据和训练后动作。
2. 领域事实由对应专业 Skill 提供；文档 Skill 只负责学习路径、案例结构、练习、讲师提示、答案边界和载体。
3. 先在既有两份 reference 中增加最小路由与结构，不新建顶层 Skill；只有常见任务需要读取大量无关章节时再拆 reference。

### Wave C：有证据才扩散

`PKA-05`、`PKA-07`、`PKA-08` 仅在现有 Skill 对合成反例确实失效时推进。产品架构、架构师、安全专家和 UI 设计专家只接收本专业增量，不复制支付对象与资金语义。

## 7. 实施与验证门禁

每个候选单独形成最小 diff，并依次满足：

1. 能回指本计划中的候选 ID、来源章节和现有 Skill 缺口。
2. 不包含原文、专有案例、个人路径、敏感信息或未经确认的外部事实。
3. `SKILL.md` 只增加必要路由；详细方法进入既有 reference，确定性行为进入 fixture/validator。
4. 同一规则只有一个权威位置，跨 Skill 只写责任边界和引用。
5. 至少有一个正常场景、一个硬负例和一个 owner/证据不足时的停止场景。
6. 运行相关 fixture 自检、触发路由检查、Skill 目录审计、统一 `scripts/validate.sh` 和同步 dry-run。
7. 由独立 Checker 复核误触发、重复知识、来源外推、隐私泄漏和验证假绿。

## 8. 待确认与停止条件

- `PENDING`：本轮已授权并完成本地 Skill 修改；Git 提交、同步、团队共享或公开发布仍需另行确认。
- `PENDING`：训练方法是否能稳定迁移到支付之外，需要至少一个非支付合成任务验证后再决定是否扩展。
- `PENDING`：开放平台、SLA、FX、监管和厂商能力的时效结论，需在实际设计任务中读取当前官方来源。
- 停止：若候选只是在复述已有规则、没有新的行为差异、无法构造失败样例，或必须复制材料原文才能成立，则不吸收。
- 停止：若改动需要新增顶层 Skill、跨多个现有权威或扩大 Git/联网/发布权限，先返回 Owner 重新确认。

## 10. 后续 CR 与 live 验证

- 独立 Checker 首轮发现四项：开放平台与事故能力缺顶层路由、培训场景缺数据与生产安全边界、九项交付包仍写成八项，以及静态 fixture 不能证明真实行为。前三项已按最小范围修复并补静态门禁，行为项改用同模型、同运行器的基线/候选盲评补证。
- 首次 `codex exec` 因本机缺少 `codex-code-mode-host` 而无法读取源文件，归类为 Harness 失败，不计入行为结果；随后采用 `source-stdin` 运行器，在禁止工具调用的相同条件下，对五个场景的基线与候选各执行两轮，共取得 20 个回答并交由独立 Checker 盲评。
