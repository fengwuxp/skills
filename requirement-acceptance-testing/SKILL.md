# 需求验收测试

## 定位

本 Skill 是 `product verification` 类型的独立 Checker。它把已确认需求转换为可追踪的验收条件，优先复用项目现有测试与 Playwright 等自动化能力，执行授权范围内的验证，收集跨层证据并输出 `Pass / Fail / Blocked / Need Owner`。

验收本身属于测试，但不等于只写自动化脚本：稳定、可观测、可重复的条件应自动化；价值取舍、不可程序化视觉判断和高风险授权保留人工确认。它不定义需求，不修改实现以制造通过，也不替代业务 Owner、工程 Owner 或发布 Owner。

本 Skill 当前为候选能力，仅在用户显式调用时使用；准入状态见 `admission.json`。

## 工作流

1. **冻结基线**：读取需求权威、版本或指纹、实现目标、环境、测试数据、范围、非目标、风险、Owner 与授权边界。无法定位需求原文或版本时输出 `Blocked`，不凭口述补规则。
2. **原子化条件**：将需求拆为可单独判定的条件，逐项记录来源锚点、前置条件、动作、期望、不可接受结果、责任 Owner 与重测范围；详细契约读取 `references/acceptance-contract.md`。
3. **选择最低充分证据层**：先复用项目已有单元、集成、契约、浏览器、视觉或可访问性工具，不把所有条件都推到 E2E；证据选择读取 `references/evidence-routing.md`。
4. **执行已授权验证**：只运行明确目标和环境内的测试。新增或大改测试代码交 `senior-software-architect`；UI/视觉判定需要 `ui-design-expert` 的设计契约或 Design QA 证据；支付、安全等专业不变量交对应能力定义和复核。
5. **形成证据链**：每项证据记录来源、指纹、环境、方法、结果、时间、生产者、独立复核者和限制。截图只能证明静态画面，不能单独证明交互、响应式、可访问性或业务副作用。
6. **裁决与交还**：原子结果使用 `pass / fail / blocked / cant-tell / untested / not-applicable`；总裁决按必选项推导。发现实现问题只记录 finding 与重测范围，交 Maker 修复后再独立重测。

需要复核公开方法、开源 Skill 借鉴和未吸收边界时读取 `references/source-map.md`。

## 场景路由

- **业务逻辑**：优先使用已有单元或服务级测试，并核对持久化结果、幂等和失败副作用；状态文案或 HTTP 200 不能替代业务事实。
- **API / 契约**：核对双方实际共享的请求、响应、错误和版本约束；契约测试不替代端到端业务结果。
- **数据 / 事件副作用**：读取目标数据库状态、消息、审计或投影证据；没有目标环境读证据时不得外推。
- **Web UI 交互**：优先使用项目已有 Playwright 或浏览器工具，按用户可见行为定位，覆盖成功、失败、重复操作、键盘/焦点和控制台；截图不是交互证据。
- **视觉还原**：必须同时有可定位的设计来源、声明视口的运行截图和独立视觉复核；文字意外换行、裁切、重叠、缺失资产与内容不一致均是可验收项。
- **可访问性**：自动规则用于发现确定性问题，键盘、焦点、名称/角色/状态和关键任务仍需相应运行证据；不得仅凭扫描器宣称 WCAG 合规。
- **人工条件**：无法可靠自动化但属于需求的条件使用 `manual-owner`，记录决策人、观察方法和限制；不伪造自动化覆盖率。

## 输出契约

- `验收契约`：需求与实现指纹、范围、环境、数据、Owner、风险和授权边界。
- `原子条件`：来源锚点、验证类型、前置/动作/期望/反例、结果、证据和重测范围。
- `证据清单`：可复核来源、方法、结果、生产者、独立复核者与限制。
- `裁决`：`Pass / Fail / Blocked / Need Owner`、直接原因、残余风险和下一 Owner。

结构校验默认保留报告自身裁决：

```bash
python3 requirement-acceptance-testing/scripts/check_requirement_acceptance.py --file report.md
```

需要把报告用于自动准出时显式增加门禁：

```bash
python3 requirement-acceptance-testing/scripts/check_requirement_acceptance.py --file report.md --require-pass
```

脚本只做离线结构、追踪、证据充分性和裁决一致性校验；`VALID` 只表示报告合法，只有 `--require-pass` 且报告裁决为 `pass` 才返回准出成功。两者均不代表需求正确、目标系统可用或生产获批。

## 停止条件

- 缺需求权威、版本/指纹、目标实现、环境、必要测试数据或验收 Owner。
- 需要安装依赖、联网、Git、部署、生产访问、密钥、删除或不可逆动作但未获明确授权。
- 必选项不可测试、证据互相冲突，或价值取舍只能由 Owner 决定。
- 用户同时要求验收和修复时，必须先输出独立 finding，再由 Maker 修复，最后重新验收；Checker 不自证。

## 红线

- 不发明需求、补写通过条件或把实现现状反向定义为需求。
- 不把测试命令退出码、截图、DOM 存在、状态成功或 Agent 自述单独当成业务通过。
- 不为一次验收默认安装 Storybook、Pact、视觉平台或新的测试框架。
- 不把专家评审冒充目标用户验证，不把本地证据外推到目标环境或生产。
- 不自动修复、提交、同步、部署、发布或修改验收基线。
