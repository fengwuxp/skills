# 安全风险、控制与证据

## 使用时机

需要形成安全设计、威胁/滥用评审、控制矩阵或发布安全门禁时读取。本文给出共同骨架，不替代场景专项事实、独立控制评估或系统授权。

## 不适用场景

- 不用于凭关键词给系统打“安全分”。
- 不用于替代漏洞扫描、渗透测试、法律合规判断、独立控制评估或生产授权。

## 读取后必须产出

- 资产与资损、利益相关方保护需求、安全要求、主体与信任边界、风险路径、控制与恢复、声明与证据、残余风险与停止条件。
- 每条重要风险到保护需求、安全要求、控制、声明、证据和 Owner 的追踪关系；没有证据时标记未验证。
- 相对于声明准出目标的安全工程建议；不得把工程建议写成独立评估或授权决定。

## 需要继续读取的 reference

- 先在 `security-scenario-routing.md` 选择主场景和任务身份。
- 使用外部标准或版本化要求时读 `source-map.md`。

## 可追踪安全工程链

用一条可复核的因果与证据链描述风险：

```text
业务目标与风险容忍
  -> 资产、资损与保护需求 PN
  -> 安全要求或不变量 SR
  -> 威胁或滥用路径 RISK
  -> 预防/检测/响应/恢复控制 CTRL
  -> 可验证安全声明 CLAIM
  -> 证据 EVIDENCE
  -> 残余风险与安全工程建议
  -> 独立评估 Owner
  -> 授权 Owner
```

不要只列“注入、越权、泄露”等名词。路径必须说明主体如何从入口跨越信任边界到达资产，安全要求约束什么，控制在哪个节点阻断、发现、限制或恢复，证据具体证明哪项声明。

## 资产、保护需求与安全要求

- **资产**：数据、资金、凭证、身份、权限、业务资格、配置、代码、制品、服务可用性、审计证据和组织信誉。
- **资损/后果**：直接资金损失、数据泄露或篡改、未授权能力、业务中断、证据丢失、合规责任和不可恢复状态。
- **保护需求 `PN-*`**：利益相关方要求避免、限制或恢复哪类损失，以及不可承受的影响边界。
- **安全要求 `SR-*`**：从保护需求推导的可验证行为、不变量或架构约束；必须写清适用主体、对象、状态和失败行为。

需求链必须保留来源，不从客户端字段、网关 Header、网络位置、历史 token 或任务自述推断可信。产品、支付、法律或生产事实未知时回到对应 Owner，不由安全要求补造业务事实。

## 主体、边界与风险路径

- **主体**：外部攻击者、合法低权限用户、内部人员、管理员、服务身份、第三方、设备、任务和 AI/自动化代理。
- **信任边界**：公网/内网、租户、组织、权限域、服务、数据域、运行环境、第三方、构建发布和人工审批边界。
- **风险 `RISK-*`**：写清资产、主体、前提、入口、跨越边界、动作与传播、后果、现有控制和失效方式。

至少从与当前资产有关的伪造、账户接管、越权、职责串用、篡改、重放、竞态、数据生命周期、业务绕过、内部合谋、供应链、拒绝服务、告警失效和恢复失败中选择。优先级使用组织既有方法；没有既有方法时使用 `CRITICAL / HIGH / MEDIUM / LOW` 并写依据，不做伪精确乘法打分。

## 控制闭环

| 层次 | 回答的问题 | 典型证据 |
| --- | --- | --- |
| 预防 | 如何减少发生概率或限制入口 | 默认拒绝、最小权限、输入/协议校验、隔离、审批、签名、限额、不可变策略 |
| 检测 | 如何在损失扩大前发现 | 安全日志、指标、异常规则、完整性校验、配置漂移、对账、关联告警 |
| 响应 | 发现后谁在多长时间内做什么 | 分级、隔离、冻结、吊销、阻断、人工接管、证据保全、通知与决策记录 |
| 恢复 | 如何回到可信状态并防止复发 | 回滚、密钥轮换、数据/账务修复、重放校验、对账、演练、复盘和回归门禁 |

控制使用 `CTRL-*` 标识，记录作用点、Owner、失败模式、旁路、依赖、业务代价和验证方式。高风险控制若只存在于文档、前端提示、未启用配置或无法回读的流程中，视为未落地。

## 声明与验证证据

安全声明使用 `CLAIM-*` 标识，写成可证伪结果，例如“同一调用方的同一 nonce 第二次提交必被拒绝”，不能写“已安全”。证据使用 `EVID-*` 标识，并带目标、环境、版本/时间、结果和保管位置。

证据分层声明，不跨级声称：

1. `D1_DESIGN`：保护需求、安全要求、路径、控制、声明和验收已定义。
2. `D2_IMPLEMENTATION`：代码、配置、策略或基础设施已实现并可定位。
3. `D3_ENABLED`：目标环境已加载/启用，配置与权限可回读。
4. `D4_RUNTIME`：测试、扫描、日志、告警、故障注入或演练证明控制按预期工作。
5. `D5_PRODUCTION`：目标生产版本、真实依赖、观测窗口、Runbook、值守与风险 Owner 完整。

扫描无发现只是一类证据；测试、配置回读、制品来源、运行观测和人工演练按风险组合。追踪表中的“实际证据等级”表示该风险已闭合证据包的最低等级，不是其中最高一项证据的等级。

## 相对准出与职责分离

先声明准出目标，再形成安全工程建议：

| 准出目标 | 最低证据 | 只证明什么 |
| --- | --- | --- |
| `DESIGN_D1` | `D1_DESIGN` | 设计输入、要求、路径、控制和验收可进入后续实现 |
| `IMPLEMENTATION_D2` | `D2_IMPLEMENTATION` | 实现可定位，不证明目标环境已启用 |
| `ENABLEMENT_D3` | `D3_ENABLED` | 目标环境已启用并可回读，不证明运行效果 |
| `RUNTIME_D4` | `D4_RUNTIME` | 控制在目标运行验证中按预期工作 |
| `PRODUCTION_D5` | `D5_PRODUCTION` | 指定生产版本、依赖、观测和值守证据闭合 |

- `ENGINEERING_READY`：所有重要风险相对于准出目标闭合，没有阻断项；不等于独立评估通过或系统授权。
- `ENGINEERING_READY_WITH_RISK`：没有阻断项，条件性残余风险、补偿控制、期限和人类风险 Owner 明确；不等于风险已获授权接受。
- `ENGINEERING_BLOCKED`：关键资产/责任未知、重要路径无控制、实际证据低于目标、控制未启用/未验证、恢复不可用，或风险无人负责。

安全工程 Owner 负责安全要求与建议，独立评估 Owner 负责与设计/实现责任分离的控制评估，授权 Owner 负责人类风险接受和系统/生产授权。参与设计的 Agent 不得给自己签发“独立评估通过”，也不得代替授权 Owner。

## 风险控制证据追踪

正式安全评审至少为每条重要风险填写一行；多个控制或证据可以在同一单元格使用逗号分隔：

| 风险 ID | 优先级 | 保护需求 ID | 安全要求 ID | 控制 ID | 控制 Owner | 声明 ID | 证据 ID | 实际证据等级 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| RISK-001 | HIGH | PN-001 | SR-001 | CTRL-001 | 平台安全负责人 | CLAIM-001 | EVID-001 | D4_RUNTIME | CONDITIONAL |

状态只使用 `CLOSED / CONDITIONAL / OPEN`。`CONDITIONAL` 只表示工程上有具名残余风险，不替代人类接受；`OPEN` 必须进入阻断项。

脚本只检查结构、ID 引用、目标证据等级和状态一致性。字段完整与 ID 相连仍不代表风险、控制、声明和证据在语义上相关；该判断必须由独立 Checker 读取真实材料完成。
