# 安全场景路由

## 使用时机

安全任务跨业务、资金、身份、数据、协议、软件或运行层时读取。先选主场景，再读取风险控制方法；不要一次展开全部清单。

## 不适用场景

- 只有普通产品语义、一般代码修复、单纯支付对象设计或法律意见时，不由本 Skill 主持。
- 只要求仓库/path 或 Git diff 漏洞扫描时，直接使用下文对应的 `codex-security:*` 能力。

## 读取后必须产出

- 一个主场景、必要的相邻场景、事实 Owner、关键资产、信任边界和停止条件。
- 明确哪些事实由产品、支付、架构、外部标准或人类 Owner 提供。

## 需要继续读取的 reference

- 建立资产、路径、控制、证据和残余风险闭环时读 `security-risk-control-and-evidence.md`。
- 引用外部标准、版本与时效事实时读 `source-map.md`。

## 任务身份门禁

先按目标产物正名，再选择安全场景：

| 目标产物 | 主责 | 本 Skill 的位置 |
| --- | --- | --- |
| 安全需求、架构约束、风险路径、控制与证据设计 | 本 Skill | 主责安全工程建议 |
| 与设计、实现责任分离的正式控制有效性评估 | 独立 Checker / 人类评估 Owner | 提供控制声明、证据包和已知缺口，不自称独立 |
| 代码、配置、基础设施与运行改动 | `senior-software-architect` 或对应运维 Owner | 提供安全约束和验收种子 |
| 风险接受、系统授权与生产上线 | 人类授权 Owner | 提供残余风险和 `ENGINEERING_*` 建议，不代签授权 |
| 法律、监管、隐私合规与认证结论 | 对应专业 Owner | 提供安全事实，不作正式适用性结论 |

## 按任务读取索引

| 主场景 | 先问什么 | 重点边界 | 协同能力 |
| --- | --- | --- | --- |
| 业务安全 | 哪种欺诈、越权、流程绕过或内部滥用会造成何种资损 | 业务资格、审批、额度、职责分离、人工处置、审计 | 产品事实用 `product-architecture-expert` |
| 资金安全 | 谁的钱、谁能下令、何时不可逆、错误如何止损恢复 | 账户接管、重复/冲突指令、异常放款、冻结解冻、对账与追偿 | 支付语义用 `payment-expert` |
| 身份与权限 | 主体是谁、凭证从何而来、权限授予/撤销由谁负责 | 身份生命周期、MFA、最小权限、对象/数据级授权、特权访问 | 实现用 `senior-software-architect` |
| 数据与信息 | 数据为何敏感、沿何路径采集/使用/共享/保留/删除 | 最小化、分级、隔离、加密、脱敏、密钥、日志与导出 | 隐私与合规适用性由专业 Owner 确认 |
| 协议与集成 | 对端是谁、消息如何认证、完整性与新鲜性如何证明 | TLS、mTLS、签名、nonce/时间窗、重放、降级、重试、回调与幂等 | 协议实现和互操作测试用架构师 |
| 软件与供应链 | 哪些源码、依赖、构建、制品和发布权限可改变系统 | 安全设计、代码缺陷、依赖来源、SBOM、签名、CI/CD、密钥和环境隔离 | 扫描/验证按下表选 `codex-security:*`，工程修复用架构师 |
| 运行与事件 | 如何发现异常、限制影响、保全证据并恢复可信状态 | 监测、告警、分级响应、隔离、轮换、回滚、取证、演练和复盘 | SRE/安全/业务 Owner 决定生产动作 |

## `codex-security:*` 精确路由

| 目标产物 | 主能力或方法能力 | 边界 |
| --- | --- | --- |
| 仓库或指定 path 的标准单次安全扫描 | `codex-security:security-scan` 主能力 | 不用于 PR、commit、branch 或工作树 diff |
| Git-backed diff 安全评审 | `codex-security:security-diff-scan` 主能力 | 不替代完整仓库扫描或跨业务安全准出 |
| 已有候选 finding 的真伪与严重度验证 | `codex-security:validation` 主能力 | 不接管代码修复 |
| 已验证或可信 finding 的代码修复 | `senior-software-architect` 持工程交付责任，加载 `codex-security:fix-finding` 方法能力 | 不让插件成为第二 Owner；仍遵守项目测试、CR 和发布门禁 |
| 仓库范围的威胁模型 | `codex-security:threat-model` 主能力 | 跨业务、资金、协议与运行控制的安全结论仍由本 Skill主责 |
| 基于漏洞、事件、源码或扫描结果的系统性加固建议 | `codex-security:propose-security-hardening` 主能力 | 若问题扩展到业务资损、资金责任、跨层控制和风险接受，切回本 Skill主持 |

## 组合规则

- 一个任务只设一个安全工程建议 Owner；相邻能力提供事实、实现或独立验证，不建立平行安全方案，授权决定仍由人类 Owner 持有。
- 资金安全必须消费支付事实，但不能由支付成功推导安全完成；业务安全必须消费产品事实，但不能把业务规则等同安全控制。
- 协议安全至少同时检查通信通道、消息/业务语义和凭证生命周期。TLS 保护链路，不自动证明对端业务权限、消息新鲜性或幂等。
- 数据安全至少贯穿采集、传输、存储、使用、导出、日志、备份与销毁，不只检查数据库加密。
- 运行安全必须闭合检测、响应和恢复；只有预防控制的方案无法证明事故可控。

## 停止条件

- 资产、法主体、权限 Owner、资金责任或生产环境未知，且会改变控制结论。
- 关键协议/依赖版本、密钥责任或外部终态权威无法核验。
- 高风险动作没有止损、恢复、审计或风险接受 Owner。
