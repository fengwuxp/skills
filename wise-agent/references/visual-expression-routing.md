# 视觉与结构表达选择

## 使用时机

当用户要看懂复杂概念、流程、方案或代码变化，或结构关系比文字更适合说明当前问题时读取；无需专用命令。单个事实、简短定义、纯文本创作直接完成；既有图形编辑和科学 / 实时数据图表按对应任务能力处理，不套用概念图流程。

## 先定问题，再选表达

从已有材料确定读者需要理解或决定什么，沿用用户指定的载体、格式和范围；未指定时由当前 Agent 选择，无需让用户挑工具或补一张说明卡。最小表达以能保留结论所需的条件、关系和例外为准，不等于节点最少、字数最短或一律纯文本。

| 理解上的主要困难 | 合适的表达 |
| --- | --- |
| 单一事实或短定义 | 短段落或小例子；不附无助于理解的图 |
| 比较选项、对应关系、权衡条件 | 表格；保留差异与未知，不臆造评分、排序或业务取舍 |
| 看清层级、过程、状态或参与者关系 | 最小结构图、流程图、时序图或状态图；不因为参与者多就扩成全系统架构交付 |
| 理解代码形状或具体变更 | 读 `senior-software-architect/references/diagram-output.md` 的“轻量结构表达选择”，复用伪代码、调用树、组件树、浅文件树、类型 / 签名和差异视图的现有裁决 |
| 理解原因、参数变化或不同情境的结果 | 交互确能帮助理解时优先采用当前可用的交互可视化，显示输入、规则、结果与适用边界；无法交互时提供可比较的静态情境 |

默认围绕一个主问题选择一种主表达；第二种视图必须回答不同问题。先给关键结论并配所需结构，不先输出工具菜单、格式选择过程或重复的大段解说。

## 领域与载体分开

领域主能力与候选准入以 `capability-routing.md` 为唯一权威。普通概念可直接解释；只有领域判断确需专项时才装载专业能力。图或 HTML 后缀不自动触发产品设计、UI 重设计或架构流程，讲解页面也不等于产品原型。

- 产品 / 工程的正式图形交付分别沿用对应 `references/diagram-output.md`；用户指定 SVG、文档内 Mermaid 或交互 HTML 时遵从其结果要求。对话中的局部说明不因正式图形默认 SVG 而强行生成文件。
- 交互解释可使用当前可用的可视化工具或本地 HTML；Archify 等只在题型、能力和验证方式适配时作为后端。读取当前工具状态；一个后端缺失时选择已有等价能力，不能把未安装某工具变成任务整体阻塞。
- 只需聊天内说明时就地表达。任务明确需要可操作或可分享产物时，在授权范围生成并回读，不重新索要已给出的文件授权；执行工具必要的临时产物不自动成为仓库文件。截图、导出或发布按本轮交付需要和授权处理。

## 保真与验证

- 节点、箭头、状态和数值须回指材料；源码理解与 CR 保留源码锚点，区分实际实现、用户给定示例、候选目标和未确认连接。未知关系保持可见，不能为了图完整补造业务规则或因果。
- 按载体核对结果：文本结构回读对象与顺序；图检查方向、标签和可读性；交互产物检查默认值、参数变化和关键边界。缩短表达不能丢失失败路径、责任与限制。
- 工具不可用或事实不足时，只暂停依赖该缺口的部分，继续可确认内容；格式可读、脚本通过或截图不证明读者已理解、业务正确或架构验收通过。
