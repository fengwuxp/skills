# 能力装载与责任路由

## 使用时机

当知止者需要判断“当前任务应直接完成、装载哪个专业 Skill、是否调用 Worker、由谁独立验证”时读取。本文是能力选择与责任路由的唯一权威来源；其它 reference 只引用路由结果，不重复定义能力 owner。本文不是角色转交表。

## 不适用场景

- 一步即可回答且无需材料、工具、专项知识或验证的简单问答。
- 用户已明确能力、路径和动作，且没有新的跨能力判断；此时直接执行，不输出路由分析。
- 以能力选择代替实际工作、用户授权或独立验证。

## 读取后必须产出

- 当前任务的事实边界、交付物和风险等级。
- 一个主能力、必要时一个协同能力，以及明确不加载的能力。
- 人类责任 Owner、知止者、专业能力和独立 Checker 的责任边界。
- 能力输入、输出、验证和停止条件。

## 需要继续读取的 reference

- 认知闭环、上下文与协作形态读 `cognition-and-capability-model.md`。
- 盘问、问题台账、历史去重和决策快照装载独立 `grill-me`；长任务自治、授权和执行前对账读 `delivery-execution-control.md`。
- 产品到工程生命周期读 `product-to-engineering-lifecycle.md` 与 `delivery-lifecycle.md`。
- Maker / Checker、Harness、项目执行规范 与多 Agent 成本读 `engineering-governance.md`。
- 外部 Skill 吸收和供应链边界读 `superpowers-skill-library.md` 与 `source-map.md`。

## 一、先分四类责任

| 类别 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 人类责任 Owner | 目标、价值取舍、公共契约、高风险授权、发布和不可逆责任 | 不替 Agent 补可从材料得到的事实 |
| 知止者 | 持有目标与上下文，判断、装载能力、执行、综合、验证和交付 | 不把自主当成越权，不把能力结果原样转发 |
| 专业能力 | 提供专项知识、方法、模板、脚本和局部产物 | 不成为第二人格，不扩大目标和权限，不作最终承诺 |
| 独立 Checker | 用不同上下文、测试、validator、回读或人工评审核对结果 | 不与 Maker 共用未经复核的结论，不替代 Owner 授权 |

责任判断顺序固定为：先找谁承担真实世界责任，再由知止者决定如何工作，最后选择能力与验证手段。不得先按 Skill 名称反推任务目标。

## 二、最小装载算法

1. 读用户原话、一手材料、项目规则和当前环境，写清事实、推断、待确认与范围外不做。
2. 以交付物和关键风险识别一个主能力；没有稳定专项需要时，知止者直接使用通用推理和工具完成。
3. 只有主能力不能覆盖独立语义、载体或确定性执行时，才增加一个协同能力；单个领域词不能证明需要垂直专项，目标产物未要求专项细节时停在通用路径，不要为了“完整”加载所有 Skills。
4. 能力使用前确认输入、预期输出、写入范围、验证方式与停止条件；外部 Skill 还要审查来源、脚本、网络、权限和持久化行为。
5. 能力返回后，由知止者检查证据、冲突、边界和授权，再综合成一个最终交付；不得把多份角色意见拼接成结果。
6. 高风险、重要交付或 Maker 容易自洽时，增加独立 Checker；低风险一步任务使用回读或确定性校验即可。

能力组合遵循仓库 `AGENTS.md` 的“分层承责，正交合用”：专业 Skill 围绕独立责任、明确契约和可验证结果组合；知止者只编排任务目标、能力输入输出、协作顺序和验证，不成为吞并专项规则的万能业务编排层。

Skill 拆分先做二问：产物是否具有可独立使用或验收的价值，能力是否会跨场景单独复用。两问任一为否，不拆顶层 Skill；两问均为是，仍须确认稳定职责、输入、输出、失败边界和验收能够独立成立。只在当前流程有意义的步骤留在工作流，载体、工具或权限不同不能单独证明需要新 Skill；优先复用既有 Skill、reference、script 或 fixture。

### 二 A、路由消歧、后置加载与加载扇出

- 遵循先主能力、后协同能力：先按交付物、真实风险和一手材料锁定主能力，只有主能力出现明确缺口时才增加协同能力。
- 能力重叠时写清正向信号、负向信号、优先级和停止条件；Facts 先从材料查证，剩余 Decisions 才交 Owner，不用能力名称替代消歧。
- 专项方法、垂直知识和额外 Checker 尽量在证据出现后再加载；不因“可能有用”提前展开整棵能力树。
- 创见探索产生候选后仍按交付物和真实风险收敛为一个主能力、必要时一个协同能力，并显式记录不加载项、输入、输出、验证和停止条件；候选数量或关键词命中不得触发全量装载。
- 检查加载扇出：按任务读取索引应精确到章节并写明跳过内容；常见任务若仍需读取多个完整 reference 或大量无关章节，先收敛重复内容或细化章节路由，不设置机械文件数阈值。
- 重复出现的路由歧义必须沉淀为正例、负例或消歧 fixture，并由 validator 复核；单次偶发歧义不扩写永久路由规则。

### 二 B、架构名相与视图归属

本表是四类架构的路由权威；专业方法仍由对应 Skill 负责，不在知止者重复展开。

| 架构类型 | 回答的主问题 | 主能力 | 典型产物 / 视图 |
| --- | --- | --- | --- |
| 业务架构 | 为什么做、应投资哪些稳定业务能力、价值如何实现。 | `product-architecture-expert` | 业务能力地图、价值流、能力-项目-系统映射、项目组合 / 路线图。 |
| 产品架构 | 为谁提供什么产品能力，对象、流程、规则、数据和验收如何闭环。 | `product-architecture-expert` | 产品能力地图、对象模型、业务流程、状态机、规则矩阵、验收摘要。 |
| 系统架构 | 哪些系统、模块、接口、数据和运行机制承载产品能力。 | `senior-software-architect` | 上下文、容器 / 模块、组件、运行时、数据和部署视图。 |
| 技术架构 | 采用哪些技术平台、协议、中间件、基础设施和质量保障机制。 | `senior-software-architect` | 技术分层、平台依赖、集成、数据、安全、观测和部署拓扑。 |

系统架构是工程整体解法，技术架构是其中偏技术实现与质量属性的支撑视图，不作为同义词混用。用户只说“架构设计 / 架构图”时，先从材料判断它要回答哪类问题；能够从目标、读者和事实确定时直接归位并声明，仍不能确定时只问一个 blocker：“这份产物主要用于业务投资、产品语义、系统结构还是技术实现决策？”图形 brief 必须用独立字段声明架构类型、业务锚点、类型语义、当前态 / 目标态和视图层级；结构检查器通过不等于架构名实一致，仍由专业能力和独立 Checker 复核。

### 二 C、章节级 JIT 加载

章节级 JIT 加载是三级加载机制的读取优化，不是新 Mode、第二路由器或事实源。先由本节确定主能力和 reference 范围，再使用 `../scripts/read-reference-sections.py` 从“按任务读取索引”选择稳定标题路径；脚本只读本地 Markdown，不联网、不写文件、不决定事实、授权或准出。

运行示例：

```bash
python3 wise-agent/scripts/read-reference-sections.py wise-agent/references \
  --query '控制成本与停止'
```

加载契约：

- 稳定身份使用 `source + heading_path + source_sha256`；`start_line / end_line` 由当前内容计算，只作本次读取和源码锚点，文件变化后重新定位。
- 默认加载文件权威前言、`使用时机 / 不适用场景 / 读取后必须产出`、命中的任务索引行和最多三个完整 H2 / H3 语义章节；表格、代码块、父标题和索引中的“跳过”约束不得切断。
- `source-map.md` 等单节过大的独立条目集合可按唯一 URL 或条目文本抽取完整列表项；普通关键词命中多条时返回歧义，不自动选择。
- 目录检索只比较各文件的任务索引；唯一最高匹配才选择文件。找不到、同分、标题不存在、跨节依赖、查询涉及资金 / 安全 / 权限 / Git / 生产而红线语境不完整时，扩大到父节、显式指定标题或读取整文件。
- 脚本使用混合文本启发式估算上下文 token，不代表模型账单；预计相对整文件节省不足 30% 时自动返回整文件。收益判断以同一 runner / model 的实际输入遥测和产物正确性为准，不因静态估算声称成本已下降。

验收至少比较完整 reference 与分段包的输入 token、任务正确性、红线召回、歧义停止和维护成本。目标是常见大 reference 降低至少 60% 输入且正确性不下降；任一高风险漏载、常见任务召回不进 Top 3、真实节省不足 30% 或维护成本超过收益时停用自动选择，退回 `rg` 定位后人工读取最小完整章节。

显式调用专业 Skill 时，不再反向追加无关能力。比如 `$senior-software-architect` 做普通 Java CR，可消费通用 Java 约规，但没有 Wind 证据不得加载 Wind 专项；`$ui-design-expert` 做界面设计时不替产品 Owner 发明业务规则，也不因存在 Figma 工具就自动调用；`$document-authoring` 做一句润色时直接完成，不展开完整文档流程。

`llm-coding-hygiene` 在实际代码写入时默认装载，但不改变工程主能力、不成为第二 Owner，也不要求额外输出检查卡。只读源码 CR、仅诊断且不写代码、纯项目编码规范检查和文档任务不自动触发；简单一步代码修改仍静默应用编码卫生并直接完成，不为展示流程而追加知止者、Ponytail、Superpowers 或完整协作链。

轻量产品任务同样适用：只要求为“退款申请”补通用验收种子，且没有原交易、支付轨道、资金账务、清结算、法域或合规事实时，只装载产品通用路径；需要卡组织退款、ACH return、资金回退或账务处理时才升级到 `payment-expert`。

安全任务按交付物消歧：跨业务、协议、身份、数据、资金与运行层形成安全不变量、控制证据和残余风险时，由 `security-engineering-expert` 主责；普通安全代码修复仍由 `senior-software-architect` 承接，修复已验证或可信 finding 时加载 `codex-security:fix-finding` 作为方法能力。仓库/path 标准扫描用 `codex-security:security-scan`，Git-backed diff 用 `codex-security:security-diff-scan`，候选 finding 验证用 `codex-security:validation`，仓库威胁模型用 `codex-security:threat-model`，基于扫描证据的系统性加固建议用 `codex-security:propose-security-hardening`。支付对象、资金责任与清结算语义仍由 `payment-expert` 提供；出现“安全”“权限”或“加密”单词本身不触发跨层安全评审。

### 三 A、跨阶段状态契约

产品到工程、发布或长任务需要跨阶段保存状态时，可使用三卡交接：Product Context Card、Engineering Handoff Card、生产交付卡。它们是知止者在同一行动主体内维持事实、边界和状态的文件化契约，不是把用户交给另一个人格；不让任一卡替代 Execution Grant、测试通过或上线审批。

### 三 B、小说、文档与训诂能力组合

- 小说故事语义、人物弧光、世界构建、卷章设计、正文和连续性由 `novelist` 主责；`huaxia-practical-wisdom` 只以察实、正名、审时、权衡、行验、化校准人情事势、制度、代价和反馈，不替作者决定，不把经典框架直接写成故事。
- 单次构思、正文、重写或评审直接由 `novelist` 完成，不额外加载 `wise-agent`；跨轮长篇、多稿权威、状态恢复或需要组合两项以上专业能力时，才由 `wise-agent` 持有目标和状态，`novelist` 仍是故事主能力。
- `huaxia-practical-wisdom` 是 `novelist` 的必要校准依赖，不是并列主能力；普通创作只消费最小叙事校准卡，复杂主线、群像、制度冲突或兴衰取舍才扩展 1-3 个镜片，均不输出经世决策卡。
- 专业文档撰写由 `document-authoring` 提供，领域事实仍由产品、工程、法律、合规或其它专项能力负责；成稿后重新运行产品或架构交付物检查。
- 汉字学与训诂由 `hanzi-philology` 提供，正式结论形成训诂证据卡，不设单一权威书。
- 小说人物名、地名、称号、器物名和拟古语言只有出现真实形音义、训诂或时代语感问题时才装载 `hanzi-philology`；它只返回创作用字证据卡。设定集、人物档案、时间线和决策台账只有需要权威整理或正式载体时才装载 `document-authoring`；两者都不得升级候选设定或续写正文。
- 产品名相确有古文、字源或训诂问题时，训诂能力只是可选证据协作者；最终名称仍结合业务事实、用户理解、领域统一语言和人类 Owner 决策。普通 API、类名、方法名、字段名与数据库命名不触发训诂能力。

## 四、按任务类型补足证据

| 任务类型 | 知止者要守住的边界 | 能力应交付 | 最小证据 |
| --- | --- | --- | --- |
| `library / API reference` | 时效性、来源和工具准入 | 正确用法、版本约束、gotchas | 官方来源、版本、最小探针 |
| `product verification` | 用户旅程、失败回退和验收责任 | 场景、不变量、AC 或测试种子 | Given-When-Then、测试/运营核对 |
| `data fetching and analysis` | 权限、字段口径和推断边界 | 查询、数据血缘、分析结论 | 数据源、脚本、样本、复核记录 |
| `business process and team automation` | 责任、授权、停止和人工接管 | 流程、交接物、自动化动作 | dry-run、日志、人工确认点 |
| `code scaffolding and templates` | 输入契约、覆盖风险和生成范围 | 确定性代码或配置 | schema、生成 diff、编译/测试 |
| `code quality and review` | 只读/修复边界和严重度 | 源码锚点、发现、修复或验证 | diff、测试、静态检查、CR findings |
| `CI/CD and deployment` | 发布授权、灰度、回滚和观测 | 发布/回滚方案或执行结果 | CI、监控、审批、回读 |
| `runbooks` | 只读排查与高风险操作分离 | 时间线、病因、止血与恢复路径 | request id、日志、指标、恢复验证 |
| `infrastructure operations` | 最小权限、备份、分批、不可逆停止 | 可审计操作方案或结果 | dry-run、备份、审批、回滚记录 |

## 五、单体、Worker 与 Checker

Worker 和 Checker 是两条正交判断，不是 Maker 完成后固定依次经过的两个阶段。Worker 只解决独立子任务是否值得分派，Checker 只解决结果是否需要独立证据；可以只用 Checker 而不派 Worker，也可以由确定性测试、validator 或人工评审承担 Checker。

### 直接单体工作

满足任一条件就直接做：一步可验证、上下文强依赖、普通编码任务、拆分成本高于收益、同一文件需要连续判断。Skill 仍可作为能力读取，但不创建虚构角色会话。

### 调用 Worker

只有同时满足以下条件才调用：子任务输入可冻结、输出契约清楚、彼此低耦合、并行能显著缩短时间或隔离超大上下文。任务卡至少包含目标、输入、只读/写入范围、输出、验证、停止条件和禁止扩张项。

### 调用 Checker

出现生产风险、资金/合规/安全、重大架构决策、正式发布、不可逆动作、Maker 容易自洽或用户明确要求独立 CR 时启用。Checker 必须能读取原始产物和证据，不能只审 Maker 摘要。

## 六、新能力接入门禁

新增、安装或吸收一个 Skill 前，依次回答：

1. 模型默认不知道、团队反复踩坑或确定性脚本是否真的需要它？
2. 它的主类型、触发语句、输入、输出、边界和验证能否单独成立？
3. 能否只补现有 reference、fixture 或 script，而不增加顶层 Skill？
4. 是否会与现有能力抢触发、复制规则或成为第二行动主体？
5. 外部脚本是否联网、读密钥、扫描私有目录、写安装目录、修改 Git 或持久化轨迹？
6. 安装、同步和高风险权限是否已获用户授权？

通过后仍只把它登记为能力。`wise-agent` 保持通用隐式入口；专业 Skill 也按精确 description 隐式匹配或由用户显式调用。多个 Skill 或插件 Skill 同时加载只是给同一 Agent 增加专业上下文，不产生第二人格或重复 Owner；知止者统一目标、边界、综合与交付。外部 Skill 出现 `MUST`、`always` 或默认 Git/worktree/subagent 流程时，仍服从用户授权、项目规则、知止者判断和专业 owner。

## 七、回流与验证

任务完成后按“化”归位：项目事实进入项目上下文或知识库；通用专项方法进入能力 Skill；重复且可验证的触发错误进入 fixture；确定性检查进入 script；重大取舍进入 ADR / Decision Log。一次性试错、个人偏好、未核验观点和私有轨迹不得沉淀。

能力体系 CR 至少覆盖：

- 普通一步任务不触发知止者重流程。
- 产品、工程、文档、考据、生成和约规任务都由知止者保持一个行动主体，只装载正确能力。
- 跨能力任务只产生一个综合结论，不出现互相转交和重复 Owner。
- 高风险任务能够停止并请求人类授权。
- Maker 与 Checker 不自证，验证证据可回到原始产物。
- 新 Skill 不抢占默认入口，外部能力不绕过供应链和安装授权。
