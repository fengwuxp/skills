# 工程变更契约

本文用于公共接口、公开方法、跨模块模型和多文件重构的写回前约束。它不是规划文档、审批表或第二状态源，而是把“为什么存在、谁消费、承担什么、如何证明”压成可校验的最小记录。

## 何时使用

以下任一项命中时，在首次写回前建立并校验一份工程变更契约：

- 新增、修改、删除公共 interface、公开方法或跨边界模型。
- 修改请求、响应、事件、持久化模型、状态或错误语义。
- 跨模块、多消费者、跨项目或需要兼容 / 迁移的重构。
- 需要把局部测试结果描述为消费者已采用或运行时已生效。

私有方法重命名、单文件行为保持整理和一行低风险修复不强制成文；仍需按工程主能力完成最小判断和验证。

## 写回前最小判断

每个 interface、method、model 都要能回答以下问题：

1. **真实消费者**：谁已经消费它，或哪个已确认用例需要它？不能用计划中的调用点证明价值。
2. **责任与 Owner**：它对哪个可观察结果负责，谁维护状态、不变量、事务、失败和恢复？
3. **契约**：输入、输出、前置条件、空值、错误、版本、兼容和副作用是什么？
4. **最小结构**：已有接口、方法或组合是否足够？新增接口、工厂、Provider、缓存和配置是否有真实变化轴？
5. **验证**：哪个源码锚点、契约测试、消费者编译、运行时场景或独立评审能证明它？

缺少消费者、职责或验证依据时，只能保留为 `candidate` / `pending`，不得直接写成已采用的公共能力。组合编排者默认依赖稳定接口并委托，不因复用代码而继承提供者接口；具体依赖关系由架构师和消费项目规则裁决。

## 证据状态

工程变更契约使用四种事实状态：

- `fact`：已有可回读证据直接支持；每个引用必须指向通过的证据。
- `inference`：由通过的源码或测试证据推导出的判断，不能单独作为准出。
- `pending`：尚未关闭的事实、Owner 决策或运行验证，必须写明 Owner 和停止原因。
- `not_done`：明确尚未完成的动作，必须写明原因和下一验证入口。

采用层级必须与证据一致：

- `candidate`：设计候选或在途变更。
- `provider-verified`：每个变更项直接关联通过的提供者源码和目标测试证据；必要 validator 另按任务约束补充。
- `consumer-adopted`：每个变更项保留通过的提供者源码、目标测试和真实消费者重新编译或契约 / 集成验证证据。
- `runtime-accepted`：每个变更项保留通过的提供者、消费者证据，并关联真实运行路径和失败边界验证。
- `blocked`：存在失败或未关闭的承重阻塞。

局部测试、静态扫描、文档检查、队列投递或单方 ACK 不能单独把状态提升到 `consumer-adopted` 或 `runtime-accepted`。缺少证据时报告 `partial` 或 `pending`，不要用“已完成重构”覆盖范围外缺口。

`verification_refs` 是该变更项当前采用层级的验证依据。`provider-verified` 的每个项必须直接引用通过的 `source` 与 `test`；`consumer-adopted` 还需通过的 `consumer_compile`；`runtime-accepted` 再需通过的 `runtime`。全局证据存在但没有逐项关联，或同一项仍引用这些必需类别的 `fail` / `pending` 证据，都不能证明该接口、方法或模型已经达到当前层级。

未被当前项引用的历史失败或未决证据可保留在全局记录中，用于追溯；它不替代当前通过证据，也不会阻断已修复且逐项关联了当前通过证据的采用层级。

## 机器校验

使用：

```bash
python3 wise-agent/scripts/validate-engineering-change.py <contract.json>
```

校验器只检查结构、引用关系和最低证据门槛，不替代架构判断、业务 Owner、源码 CR 或运行时验收。它不联网、不写文件、不读取密钥；输入由当前任务显式指定，输出只写标准输出 / 错误输出。

契约记录应随现有项目执行规范、任务文档或验证矩阵保存；没有现成状态载体时可以放在任务临时目录，不为此创建长期知识库或第二真相源。
